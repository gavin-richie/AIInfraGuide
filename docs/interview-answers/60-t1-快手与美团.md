## 一、推理与服务

### Q1. PD 分离与 AF 分离：已有 PD 为何还要 AF？（快一 基础 1）

**PD 分离**（[05](./05-推理引擎与优化.md) Q5）：prefill 计算密集、decode 访存密集，混部互相干扰（长 prefill 的 kernel 让 decode 的 TPOT 抖动、decode 的碎片 batch 拖慢 prefill）→ 物理分成两个池独立扩缩容、各自按 SLO 调优（prefill 看 TTFT、decode 看 TPOT），prefill 完成后 KV 传给 decode（Mooncake 式 KV 中心化）。

**AF 分离**（Attention-FFN 分离，[05](./05-推理引擎与优化.md) Q6）：在 decode 内部再切一刀——attention 部分（读 KV Cache，**带宽瓶颈**）与 FFN 部分（权重 GEMM，**算力/带宽混合**）资源画像不同：长上下文时 KV 读占据主导，把 attention 层与 FFN 层放到不同设备组，各自按瓶颈配硬件比例（KV 带宽大的实例跑 attention、算力强的跑 FFN），中间传激活（隐藏维 × batch，量小）。PD 解决"阶段间"干扰、AF 解决"算子间"资源错配——粒度更细，代价是流水线深度增加与激活传输；两者正交可叠加。评价框架：分离的收益 = 干扰消除 + 独立扩缩容 − 传输与调度复杂度。

### Q2. FlashAttention V2 相比 V1 的改进？V4？（快一 基础 2、美一 基础 9、小米校招一面、京校 推理 3）

V1→V2（详见 [04](./04-attention与kvcache.md) Q1/Q2）：①**循环交换**——外层遍历 Q、内层遍历 KV（v1 反过来），Q 块驻留寄存器，O 和 l 不再需要反复重缩放/写回 HBM（v1 每个块更新一次全局 O）；②**在线 softmax 重写**：把分母累加与最大值更新合并，减少非 exp 核操作；③并行度从 (B,H) 扩到 (B,H,S/Bm)——序列维也切 block，长序列小 batch 也能吃满 SM；④寄存器占用优化（tiling 细调 + softmax 缩放常量折叠）。V2 常见 2× 于 V1。V3（Hopper）：warp specialization（生产者-消费者）+ softmax 与 GEMM 的指令级重叠 + TMA + wgmma，再 1.5-2×。**"V4"**：目前没有官方版本（有 FA-3 之上的 sparse 变体/NSA 等研究线），答"V3 之后官方只有 sparse/long-context 变体与 Triton 化的 FlexAttention 生态"即可，能讲清趋势（稀疏化、编译器化、FP8）。仓库实现：`answers/attention/flash_attention.py`（v1/v2 教学版 + 与 SDPA 对拍）。

**实测（RTX 3090，本仓库）**：B2×H8×S1024×D64 causal prefill——显式 $S\times S$ 的 naive 1.07 ms / 峰值显存 212 MB；**SDPA（生产融合 kernel）0.435 ms / 30 MB：2.46× 加速、显存 1/7**（S 越大差距越大，显存从 $O(S^2)$ 变 $O(S)$）。注：教学版 v1/v2 是 python 循环演示算法结构，小 shape 下 launch 开销主导，不代表 kernel 性能。

### Q3. Transformer 一层有几个线性层？TP 怎么切？AllReduce 如何优化？（快一 基础 3）

以标准 LLaMA 层计（忽略 bias）：**7 个**——QKV 投影（可合并为 1 个 [3H·d, d] GEMM，也可算 3 个）、O 投影 1 个、FFN up/gate（SwiGLU，2 个）、FFN down 1 个。TP 切分（[07](./07-分布式训练.md) Q4）：**QKV/O 按输出维（列）切**——各卡持有部分 head，attention 天然按 head 独立，O 投影按输入维（行）切，部分和 **AllReduce**；**FFN up/gate 列切、down 行切**，再 AllReduce。每层 fwd 2 次 + bwd 2 次 AllReduce。

AllReduce 优化：①**列切+行切组合**让中间非线性段免通信（Megatron 的核心设计，AR 从 4 次压到 2 次）；②序列并行 SP 把 AR 换成 RS+AG（总量不变但激活显存 /tp）；③层级通信（NVLink 域内先 RS、域间 AG）；④与计算 overlap（scatter-gather 通信器、异步桶）；⑤减小通信 payload（bf16 梯度、FP8/1bit 压缩）。

### Q4. Ray 的底层实现与关键特性（快一 基础 4）

三层架构：**Driver（提交任务）→ Head/Worker Node（每 node 一个 raylet）→ Object Store**。核心机制：①**Actor/Task 抽象**：一切计算是远程函数（无状态 task，注册到 GCS）或远程类实例（有状态 actor，方法串行保证线程安全）；②**分布式对象存储**：每个 node 一个 Plasma 共享内存 object store，函数返回值写入本地 store，跨 node 通过**按需拉取（fetch）零拷贝共享内存**传大对象（同 node 直接 shm 读）；③**调度**：raylet（本地资源表 CPU/GPU/自定义资源）做自底向上调度——任务创建时带上资源需求，分布式调度器找满足的 node；**GCS（redis/内存）**只存轻量元数据（函数表、actor 位置），不在数据路径上；④**容错**：lineage 重放（对象丢失按依赖重算）、actor 重启；⑤异步：所有 remote 调用立即返回 ObjectRef（future），`.get()` 阻塞取。LLM 相关用法：vLLM 多 worker 管理、RL rollout 的并行环境池（数万 actor 拉起）。

### Q5. CUDA GEMM 的优化方法与 Shared Memory 大小选取（快一 基础 5、快实 基础 4）

完整谱系见 [02](./02-cuda-编程题.md) Q3 与 [03](./03-gemm与算子优化.md)：向量化访存 → smem tiling（消 O(N) 重复读）→ 寄存器 tiling（线程算 4×4/8×8 子块）→ double buffering（cp.async 预取）→ warp specialization/TMA（Hopper）→ split-K（M/N 小 K 大时切 K 换并行）+ autotune。

**smem 大小选取**是本题特色追问，推导：设 tile 为 (BM, BN, BK)，双缓冲需要 A、B 各 2 份：$s = 2 \times (BM \times BK + BK \times BN) \times b_{dtype}$。约束：① ≤ 每 SM smem 上限（Ampere 164KB 可用/Hopper 228KB，留 1KB 保留）；② ≤ 每线程块可映射上限；③ tile 越大复用越高（访存比 $\frac{1}{BK} + \frac{1}{BM}$ 递减）但 occupancy 降——每 SM 的 block 数 = smem 总量/s，通常留 2 个 block 驻留以隐藏延迟；④ 与寄存器配平：每线程 fragment 累加器 $thr\_m \times thr\_n$ 个寄存器，总寄存器 ≤ 255/线程。例：FP16、BM=BN=128、BK=32、双缓冲 → 2×(128×32)×2×2 = 32KB，SM 164KB 可驻 5 块（取 2-4 平衡 occupancy）。经验：先定 BM/BN（128×128 或 64×128），再让 BK 与 bank/向量宽度对齐（BK×dtype = 128bit 的倍数），最后用 autotune 微调。

### Q6. 量化与 FlashAttention 的实际优化效果（快实1 推理 1，重点）

原理部分：量化见 [06](./06-量化.md)（PTQ/QAT、W4A16/W8A8、GPTQ/AWQ/SmoothQuant），FA 见 Q2/[04](./04-attention与kvcache.md)。**实测口径（RTX 3090，本仓库）**：

- **FA（生产 kernel）**：S=1024 causal prefill 相对显式 softmax 版 **2.46× 加速、峰值显存 1/7**（212→30MB）；序列越长优势越大（$O(S^2)$→$O(S)$ 访存）；
- **Weight-only W4**：decode GEMV 实测 bf16 有效带宽 732 GB/s（spec 936 的 78%）；W4 只读 1/4 字节，**理论收益上限 ~5.1×**，Marlin 类解包融合 kernel 实际拿到 **3-4×**（batch 小时）；W8A8 在大 batch prefill 下吃 INT8 Tensor Core 约 2×；
- **量化精度参考**：W4A16 per-group128 + AWQ/GPTQ 校准，Llama/Qwen 系 ppl 掉幅 <0.05，下游任务基本持平；KV FP8 近无损。
- 答题模板：先给机理（decode 带宽受限→W4 有效；attention $O(S^2)$ 访存→FA 有效），再给数字（实测倍数+显存），最后说边界条件（batch 大时量化收益消失、FA 在短序列小 batch 下收益小）。

### Q7. TensorRT 的底层加速原理（快实1 推理 2）

①**图编译优化**：parser 建 network → 优化器 pass 链：常量折叠、算子融合（conv+BN+ReLU、scale/act/短路 elementwise、GEMM 链）、精度下降（FP16/INT8/FP8 层级选择）、kernel autotune（按 GPU 与 shape 实测选 tactic）、内存规划（tensor 生命周期分析复用 buffer）；②**执行期**：序列化 engine 直接加载，CUDA Graph 式整网提交，消除逐算子 launch；③INT8：校准（entropy/minmax）+ INT8 Tensor Core kernel；④动态 shape 用 optimization profile（min/opt/max 三档各编译一次）。对比 PyTorch eager：省 python 开销 + 全图视野的融合与内存复用 + 每 shape 最优 kernel 实测挑选。LLM 侧对应物是 TensorRT-LLM（相同理念 + attention plugin/量化/CUDA Graph/in-flight batching）。

### Q8. vLLM / PagedAttention / Chunked Prefill / Continuous Batching（快实1 推理 3、快实2 基础 1）

- **PagedAttention**（[04](./04-attention与kvcache.md) Q6）：KV 分页（16/256 token 块）+ block table 间接寻址，按需分配、块级共享（prefix cache），显存利用率 >90%，浪费从预留式 ~60-80% 降到 <4%；
- **Continuous Batching**：iteration 级调度，每步结束后完成的序列退出、新序列补位，GPU 不空等整个 batch（静态 batching 的队尾等待消除），吞吐 2-4×；
- **Chunked Prefill**（[05](./05-推理引擎与优化.md) Q3）：长 prompt 切块、与 decode step 混排，平滑 TPOT 抖动；注意语义是**不同请求间**的插入（[61](./61-t1-蚂蚁华为京东.md) Q49）。
- vLLM 整体架构与调度细节见 [05](./05-推理引擎与优化.md) Q2/Q3。

### Q12. GPU 与 CUDA 基本概念、最基础的物理执行单元（快实1 基础 7）

GPU = 大规模并行 SIMD/SIMT 处理器：SM（流式多处理器）为调度执行单元集合，每个 SM 含调度器、寄存器堆、L1/smem、多个 CUDA Core（FP32 ALU）与 Tensor Core。**最基础的物理执行单元是 CUDA Core**（一个 FP32 ALU，线程的最小执行载体；严格说整数/浮点是分离管线）——往下还有 warp（32 线程的调度单位，软件概念但对应硬件 warp scheduler 每 cycle 发射）。层级：thread → warp → block（驻留 SM，共享 smem）→ grid。详见 [01](./01-cuda-基础与体系结构.md)。

### Q13. 模型参数量与计算量怎么算（快实1 项目 8）

- 参数量：ATTN 层 $4 d^2$（QKVO；GQA 为 $2 n_q d + 2 n_{kv} d$）、FFN（SwiGLU）$3 \times 4d^2$（LLaMA 式 $8d^2$）、norm/lm_head 另计 → 每层 ≈ $12 d^2$。Qwen3-8B：d=4096、36 层 → 36×12×4096² ≈ 7.25B + embedding（152K×4096≈0.62B）+ heads ≈ 8.2B ✓；
- 计算量（FLOPs）：每 token ≈ 2×参数量（GEMM 主导）；attention 计算额外 $2 \times 4 \times L \times S \times d$（因果减半）随序列增长。训练总 FLOPs ≈ 6 × 参数量 × token 数（fwd 2 + bwd 4），由 token 量推训练时间见 [05](./05-推理引擎与优化.md) Q11（6ND 定律 + MFU 换算）。

### Q14. 推理框架的算子优化与 Memory Pool 设计（快实2 项目 2/3）

算子优化方法论见 [03](./03-gemm与算子优化.md)（Roofline 判瓶颈 → 访存/计算/调度三类手段）。**Memory Pool 设计**（本题指推理框架的 KV/激活池）：①**布局**：预分配大块显存（启动时按 `gpu_memory_utilization` 切走），内部按 block（16 token）划分，free-list + 引用计数管理；②**分配策略**：per-size-class 的 free list（避免 best-fit 扫描）、O(1) 分配/释放；③**碎片治理**：块大小统一化（分页本身就是解法）、定期 compaction（重映射 block table）；④**复用**：prefix cache（哈希前缀 → 块引用 +1）、swap 到 CPU（分层）；⑤**并发**：多 stream 分配加 lock-free 队列或 arena per stream。参考实现：`answers/attention/paged_attention.py::BlockAllocator/PagedKVCache`（含测试）。

### Q15. 框架测试方案设计（快实2 项目 4）

分层：①**单算子对拍**：与 PyTorch 参考实现比 atol/rtol（含边界 shape 与极端值）；②**数值一致性**：整网输出与 HF 实现比（logits 余弦相似度 > 0.999，逐层误差单调不减的 sanity）；③**性能回归**：固定 shape 集基准（吞吐/延迟/p99），CI 阈值报警；④**长稳/压力**：随机长度 soak test（显存泄漏/碎片/随机崩溃，见 [61](./61-t1-蚂蚁华为京东.md) Q6）、并发与抢占场景；⑤**端到端业务指标**：生成质量评测（ppl/下游任务）防优化伤精度。规模表述：单测覆盖 ~200+ shape 组合、长跑 24-72h、并发达 2× 目标 QPS。

### Q17. MHA/MQA/GQA 与 KV 广播；MLA 对应多少个 GQA head（快实3 基础 2）

MHA/MQA/GQA 见 [04](./04-attention与kvcache.md) Q4/Q5 与 `answers/attention/mha.py、gqa.py`。**KV 广播实现**：GQA 前向把 KV 头复制/扩展到对应 query 组——`kv.repeat_interleave(group_size, dim=1)`（显存放大但可直接用标准 MHA kernel），高效实现是 **grouped GEMM 或索引映射**（kernel 内 query head 按 `kv_head = q_head // group_size` 直接取，零拷贝；vLLM 的 paged kernel 就是按此映射读块）。

**MLA 与 GQA 的对应**（`answers/t1/memory_model.py`）：MLA 每 token 每层只缓存 latent + rope 两段共 $d_c + d_{rope}$ 元素（DeepSeek-V3：512+64=576，FP8 下 576B），与 GQA 每 KV 头 $2d$（K+V）对齐：**等价 head 数 = (512+64)/(2×128) = 2.25 个**；对比 128 头 MHA 压缩 ~57×（`mla_vs_mha_compression`）。MLA 细节（吸收、两段缓存原因）见 [04](./04-attention与kvcache.md) Q3 与 [61](./61-t1-蚂蚁华为京东.md) Q21。

### Q18. ZeRO-1/2/3 显存推导（快实3 基础 3，重点）

完整推导见 [07](./07-分布式训练.md) Q3，此处给快手版追问（P 卡、FP32/FP16 影响）：

- 基线 DDP（混合精度，参数量 N）：FP16 参数 2N + FP16 梯度 2N + 优化器状态 12N（Adam：FP32 master 4N + m 4N + v 4N）= **16N**；
- **ZeRO-1**：优化器状态按 P 卡分片，每卡 $12N/P$ + 完整梯度 2N + 完整参数 2N = $4N + 12N/P$（P=8 时 5.5N，省 66%）；
- **ZeRO-2**：梯度也分片（用 RS 直出分片）= $2N + 14N/P$（P=8 时 3.75N）；
- **ZeRO-3**：参数分片，前向逐层 AG 聚合 = $16N/P$（P=8 时 2N）；
- 纯 FP32 训练：参数 4N + 梯度 4N + 状态 8N = 16N（总账相同、分布不同；混合精度的 12N 优化器状态永远是 FP32——这是新手常错点）；
- 数字题例：N=8B、P=8：ZeRO-1 显存 44GB/卡 → 放进 A100-80G 还要算激活（重算 + TP/PP 分摊）。

### Q19. KV Cache 稀疏计算的实现与 vLLM Triton kernel 写法；为何不用掩码（快实3 项目 7，重点）

**为何不用掩码**：稀疏 attention 用 mask 实现（`attn_weights.masked_fill(~keep, -inf)`）计算量不减少——softmax/GEMM 仍然算全量 $S^2$，只改结果；稀疏的收益必须来自**跳过数据搬运与计算**：按块选取（top-k 块、H2O 淘汰）后只 gather 命中块的 KV 参与点积，访存与 FLOPs 都随稀疏率线性下降。掩码版只在"动态、每步都变、块不规则"的兜底路径有用。

**Triton kernel 写法骨架**（vLLM paged/稀疏 decode kernel 的结构，对照 `answers/attention/paged_attention.py` 的 PyTorch 版）：

```python
@triton.jit
def paged_attn_kernel(Q, K_cache, V_cache, O,                  # KV 按 (num_blocks, block_size, H, D) 分页存放
                      BlockTable, LastLen,                      # 每请求的块表与长度
                      sm_scale, stride_q, stride_o, ...,
                      BLOCK_N: tl.constexpr, BLOCK_D: tl.constexpr):
    pid_req = tl.program_id(0); pid_head = tl.program_id(1)    # 一个 CTA 负责一个 (请求, head)
    kv_head = pid_head // GROUP_SIZE                            # GQA 映射，直接读共享 KV 头
    q = tl.load(Q + pid_req*stride_q + pid_head*stride_h + offs_d)   # (BLOCK_D,)
    m_i = -inf; l_i = 0.0; acc = tl.zeros([BLOCK_D], tl.float32)    # online softmax 状态
    n_blk = tl.load(NumBlocks + pid_req)
    for b in range(n_blk):                                      # 顺序扫块 —— 稀疏版在此改为只迭代选中块
        blk_id = tl.load(BlockTable + pid_req*n_max + b)        # 逻辑块 → 物理块（分页间接寻址）
        k = tl.load(K_cache + blk_id*stride_blk + kv_head*stride_h + offs)  # (BLOCK_N, BLOCK_D)
        qk = tl.sum(q[None, :] * k, 1) * sm_scale
        m_new = tl.maximum(m_i, tl.max(qk, 0))
        p = tl.exp(qk - m_new); alpha = tl.exp(m_i - m_new)
        l_i = l_i*alpha + tl.sum(p, 0)
        v = tl.load(V_cache + ...)                              # 命中块才 load V —— 稀疏的收益所在
        acc = acc*alpha + tl.sum(p[:, None]*v, 0)
        m_i = m_new
    tl.store(O + ..., acc / l_i)
```

要点：①**program 组织**（request × head 切 grid，decode 每 CTA 一个 token 的 query）；②**block table 间接寻址**（分页与非连续 gather 的通用解法）；③**online softmax**（m/l 累计，块间重缩放）；④稀疏化改造点=外层循环只迭代被选中的块（top-k 索引列表传入），kernel 主体不变；⑤ 进一步用 `num_warps/num_stages` 与 `BLOCK_N` autotune。完整可运行版（PyTorch 语义）见 `answers/attention/paged_attention.py::paged_attention_decode`，与 `BlockAllocator` 配套测试在 `tests/test_attention.py`。

### Q20. SmoothQuant 原理细节与超参（快实3 基础 4）

见 [06](./06-量化.md) Q3：迁移因子 $s = \max|X|^\alpha / \max|W|^{1-\alpha}$，等价变换 $Y=(X/s)(sW)$ 把激活离群难度搬到权重。快手追问三点：

- **超参 α 确定**：逐层网格搜索（0.0-1.0，步长 0.05-0.1），目标 = 量化后输出误差（与 FP16 逐层比 MSE/cosine）最小；全局单一 α（易部署）vs 逐层 α（精度更好），论文 α=0.5 起步；也可按"迁移后激活 max 落入 INT8 表示范围"自适应反解；
- **是否适合的判断**：看激活离群结构——**离群集中在少数固定通道（systemmatic/channel-wise outlier）** 且持续出现（所有 token 都有）→ SmoothQuant 有效；离乱随机分布或权重本身饱和 → 无收益；诊断 = 逐层统计激活 per-channel max 的分布（基尼系数/最大最小比），W8A8 时激活 per-channel max 差距 >20× 的层收益最大；
- **看 input 还是 output channel**：看**该层输入激活的 channel 维分布**（即 X 的特征维），因为量化困难来自输入激活的通道离群；对应地 scale 作用在 X 的**特征（input）维** = W 的**输入维（行）** 上做等价缩放（W 按行除 s）。注意表述：对线性层 $Y=XW^T$，s 对 X 的最后一维（input channel）缩放、W 的对应行反向缩放。

### Q21. AWQ 与 GPTQ 的区别、场景选择（快实3 基础 5、快实3 项目 8）

见 [06](./06-量化.md) Q3 对比表：GPTQ（逐列 Hessian 贪心 + 误差补偿，量化慢精度好，适合追求精度的 W4）vs AWQ（激活感知 per-channel scale 保护，快且稳，W4 默认选）。场景：服务化批量部署选 AWQ（校准快、跨模型鲁棒）；精度敏感/极端压缩（W4 以下）用 GPTQ；W8A16 直接 RTN；W8A8 配 SmoothQuant。快手项目视角：线上 decode 服务用 AWQ W4A16（Marlin kernel），离线批处理用 SmoothQuant W8A8。

### Q23. 量化误差视角：理想数据分布、FP4 为何例外（快实 基础 1-3，重点）

- **理想分布**：对称、集中（动态范围窄）、无重尾离群——量化噪声 uniform assumption 成立，相对误差小。均匀分布下的均匀量化是 SNR 最优的直觉：步长与分布宽度匹配、各桶被均匀使用；
- **"分布越均匀量化越好"在 INT8/FP8/INT4 成立**：均匀量化步长一致，分布均匀 → 每个码字的代表性误差一致、无浪费区间；
- **FP4 例外的原因**：FP4（E2M1）只有 16 个码字且**间距非均匀**（指数结构，大值间距大）；若数据均匀分布，绝大多数点落在 FP4 稀疏的大数值区间 → 相邻数值映射到同一码字（粗尾数只有 1 bit mantissa），相对误差暴涨。FP4 适合的是**对数/钟形分布**（LLM 权重恰好接近），且必须配 **block-wise scale**（每 16 元素一个 E4M3 scale，把局部动态范围归一到 FP4 的有效区间——NV FP4 格式的设计核心）。一句话：均匀码字（INT）吃均匀分布，对数码字（FP4）吃对数分布，分布与格式的"形状"要匹配。
- 蚂蚁同族题（均匀/非均匀量化）见 [61](./61-t1-蚂蚁华为京东.md) Q11。

### Q24. CUDA Norm 算子（快实 编程 7）

$(x-\mu)/\sigma$ 即无放射（affine-free）LayerNorm。实现：block 归约求 μ（warp shuffle + smem 两级）→ 同法求方差 → 归一化写回；关键点：**一遍 Welford 或两遍扫**的取舍、广播 μ/σ 到全 block、向量化访存。完整实现与实测：`solutions/cuda/src/norm.cu`（LayerNorm/RMSNorm，含对拍），文档 [02](./02-cuda-编程题.md)。PyTorch 版见 `answers/triton_kernels/layernorm.py`（Triton 融合版）。

### Q25. 性能优化何时接近瓶颈、衡量指标（快校1 基础 2）

### Q26. 算子融合的工程难点（快校1 基础 3）

### Q27. 多设备/多任务负载均衡（快校1 基础 5）

分层答：①**任务级**：按预估开销（token 数/模型大小）加权分队列，动态再平衡（work stealing）；②**卡级**：TP 组内天然同步（木桶效应，同批最慢卡决定速度）——组内选同型号同负载卡、ECC/降频监控；③**请求级（推理）**：goodput 调度（SLO 内吞吐最大）、KV 水位感知路由、prefix 亲和（请求路由到有前缀缓存的实例）；④**MoE**：expert 负载均衡损失 + 溢出丢弃策略。快手场景：异构卡混部时按"算力当量"加权分配 micro-batch 数。

### Q28. H100 相比 A100 的架构改进（快校2 基础 1）

①SM 结构：Ampere 108 SM → Hopper 132 SM，每 SM 4 组 warp scheduler 不变但寄存器/smem 扩大（smem 164→228KB）；②**线程块集群（TGPC/DSMEM）**：block cluster 让多 block 共享分布式 smem；③**TMA**（异步批量张量拷贝，硬件多维 descriptor）；④**warp specialization + wgmma**（异步寄存器级 MMA）；⑤**FP8 Tensor Core**（E4M3/E5M2，dense ~2×于FP16）；⑥Transformer Engine（软件栈）；⑦互联：NVLink 600→900 GB/s、NVSwitch 全互联。对 kernel 开发的影响（迁移改造清单）见 [07](./07-分布式训练.md) Q15。

### Q29. Warp 概念与作用（快校2 基础 2）

见 [01](./01-cuda-基础与体系结构.md)：32 线程的调度执行单位，SIMT 锁步 + 分支掩码（divergence 串行化）；warp shuffle 做寄存器间归约（`__shfl_sync`）、warp 是 smem/bank 访问与 launch 配置的基本颗粒（block 尺寸取 32 倍数）。

### Q30. DP 与 TP-SP 的计算通信重叠（快校2 基础 3）

- **DP**：梯度桶化——反向产出梯度攒 bucket，bucket 满即发起 AllReduce，与后续层反向计算重叠（NCCL 异步 + compute stream）；梯度累积用 `no_sync` 延后通信；
- **TP**：fwd 的两次 AllReduce 与计算天然串行（需要完整输出）——重叠手段：把 AR 拆 chunk 流水（边算边 reduce）、RS+AG 形式的 SP 化；bwd 的 AR 与上一 micro-batch 的 fwd 重叠（**one-batch overlap / TBO**：micro-batch A 的通信与 B 的计算配对，[07](./07-分布式训练.md) Q6）；
- **SP**：LN/Dropout 的 RS/AG 与 TP 的 AR 合并成总量不变但可切小块重叠的组合。
- 本质：通信与计算在不同资源（NVLink/NIC vs SM）上，重叠条件是**无数据依赖**（下一块计算不依赖本次通信结果）——按依赖图找可并行对。

### Q31. 使用 PP 与不使用 PP 的显存峰值（快校2 基础 5）

不同。PP 下每卡只存**本 stage 的层**（权重/优化器状态按层数均分，约为总量的 1/p），但新增：①流水线气泡（时间换显存）；②**in-flight 激活**：1F1B 下第 j stage 驻留最多 $p-j$ 个 micro-batch 激活（首卡最多）；③micro-batch 切小后单卡放不下的大模型可训。**显存峰值**：PP 显著低于 TP 全复制（TP 权重均分但每卡持全层激活 + 通信缓冲）。用 PP 时峰值 = 权重/p + 激活(与调度相关) + 通信缓冲；不用 PP（纯 DP）= 全部 16N + 激活。可运行对比见 `answers/t1/zero_bubble.py` 的 `peak_activations`（GPipe=m、1F1B≤p-j、ZB-H2≈2p-1）。同族：华为 PP 题 [61](./61-t1-蚂蚁华为京东.md) Q28。

### Q32. CUDA_DEVICE_MAX_CONNECTIONS 与 launch bounds、H2D/D2H 重叠（快校2 基础 6/7）

- **CUDA_DEVICE_MAX_CONNECTIONS**：每 SM 的**连接数**（并发流上下文/工作队列数，Ampere+）。每连接占用 1 个 smem buffer 用于 grid 排序（CUDA 12 之前），多流并发时若连接不足会串行化。经典关联：**warp specialization / 多流 kernel 的并发**（减少连接数可强制不同流 kernel 排队，反而提高单 kernel occupancy——TRT-LLM 与 FA3 都调它）；设小（如 1）会让多 stream 顺序执行但每 kernel 资源更足；
- **`__launch_bounds__(maxThreadsPerBlock, minBlocksPerSM)`**：编译器提示——限制寄存器使用量（溢出到 local memory 换 occupancy）、指导指令调度；适用：已知 block 尺寸与目标驻留数的 kernel；
- **H2D/D2H 重叠**：可以。DMA 引擎独立于 SM——用**独立 stream + 异步拷贝 API**（`copy_` 带 `non_blocking=True` + pinned memory），与计算流并发；同一 stream 内串行。pinned memory 是达到全带宽的前提。

见 Q5（smem 推导）+ [02](./02-cuda-编程题.md) Q3：分块三重目的（数据复用、并行分解、寄存器/smem 适配）；块大小选择逻辑：BM×BN 由寄存器（累加器）与复用率定（128×128 经典），BK 对齐向量宽度与 bank（32×dtype=128b），乘上 double buffer 后 smem ≤ 上限且留 ≥2 block 驻留；M/N 小时用 split-K（K 切分并行 + 归约），batch 小 GEMM 用 stream 并发或 grouped GEMM。最后 autotune 实测选（理论只给候选）。

## 二、美团（AI Infra 面）

### Q35. Decoder-only vs Encoder-only（美一 基础 2）

Decoder-only（GPT 系）：causal mask + next-token 目标，生成与训练目标一致（无 exposure bias 的 mismatch）、KV Cache 自然支持、 Scaling 律最好（数据效率高，等参数量下做生成任务强）；不足：双向理解任务（检索/分类 embedding）要改造（prefix LM/填充式）。Encoder-only（BERT 系）：双向注意力，判别式任务（分类/NER/检索召回）强、表示质量高；不能自然做自回归生成、每位置只训练一次 masked 预测（数据利用低于 LM 的每 token 监督）。现代趋势：decoder-only 统一（理解任务靠 prompt/下游 head + 强嵌入模型也是 decoder-only 训练如 E5/BGE）。

### Q36. LLaMA 的主要设计（美一 基础 3）

Pre-LN RMSNorm（无 bias/均值，比 LN 稳且快）、SwiGLU FFN（门控，三个矩阵 dim 2/3·4d）、RoPE（相对位置，外推友好）、无 bias 全连接、词表 sentencepiece 32K、AdamW+cosine、Chinchilla-optimal 数据配比。2/3 演进：GQA（2 起）、长上下文 YaRN（2/3）、tie embedding（小模型）、3 的 QK-Norm 与 thinking mode。与 Qwen 差异见 [61](./61-t1-蚂蚁华为京东.md) Q38。

### Q37. CUDA 编程模型/内存层级/bank conflict/寄存器溢出（美一 基础 4-7）

集中见 [01](./01-cuda-基础与体系结构.md)：层级 grid/block/thread + smem/global/const；bank conflict：32 bank×4B，跨步访问冲突 → padding/swell 存取模式/广播；寄存器问题：每线程 255 上限，超了**溢出到 local memory**（实为 global，慢 10-100×）——诊断（`-Xptxas -v` / NCU 寄存器计数）与治理（减小 tile、launch bounds、`__restrict__` 帮助缓存、拆 kernel）。OPPO/网易同族题见 [62](./62-t1-小米oppo-vivo-网易等.md)。

### Q38. GPU 与 CPU 多线程调度差异（美一 基础 8）

CPU：粗粒度任务级抢占调度（OS 时间片、上下文切换 μs 级、分支预测/大缓存优化单线程延迟），线程间独立进展；GPU：**细粒度吞吐调度**——warp 为单位、无抢占（kernel 内不可换出，同 SM 多 warp 靠**切换隐藏延迟**而非等待）、锁步 SIMT（分支用掩码串行）、上下文极轻（硬件 warp scheduler 每 cycle 发射）。结论：CPU 优化延迟（快速完成单任务），GPU 优化吞吐（万级线程切换掩盖访存延迟）；B站同族（调度公平性）见 [62](./62-t1-小米oppo-vivo-网易等.md) Q33。

### Q39. Zero-Bubble 流水线调度原理（美实 基础 1，重点）

论文：*Zero Bubble Pipeline Parallelism*（arXiv:2401.10241）。可运行模拟：`answers/t1/zero_bubble.py`（GPipe/1F1B/ZB-H1/ZB-H2，pytest 断言全部公式）。

**机理**：把反向拆成 **B（输入梯度）** 与 **W（权重梯度）**——B 必须回传上游卡（跨卡关键依赖），W 只被 optimizer step 依赖、**可任意延后**。1F1B 的气泡来自 warmup/drain 期间等梯度；ZB 的两招：①**延后 W**：B 链每跳只花 b（不被 W 拖慢），梯度更早回流；被延后的 W 塞进空闲时隙（fill bubble）与尾部（drain）；②**放松优化器依赖**：step 只等本卡 W，不等全卡同步。调度变体：

| 调度 | 气泡（首卡 idle） | 激活峰值 | 说明 |
|---|---|---|---|
| GPipe | $(p-1)(f{+}b_{total})$ | m（全部微批驻留） | 全前向后全反向 |
| 1F1B | $(p-1)(f{+}b_{total})$ | ≤ p（O(p) 驻留） | 时间同 GPipe、显存 O(p) |
| **ZB-H1** | $(p-1)(f{+}b{-}w)$ | 与 1F1B 相当（W 占的内存更小） | 同 1F1B 结构 + W 延后填隙 |
| **ZB-H2** | **0**（所有卡零 idle） | ~2p-1（首卡） | 加大 warmup + W 重排 + step 放松，trapezoid→parallelogram |

**模拟器实测**（p=8, m=32, f=b=w=1，`summary_table()` 可复现）：1F1B 总时长 110、首卡 idle 14；ZB-H1 总 103、idle 7（恰 ½，论文"⅓"对应其实验 F/B/W 配比）；**ZB-H2 总 103、全部卡 idle=0**，总时长 = $(m{+}p{-}1)f + m(b{+}w)$；代价 = 激活峰值 17 vs 1F1B 的 8（显存换气泡）。工程配套：微批数 m ≥ 2p 才能填满、通信可另入 ILP、conv 依赖（如 BN 统计）要 ZB-V 变体。答题结构：气泡来源 → B/W 拆分原理 → H1/H2 两个调度与公式 → 显存代价 → 配套条件。

### Q40. DeepEP 的设计思想与核心机制（美实 基础 2，重点）

DeepSeek 开源的 **MoE 专家并行通信库**（dispatch/combine 两个 all-to-all 语义原语），目标：把 EP 的通信从 NCCL all-to-all 的通用路径上特化到 MoE 负载，压延迟提带宽。核心机制：

1. **两种模式**：**Normal（高吞吐）**——训练/prefill 大 batch；**Low-latency（低延迟）**——decode 小 batch 纯 RDMA 单边写；
2. **Normal 模式**：**节点内纯 NVLink**（基于 NVSHMEM 对称内存，token 直接 P2P 写到目标卡的接收 buffer，无根代理无额外拷贝）+ **节点间 RDMA**（IB GDR），dispatch 与 combine 融合为**单 kernel**（路由计算、padding、收发一个 kernel 完成，消灭中间 kernel launch 与 staging copy——NCCL all-to-all 要先打包进连续 buffer、group launch 开销大）；
3. **Low-latency 模式**：每卡**预注册固定大小的 RDMA buffer**（避免运行时分配）、one-sided 直写 + 上下层 hook（发送前/接收后回调，可插入量化/反量化），支持 **FP8 传输**（bytes 减半）；典型把 dispatch 延迟压到 ~50μs 级；
4. **与计算 overlap**：hook 与分层 buffer 让 dispatch/combine 与 expert GEMM 流水（DeepSeek-V3 的 DualPipe 双向重叠就是建立在它之上）；
5. 对比一句话：NCCL all-to-all 是通用集合通信（数据无关），DeepEP 是**面向 MoE token 路由的专用点对点库**：拓扑感知（NVLink 域内/域间分治）、零中间拷贝、单 kernel、低延迟模式免分配。

### Q41. RL 中的异步调度方案与算法适配（美实 基础 3/4）

RLHF/RL 训练的三大环节（generate rollout → 算 reward/advantage → 更新 policy）资源画像不同（rollout 是推理负载、更新是训练负载），异步方案谱系：

- **同步 on-policy**（标准 PPO）：所有 worker 同步采样 → 聚合更新，GPU 利用率低（rollout 时训练卡闲）、但数据严格 on-policy；
- **半异步（one-actor 异步/impala 式）**：actor 持续 rollout、learner 持续消费，旧数据用**重要性采样比 r = π_new/π_old** 修正（V-trace 截断防发散）；
- **全异步 disaggregated**（现代 LLM RL：rollout 与 training 物理分离的推理集群 + 训练集群，权重异步同步（增量/广播），KV/经验经 replay 传递；
- 各自优缺点：同步——简单稳定但资源利用率低；半异步——利用率升但引入 off-policy 偏差（r 方差大时要 clip/punish）；全异步——吞吐最高（每种负载独立扩缩容），但要做 staleness 控制与 loss 修正，且权重版本管理复杂（参数服务器/一致性哈希路由）。

**算法层适配**：①重要性采样 + PPO clip 容忍轻度 off-policy；②V-trace（impala）截断旧数据的有效性；③经验回放配 KL 约束防漂移；④rollout 的采样参数（temperature/top-p）与训练 temperature 一致性；⑤GRPO 的组采样在异步下要保证同组样本同权重版本（组内一致性比组间重要）；⑥reward model 与 policy 的版本对齐（旧 reward 评分引入漂移）。

### Q42. Transformer 架构与 RNN 对比（美北 基础 1）

RNN/GRU/LSTM：序列递推 $h_t = f(h_{t-1}, x_t)$——任意步长 O(1) 参数，但**无法并行训练**（时间依赖链）、长程梯度消失（LSTM 门缓解但 ~百级）、上下文有界。Transformer：自注意力的全局依赖（任意两位置直连路径长度 1）+ 完全并行（矩阵乘）+ 位置编码补时序信息；代价：O(S²) 计算/显存（长上下文的主线优化：FA/稀疏/线性注意）、外推要 RoPE 类处理。结论表述：Transformer 赢在"并行度带来的可扩展性"（Scaling 律兑现），不是单步建模能力。

### Q43. Transformer 参数分布、计算量最大的部分（美北 基础 2）

参数：每层 $12d^2$ 中 FFN 占 $8d^2$（SwiGLU 3×）≈ 2/3、attention $4d^2$ ≈ 1/3（GQA 更少）；**参数量最大**：FFN（大 embedding 的模型如 Qwen 152K 词表时 embedding+lm_head 可到 0.6-1.2B 超过单层 FFN，但通常说"FFN 占大头"）；**计算量最大**：同样是 FFN GEMM（FLOPs 与参数成正比，每 token 2×params），但**长序列时 attention 的 QK^T/PV 是 O(S²) 项**会反超（S > ~6×d 时，见 [05](./05-推理引擎与优化.md) Q1 的分界推导）；推理 decode 阶段 attention 的 KV 读取是带宽瓶颈。参数量/计算量公式展开见 Q13。

### Q44. CUDA Core 与 Tensor Core、常用 GPU 型号（美北 基础 3）
