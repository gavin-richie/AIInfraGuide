## Q1. 当前 LLM 推理的主要瓶颈在哪里？（云-实习 Q1）

分阶段回答（面试官想听"分层 + 定量"）：

1. **Decode 阶段：memory bound**。每步只算 1 个 token，GEMV/瘦 GEMM 算术强度极低，瓶颈是**权重读取 + KV Cache 读取**的带宽。7B fp16 权重 14GB，3090 带宽 936GB/s → 纯 decode 上限 ~70 tok/s/卡；batch 增大分摊权重读取后 KV 读取成为新瓶颈。
2. **Prefill 阶段：compute bound**。FLOPs ∝ S²，长 prompt 的 TTFT 由算力决定（FA 后注意力部分已近最优，大头在 GEMM）。
3. **调度与执行层**：kernel launch 开销（小 batch 每步几十个 kernel）、Python 调度开销、prefill/decode 混跑互相干扰、batch 组装 padding 浪费。
4. **显存容量**：KV Cache 随 batch×序列线性增长，先于权重把显存吃满 → 限制并发（PagedAttention 解决利用率，不减少总量）。
5. **长尾**：多轮对话 prefix 重复计算、采样/解码的 CPU 开销、output tokenization。

一句话总结：**小 batch decode 是带宽瓶颈、大 batch prefill 是算力瓶颈、资源层是显存与调度瓶颈**——对应三条优化主线：量化/compression（降带宽）、PD 分离/chunked（解干扰）、continuous batching/CUDA Graph（降开销）。

## Q2. vLLM 有哪些核心优化技术？逐一说明（云-二面 Q3、云-实习-二面-2 Q1）

三大支柱详解见《推理引擎与优化》Q2，此处按"逐一说明"的展开粒度：

1. **PagedAttention**：KV 分页管理（16 token/块 + block_table），显存利用率从 20-40% 提到 >90%，copy-on-write 支持 beam search 前缀共享（详见《Attention 与 KV Cache》Q6，`solutions/python/src/answers/attention/paged_attention.py`）。
2. **Continuous batching**（Orca）：调度粒度 = 每 step 迭代，完成的请求立刻退出、新请求插队，消除 padding 与批次气泡。
3. **Prefix caching**：按前缀块哈希缓存 KV，多轮对话/共享 system prompt 免重算，TTFT 大幅下降。
4. **Chunked prefill**：长 prompt 切块与 decode 交错，平衡 TTFT 与 TPOT（详见《推理引擎与优化》Q3）。
5. **CUDA Graph**：按 batch 档位捕获 decode 网络图，消除每 step 数十次 launch 开销（小 batch decode 提升显著）。
6. **量化支持**：GPTQ/AWQ/FP8（W4A16 详见本篇 Q21）。
7. **投机解码**：EAGLE/MTP/n-gram draft + target 验证，单请求延迟 2-3×。
8. **多 GPU**：TP（单机）、PP、PD 分离（disaggregated prefix caching）。

追问"最核心的是哪个"：答 PagedAttention（显存利用率是吞吐的地基）+ continuous batching（调度是吞吐的放大器），两者组合才有后来的 prefix cache 与 PD 分离。

## Q3. vLLM 近期值得关注的新特性？（控股-一面 Q5）

以 2025-2026 的 V1 引擎为主线索（版本迭代快，答题时声明时间点）：

- **V1 engine 全面取代 V0**：重写调度器（零开销调度，核心循环移入 Rust/C++ 侧的思想 + 前端异步化）、prefix caching 默认开启、async output processing（token 生成与后处理流水线化）。
- **Piecewise CUDA Graph**：prefill 与 decode 统一支持 CUDA Graph 捕获（按 piece 分段），小 batch decode 与中等 batch 均受益。
- **投机解码体系化**：EAGLE-1/2/3、DeepSeek-MTP、n-gram（ agents 输出重复多的场景免费加速）。
- **量化生态**：FP8（GPTQ/AWQ Marlin 路线外的新默认）、GPT-OSS 的 MXFP4、NV FP4（Blackwell）。
- **PD 分离与KV 传输**：disaggregated prefill 生产可用（Mooncake/NIXL 等传输后端）。
- **结构化输出**：xgrammar 后端，JSON schema 约束生成的吞吐损失大幅缩小。
- **多模态与 agent 场景**：V1 原生多模态 interleaved batch、工具调用解析器（tool parser）丰富。
- **可观测性**：Prometheus 指标、request-level tracing。

## Q4. DeepSeek-MTP 用在训练还是推理？工作流程？（云-二面 Q4、云-实习-二面-2 Q3）

**两个阶段都用，作用不同**（这是考点）：

- **训练阶段：辅助训练目标**。V3 在 transformer 主干之后挂 MTP 模块（独立的 1 个 transformer 层 + 共享 embedding/output head，V3 取深度 D=1 即预测下下个 token；更早的多深度级联是 V2 时代的探索）。输入 = 主干最后一层输出（norm 后）与下一 token embedding 拼接，总 loss = 主 loss + λ·MTP loss。收益：更充分的监督信号改善表征，训练后模块不丢弃。
- **推理阶段：投机解码的 draft model**。MTP 模块天然是"小 draft"：主模型 forward 产出第 1 个 token 的同时，MTP 模块以一个轻量层的代价快速产出第 2 个候选；主模型**下一次 forward 并行验证**候选（一次前向算出各位置 logits），按拒绝采样接受最长相容前缀。decode 是 memory bound、多验证几个位置几乎免费 → V3 报告 MTP 投机解码加速 **~1.8×**。

追问"为什么不直接用独立小模型做 draft"：MTP 与主模型**共享 embedding 与主干表征**，分布一致性好（接受率高）、显存额外开销小（每模块 1 层）、无需维护两个模型。

## Q5. GQA 的设计动机与作用；MHA/GQA/MLA 三者区别与适用场景（一面-1 Q1、实习-1 Q1）

手写与显存公式见《Attention 与 KV Cache》Q4（`solutions/python/src/answers/attention/gqa.py`）。

- **动机**：MQA 把 KV 头压到 1，KV Cache 缩 n_h 倍但质量受损；GQA 折中——每组 `n_h/n_kv` 个 Q 头共享一个 KV 头（如 Llama-2-70B / Qwen 系 32 Q 头 + 8 KV 头，KV Cache 缩 4 倍），质量几乎不损失。本质是"参数共享降低 KV 容量，但保留组内多样化的查询视角"。
- **MLA**：不走"减头数"路线，而是**低秩压缩**——KV 联合投影到 d_c（如 512）维 latent 存 cache，decode 时用 up-projection 吸收进权重矩阵还原，KV Cache ≈ d_c+d_r（RoPE 解耦部分）远小于 2·n_h·d_h（详见《Attention 与 KV Cache》Q3，`mla.py` 含吸收路径数值验证）。
- **适用场景**：MHA（小模型/短上下文，质量优先、显存不紧张）；GQA（当前主流默认，工程兼容性最好）；MLA（长上下文 + 大 batch 高并发，KV 访存是瓶颈时收益最大，但 kernel 生态与 TP 切分更复杂）。

## Q6. MoE 路由针对每个 token 还是每个序列？（一面-1 Q2）

**主流是 token 级**：每个 token 独立过 router（gate）选 top-k 专家（GShard/Switch/Mixtral/DeepSeekMoE 全部如此）。原因：

1. **表达力**：同一序列中语法功能 vs 专业知识 token 需要不同专家，序列级路由把整句送进同一专家组，混合粒度太粗；
2. **负载均衡**：token 数远大于序列数，大数定律下专家负载更均匀，auxiliary loss 才有效；
3. **组合性**：DeepSeekMoE 的细粒度专家设计（更多小专家 + 共享专家）依赖 token 级组合（选 8 个 64 维小专家 ≈ 组合出 2 个大专家的能力）。

例外/变体：**expert-choice routing**（反向由专家挑 token，天然均衡但训练推理不对称）、**sequence-level routing**（部分早期工作与生产简化：序列 hash/embedding 路由，省 router 开销但能力受限，基本被淘汰）。追问点：capacity factor 与 token dropping 都建立在 token 级路由上；DeepSeek-V3 的 noaux-tc（bias 修正的负载均衡）也是。

## Q7. MoE 如何判断"真正实现了专家分工协作"而不是 Dense 参数切分？（AI-Infra-1 Q11）

五个可操作的检验方法（面试亮点是给出**干预实验**而不是只看可视化）：

1. **路由统计**：专家利用率分布（熵/基尼系数）——健康状态是负载均衡但**不是均匀随机**（均匀随机的 router 等价于 Dense 平均，毫无意义）；看路由是否随输入语义聚类。
2. **专家特化分析**：对每个专家收集被路由的 token，统计词法/句法/主题分布。Mixtral 论文的结论值得引用：**分工主要在 token 级的浅层模式（数字、标点、缩进）而非高级语义主题**——"专家≠领域专家"。
3. **消融对照**：把 k 个专家换成 1 个等参数量的 Dense FFN（或专家权重平均），若 MoE 无增益 → 只是参数切分；真正的分工应表现为同训练算力下 MoP/MoE 曲线更优。
4. **干预实验**：定向禁用某专家，观察哪类输入退化（分工明确的模型会出现选择性退化）；或交换两个专家的 router 权重行看输出扰动。
5. **梯度/优化视角**：router 的 aux loss 曲线、专家间梯度冲突度量；upcycling（从 Dense 初始化）后的分化轨迹。

## Q8. Expert Parallelism 中 Dispatch 和 Combine 的具体流程（控股-一面 Q1）

EP 下每个专家放在一个 rank 上（或复制），一个 batch 的 token 分散在各 rank：

1. **Router 计算（本地）**：每个 token 算 top-k 专家 id 与 gate 权重。
2. **Dispatch（all-to-all ①）**：按目标专家所在 rank 把 hidden states 发出去。工程细节：token 先按目标 rank **分组排序（permute）**让同 rank 的 token 连续（通信高效）、top-k 展开意味着每个 token 最多发 k 份；容量控制（capacity factor）在源端丢弃超额 token。
3. **专家计算**：每个 rank 收到发给自己专家的 token，按专家分组做 FFN 前向（组内 GEMM 规整）。
4. **Combine（all-to-all ②）**：结果沿原路发回来源 rank，**inverse permute** 恢复 token 顺序，按 top-k gate 权重加权求和，加上共享专家输出（若有）。

反向是对称的两跳 all-to-all（grad dispatch/combine）。开销与优化：两跳 all-to-all 是 EP 最大开销 → DeepEP 用**低精度（BF16/FP8）RDMA 传输 + NVLink 两跳**、把 dispatch/combine 与计算重叠（hook 机制）、Two-Batch Overlap 用两个 micro-batch 交错掩盖。详见《分布式训练》Q8（DeepSeek-V3 关键优化）。

## Q9. DeepSeek 系列模型的架构特点（控股-一面 Q2）

系统展开见《分布式训练》Q8，按"架构清单"口径：

1. **MLA**：KV 低秩压缩 + 解耦 RoPE，KV Cache ~1/10 于 MHA（本篇 Q5）；
2. **DeepSeekMoE**：细粒度专家（小 FFN 多专家）+ 共享专家（常驻捕获通用知识）+ noaux-tc 负载均衡（每专家一个可学 bias 修正路由，去掉梯度干扰的 aux loss）；
3. **MTP**：训练辅助目标 + 推理投机解码（本篇 Q4）；
4. **FP8 混合精度训练**：细粒度 block-wise scaling 的 FP8 GEMM（128×128 block scale），训练成本 ~减半；
5. **通信**：DualPipe（双向 PP 流水线把计算与通信气泡对齐掩盖）、DeepEP 两跳 all-to-all；
6. **671B 总参 / 37B 激活**（V3），V3.1/R1 加上 NSA/DSA 稀疏注意力路线（见《分布式训练》Q9）。

## Q10. TP 中 AllReduce 需要执行多少次？如何推导（控股-一面 Q3）

基础见《分布式训练》Q4（TP 先列切后行切的推导）。推导用 Megatron 的 **f/g 算子**：

- TP 把每层分成两个 matmul 对：`[ColumnParallel(W_qkv)] → attention → [RowParallel(W_o)]` 与 `[ColumnParallel(W_gate/up)] → GeLU/Mul → [RowParallel(W_down)]`。
- Column+Row 组合的数学：$Y = (XA_1)A_2$，$XA_1$ 每个 rank 只有部分列，$A_2$ 每个 rank 只有部分行 → 乘积是**部分和**，必须 AllReduce 求和才是完整 $Y$。Megatron 定义：**g** = 前向 AllReduce / 反向恒等（放在组末），**f** = 前向恒等 / 反向 AllReduce（放在组首，反向把 $\partial X$ 的梯度求和）。
- **结论：前向每层 2 次 AllReduce（attention 输出、FFN 输出），反向每层 2 次（对应两个 f 的梯度求和），合计 4 次/层**；加 embedding 层（列切+一次 AllReduce）与 LM head（列切+AllGather 或一次 AllReduce）另计。
- 通信量：每次 2(n-1)/n · b·s·h · 2bytes（Ring AllReduce 的 2 倍数据量），这也是 TP 只在 NVLink 域内做的原因。加序列并行（SP）后 AllReduce 分解为 ReduceScatter + AllGather，总量不变但与 SP 的通信合并。

## Q11. KV Cache 显存占用如何计算？（控股-一面 Q4）

公式与代码见《Attention 与 KV Cache》Q7（`gqa.py::kv_cache_size`）：

$$\text{bytes} = 2_{(K,V)} \times L_{(\text{层数})} \times n_{kv} \times d_h \times B \times S \times \text{dtype 字节}$$

例：（L=32，n_kv=8（GQA），d_h=128，fp16，7B 级典型配置）单请求 S=4096：2×32×8×128×4096×2 = **512MB**。追问三个方向：① GQA/MLA 的缩减系数；② KV 量化（FP8 减半、INT4 1/4，需 per-block scale）；③ PagedAttention 改的是**利用率**不是总量（碎片从预留 max_len 的 60-80% 浪费降到 <10%）。

## Q12. KV-Cache 是训练用还是推理用？为什么训练不用？（校招-一面 Q2）

**推理（decode）专用**。训练是 teacher forcing：整句一次前向，每层的 K/V 本来就整批存在显存里并行参与 attention，无"逐 token 生成"过程；且训练要反向传播，中间量必须保留（激活 memory 由 checkpointing 管理），cache 概念没有意义。推理 decode 逐 token 生成，第 t 步若不缓存前 t-1 步的 K/V 就要重算 O(t) 长度的前向 → 总复杂度 O(S²) 退化，KV Cache 把每步降为 O(1) 增量。追问：推理的 prefill 阶段其实也不需要 cache（一次算完），cache 是 decode 阶段的概念；训练中类似思想的是 gradient checkpointing（时间换空间，方向相反）。

## Q13. Flash Attention 的核心思想；除 FA 与 KV Cache 外还有哪些注意力优化？（校招-一面 Q3/Q4）

FA 详解见《Attention 与 KV Cache》Q1（tiling + online softmax + kernel fusion，`flash_attention.py` v1/v2 与 SDPA 对拍）。其他优化按层次：

1. **结构层减少 KV**：MQA/GQA/MLA（Q5）；
2. **稀疏化**：滑动窗口（Mistral）、sink+窗口（StreamingLLM）、Longformer/BigBird 全局+局部、可学习稀疏 NSA/DSA（DeepSeek，训练感知的 token 选择）；
3. **线性化**：Linear Attention/RetNet/GLA/Mamba/RWKV——把 O(S²) 降 O(S)，用状态空间/核化替换 softmax；质量与长文本召回有差距，2025-2026 在快速逼近；
4. **访存层**：PagedAttention、KV 量化（FP8/INT4，KIVI 按通道非对称）、KV 淘汰（H2O 重打分驱逐）；
5. **复用层**：prefix cache、prompt cache（KV 复用）、跨请求共享系统前缀；
6. **解码算法层**：投机解码/MTP（Q4）、Medusa 多头并行生成。

## Q14. 量化的基本原理与实施流程（实习-一二面 一面 Q3）

原理与分类见《量化》Q1。实施流程（PTQ weight-only 主线）：

1. **校准数据准备**：从训练分布采样 128-512 条样本，前向收集待量化层的输入激活统计（max/直方图/Hessian）；
2. **确定量化参数**：per-channel/per-group 的 scale（与 zero），方法 minmax / percentile / KL / MSE 网格 / GPTQ 的 Hessian 贪心 / AWQ 的 α 搜索（Q21）；
3. **权重变换与打包**：quantize → pack（int4 打包 uint8/int32，group scale 存储）→ 按 kernel 布局重排；
4. **模型改造**：替换 Linear 为量化 Linear（W4A16/W8A8），attention kernel 改读量化 KV（若做 KV 量化）；
5. **验证与回归**：逐层余弦相似度/相对误差 → PPL（wikitext/cnwiki）→ 下游 benchmark → 业务 case；不过关的层回退高精度（混合精度）；
6. **性能验收**：kernel 级（Marlin/awq kernel vs cublas fp16）与端到端 serving benchmark。

## Q15. FP32 / FP16 / INT8 的底层存储格式与差异（实习-一二面 一面 Q2）

| 格式 | 位宽（符号/指数/尾数） | 动态范围 | 精度 | 备注 |
|---|---|---|---|---|
| FP32 | 1 / 8 / 23，bias 127 | ~±3.4e38 | 23 位尾数 ≈ 7 位十进制 | 训练传统默认、科学计算 |
| FP16 | 1 / 5 / 10，bias 15 | ~±65504，最小正规数 6.1e-5 | ~3-4 位十进制 | 混合精度激活/权重；上溢下溢风险 |
| BF16 | 1 / 8 / 7 | 与 FP32 相同 | ~2-3 位十进制 | LLM 训练默认：范围大不易溢出 |
| INT8 | 8 位补码 | -128..127 | 均匀 256 级 | 需 scale/zero 映射，只做整数累加 |

要点：浮点的**指数决定范围、尾数决定相对精度**——FP16 与 INT8 同为 16 种排列组合级别的表示力但分布完全不同：浮点相对误差均匀（对数量化），整数绝对误差均匀（线性量化）；所以 weight 适合细 group 整数量化（分布集中），激活的离群值是整数量化难点（SmoothQuant 思路，见《量化》Q3）。

## Q16. 大模型训练/推理显存不足的优化方案（一面-2 Q9 开放题）

训练侧：ZeRO-1/2/3 切分优化器态/梯度/参数（见《分布式训练》Q3）、activation checkpointing（重算省激活 ~1/3 计算换显存）、混合精度 BF16 + FP8、梯度累加（等价大 batch 不加显存）、8bit optimizer（AdamW 状态压 1/4）、CPU/NVMe offload、序列并行切激活（见《分布式训练》Q11）、PP 切参数。

## Q17. 多卡协同的通信方式；NVLink 与 RDMA 各自特点（云-实习-二面-1 Q5）

**通信方式分层**：①机内：NVLink/NVSwitch（GPU↔GPU 直连，H100 NVLink 900GB/s）、PCIe P2P（~32GB/s）；②机间：InfiniBand RDMA（200/400Gbps）、RoCE（以太网上的 RDMA）、TCP（fallback，慢一个量级）；③软件原语：NCCL（AllReduce/AllGather/ReduceScatter/AllToAll，自动选 ring/tree 算法与拓扑）、NVSHMEM（对称堆一步编程）、UCX/gRPC（控制面）。

- **NVLink**：私有高带宽低延迟互连，cache 一致性协议支持统一内存寻址；仅限机内/单节点域（NVSwitch 全互联），是 TP 的载体。
- **RDMA**：内核旁路 + 零拷贝，远端直接读写对端注册内存（网卡 DMA），延迟微秒级不占 CPU；IB/RoCE 走交换机可扩展到千卡，是 EP 的 dispatch/combine 与 PD 分离 KV 传输的载体；对网络无损有要求（PFC/ECN），有 incast 拥塞问题（DeepEP 分流、topology-aware 路由缓解）。

追问：为什么 TP 不跨机——AllReduce 通信量 ∝ 激活大小 × 4/TP 度，跨机带宽差 NVLink 一个量级，通信占比不可接受；EP 的 all-toall 消息块大且可重叠，跨机 RDMA 可行。

## Q18. 不同 GPU 生态的主要差异（云-实习-二面-1 Q6）

四个维度对比（以 CUDA 为基准）：

1. **编程模型**：AMD ROCm/HIP（hipify 源码级转译 CUDA，warp 64 与 CUDA 32 不同）；昇腾 CANN（Ascend C/算子开发，MindSpore/PyTorch 适配层 torch_npu，AI Core 矩阵单元 Cube 与向量/标量单元分离的达芬奇架构）；摩尔线程 MUSA、海光 DCU（类 ROCm）、寒武纪（bang C）。
2. **软件栈成熟度**：CUDA 的护城河在 cuBLAS/cuDNN/CUTLASS/Triton/Nsight 全家桶与十几年的算子长尾积累；其他生态常见问题：算子缺失（fallback 到 CPU）、精度对不齐、性能差距（Tensor Core 利用率）、调试工具少。
3. **算子与框架适配**：PyTorch 后端抽象（PrivateUse1/天翼 torch_aie 等）让训练框架跑起来不难，难的是**性能与长尾算子**；Triton 向多后端扩展（AMD 已成熟、NPU 在路上）是跨生态的候选中间层。
4. **迁移工程量**：API 兼容层（hipify 一天）→ 算子补齐（周级）→ 性能调优（tile/向量宽度/warp 尺寸/bank 参数全重调，月级）→ 精度回归。国产芯片的收益维度：供应安全与特定场景性价比，评估要看业务 kernel 的覆盖度。

## Q19. AWQ W4A16 量化的具体实现：Linear 改造、数据结构、内存布局、正确性验证（云-实习-二面-1 Q4）★重点

完整可运行实现在 `solutions/python/src/answers/alibaba/awq_w4a16.py`（AWQ 缩放搜索 + INT4 打包 + W4A16Linear），下面按面试的四个子问题展开：

**① 原理与缩放搜索**。AWQ 观察：激活幅度大的 ~1% 通道对量化误差最敏感（保护它们 ≠ 混合精度保留 fp16，那需要特殊 kernel），做法是 per-channel 等价缩放：$W' = W\cdot\mathrm{diag}(s),\ X' = X\cdot\mathrm{diag}(s)^{-1}$，输出不变但 $W'$ 的量化误差集中在"不重要"通道。$s = \text{act\_max}^{\alpha}$，对每层网格搜 α∈(0,1]（20 个点），**准则 = 等价变换前后该层输出的 MSE 最小**（`search_awq_scale`，α=0 即退化为 RTN 直接量化）。

**② 数据结构设计**。

```
qweight: uint8 [out, in/2]     # 两个 int4 打包进一个 uint8（低半字节在前）
scales:  fp16 [out, in/group]  # group=128 个权重共享一组 scale
zero:    fp16 [out, in/group]  # （AWQ 官方为非对称量化，zero≈8 常与 scale 打包存放）
```

打包细节是高频追问：负数按 int4 补码编码（-1→0xF），解包时 `(packed & 0xF)`、`(packed >> 4)` 后对 ≥8 的值减 16 做符号扩展（`pack_int4/unpack_int4`，roundtrip 测试保证）。

**③ Linear 层改造与内存布局**。替换 `nn.Linear` → `W4A16Linear`：权重显存 1/4 + scale 开销 ~3%（实测 memory_ratio 0.258）。布局要点：① qweight 行主序（out 为行、in 为列）与 GEMM 的 B 矩阵对齐；② 真实 kernel（awq_dequantze / Marlin）会按 tile 访问模式**全局重排**（线程交错、K 维交错），使装载后的解包片段直接对齐 mma 操作数；③ 反量化融合在 kernel 装载阶段（寄存器内 LOP3 位操作解包），不物化 fp16 权重——本模块的 `dequantize_weight` 是教学级功能等价。decode 场景 batch≤32 时 Marlin 可达 fp16 cuBLAS 的 3-4×（详见《量化》Q2 Marlin）。

**④ 正确性验证三级**。kernel 级：量化层输出 vs fp16 层输出的相对误差/余弦相似度（工程阈值 cos > 0.99；本模块 `layer_output_error` 实测：无离群激活 <15%（randn 权重的理论值），有离群通道时 AWQ 6.4% < RTN 7.1%）；模型级：PPL 回归（wikitext2 ±0.05 以内）；业务级：下游 benchmark + 端到端延迟/吞吐。逐层失败回退 fp16（混合精度）。

## Q20. 如何对互联拓扑进行建模？（云-实习 Q2）

1. **图模型**：节点 = GPU/NIC/Switch，边 = （带宽，延迟）；同构分域：机内 NVLink 全互联（全带宽）、PCIe 子树、机间 IB/RoCE 交换拓扑（rail-optimized：每卡 NIC 上联独立 rail）。
2. **层次化代价模型**：通信原语代价 $\alpha$-$\beta$ 模型 $t = \alpha + n\beta$，按路径分层的 α（latency）/β（bandwidth）参数化；树形层次模型（tier0 NVLink / tier1 机间）决定 AllReduce 走分层算法（先机内 reduce 再机间 ring）。
3. **自动探测**：NCCL topo XML（`ncclTopoGetCudaType`）、hwloc；训练前生成拓扑图喂给并行策略搜索（Alpa/Megatron 的 auto-parallel 思想）。
4. **验证手段**：nccl-tests（busbw/latency 矩阵）、ibstat/ibping 链路健康、集合通信微基准扫消息尺寸。
5. **实例（阿里）**：HPN 高性能网络（双 ToR、轨道优化、15K 卡单一二层域），把"拓扑感知"下沉到数据中心设计——回答时把建模与业务结合（如 EP 的 all-to-all 在 rail-optimized 下按 NIC 分流避免 incast）。

## Q21. 硬件形态的发展趋势怎么看？（云-实习 Q3）

开放题，给出有立场的判断框架：

1. **算力**：摩尔定律放缓 → 专用化加速：Tensor Core 代际翻倍（FP8→FP4）、域名特定架构（DSA）；scale-up 域变大（NVLink Domain / NVL72 单机 72 GPU，铜互连）。
2. **访存**：HBM 代际带宽增速低于算力 → **memory wall 是主要矛盾**，推动大容量 3D 堆叠、LPDDR 分层（推理成本敏感）、以及计算向存储靠近（PIM 概念）。
3. **互连**：scale-up（机内高带宽域）与 scale-out（RDMA/以太）分层演进；光互连（CPO/OIO）进入机内；NVLink/UALink/超以太三大阵营标准化竞争。
4. **推理形态分化**：PD 分离 → prefill 算力机型 vs decode 带宽/显存机型异构；端侧 NPU（手机/PC）跑小模型；大集群向"内存池化"（KV 池、参数池）演进。
5. **系统层**：MoE 稀疏激活天然适合"参数多算力少"的硬件趋势；FP4/FP8 让精度调度成为系统问题（哪层哪种精度）。答题落到自己方向（做推理就说 PD/带宽，做训练就说 scale-up 域与并行策略耦合）。
