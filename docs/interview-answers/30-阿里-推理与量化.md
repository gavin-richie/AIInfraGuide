## Q1. 当前 LLM 推理的主要瓶颈在哪里？（云实 Q1）

分阶段看（详见 [05 推理引擎与优化](./05-推理引擎与优化.md) Q1）：

- **Decode：访存带宽是第一瓶颈**。每生成一个 token 都要读完整权重 + 当前 batch 的全部 KV Cache，计算只有一次 GEMV → 算术强度极低（≈1 FLOP/3 Byte），带宽决定吞吐。小 batch 时权重读取占主导（batch 越大权重被摊薄，KV 读取占比上升）。
- **Prefill：计算瓶颈**（长序列一次并行计算，GEMM 打满 Tensor Core），但长上下文下 attention 是 $O(L^2)$ 二次项，激活显存也容易先爆——所以有 Chunked Prefill。
- **系统层瓶颈**：调度（batch 组合、抢占）、KV 管理碎片化（PagedAttention 解决）、CPU-GPU 同步与 kernel launch 开销（CUDA Graph 解决）、多卡/多机的通信与负载不均。
- **长尾**：多轮会话 KV 累积、prefix 复用率、首 token 延迟（TTFT）与每 token 延迟（TPOT）的 SLO 冲突 → PD 分离。

答题时先给"decode memory bound / prefill compute bound"的主结论，再按层展开，是最稳的结构。

## Q2. vLLM 有哪些核心优化技术？（云二 Q3、云二2 Q1）

与 [05 推理引擎与优化](./05-推理引擎与优化.md) Q2/Q3 同族，按"调度—显存—kernel—并行"四层答：

1. **Continuous Batching（iteration-level scheduling）**：以 step 而非 request 为调度单位，序列结束/新请求即时进出 batch，GPU 不空转——吞吐相对 static batching 提升 2-4×；
2. **PagedAttention**：KV Cache 分页管理（block 16/256 token），按需分配、消除内部碎片与预预留浪费，显存利用率 >90%（详见 [04](./04-attention与kvcache.md) Q6）；
3. **Prefix Caching**：相同前缀（system prompt、多轮对话历史）的 KV block 复用，命中即免重算 prefill；
4. **Chunked Prefill**：长 prompt 切块与 decode 混排，平抑 TTFT 抖动、避免 prefill 长kernel饿死 decode（[05](./05-推理引擎与优化.md) Q3）；
5. **Kernel 层**：FlashAttention、W4A16/W8A8/FP8 量化 kernel（GPTQ/AWQ/Marlin）、fused RMSNorm+RoPE、CUDA Graph 消除 launch 开销；
6. **并行与部署**：TP/PP/EP、 speculative decoding、PD 分离对接、多模态输入。

## Q3. vLLM 近期值得关注的新特性？（控 Q5）

开放题，答方向 + 代表性特性即可（以 v0.8+/V1 为分界）：

- **V1 引擎重写**：默认 1-step 调度器（去掉双进程 overlap 的复杂度）、**prefix-aware 调度**（调度时直接选命中 prefix cache 的请求优先入队）、**async scheduling**（CPU 调度与 GPU 计算彻底重叠，CPU 不再出现在关键路径）；
- **Piecewise CUDA Graph**：只对 decode 段 capture，兼顾 prefill 动态 shape；
- **投机解码全家桶**：EAGLE/EAGLE-3、**DeepSeek MTP**、n-gram/lookahead draft、medusa；
- **量化支持扩展**：FP8（含 fp8 checkpoint 动态/静态）、GPTQ/AWQ/INT4/FP4（Blackwell）、compressed-tensors；
- **结构化输出**：xgrammar 后端（grammar 编译成 mask，速度接近自由生成）；
- ** disaggregation（PD 分离）生产化**：KV cache 跨节点传输（NIXL/NCCL）；sleep mode（显存换出/唤醒，多租户降本）；
- **多模态统一接入**：图像/视频/音频 encoder + LLM 统一接口； LoRA 热切换、structured logging/observability。

面试加分点：讲清 V1 调度器为什么"prefix-aware + 一步调度"能同时提吞吐和降 TTFT。

## Q4. KV-Cache 在训练阶段还是推理阶段使用？训练为什么不缓存？（校 Q2）

**推理阶段**（准确说：自回归生成过程）使用。逐 token 生成时，历史 token 的 K/V 不会变，缓存后每步只算新 token 的 QKV，把 $O(L^2)$ 的重复计算降为 $O(L)$。

**训练不用**的原因：teacher forcing 下整段序列已知，注意力对全部 query 并行计算（ causal mask 下一次矩阵乘即可），每层的 K/V 本来就只算一次，没有"重复计算"可省；且训练需要为反向传播保留完整计算图/激活，缓存中间 K/V 并不能省显存（激活 checkpointing 反而会重算它们）。补充：训练流程里的** rollout 生成阶段**（RL 采样、DPO 采样）本质是推理，那一段会用 KV Cache。

## Q5. KV Cache 显存占用如何计算？（控 Q4）

$$\text{KV bytes} = 2 \times L_{layer} \times H_{kv} \times d_{head} \times b_{dtype} \times B \times S$$

（2 = K 与 V；$H_{kv}$ 是 KV 头数——GQA 下远小于 query 头数）。例：Llama-2-7B（32 层、32 头、head_dim 128、FP16）单请求 4096 token：$2×32×32×128×2×4096 ≈ 2.1\,GB$。若换 GQA $H_{kv}=8$ 则降到 0.53GB——这也是 GQA/MLA 的动机（见 Q7/Q8）。再加 batch 维即总量。追问一般是"怎么省"：KV 量化（FP8/INT4）、GQA/MQA/MLA、Paged 分配消除碎片、prefix 共享、滑窗/淘汰、offload。完整优化谱系见 [04](./04-attention与kvcache.md) Q7。

## Q6. KV Cache 有哪些常见优化策略？（一1 Q3）

按"少存、存密、存好、复用"四类（详见 [04](./04-attention与kvcache.md) Q7）：

1. **结构上少存**：GQA/MQA 减 KV 头数；MLA 低秩压缩（KV 存 latent 向量）；Cross-layer/YOCO 类跨层共享；
2. **存密**：KV 量化 FP8（近无损）/INT4（需非对称+离群保护，KIVI）； 
3. **存好**：PagedAttention 分页、prefix cache、量化+分页组合；
4. **复用/淘汰**：滑窗（Mistral）、H2O/SnapKV 等 token 淘汰（保留注意力分数高的 KV）、KV offload 到 CPU/NVMe 分层。

阿里追问多轮对话场景：命中 prefix cache 时多轮历史免重算，回答要能落到"块级命中率的统计与调度（LRU/GPU 优先驻留）"。

## Q7. Group Query Attention 的设计动机与作用？（一1 Q1）

动机：decode 阶段每步都要把 KV Cache 从 HBM 读一遍，**访存量 ∝ KV 头数**。MHA KV 头数=query 头数，KV 太大；MQA 全部 query 共享 1 个 KV 头，显存/带宽最小但质量掉。**GQA 折中**：把 query 头分成 $G$ 组，每组共享 1 个 KV 头——KV 显存与读取量降为 $G/H$，精度接近 MHA（LLaMA-2/3、Qwen 系全用它）。作用两句话：① KV Cache 缩小 → 同显存下 batch/序列更长；② decode 访存减少 → 每 token 延迟降低。MQA 是 $G=1$ 特例，数值上 GQA 可由 MHA 权重"分组平均 KV 投影"初始化以保精度。

## Q8. MHA、GQA 与 MLA 的核心区别及适用场景？（实1 Q1）

| 方案 | KV Cache 大小（相对 MHA） | 质量 | 特点 |
|---|---|---|---|
| MHA | 1× | 基线 | KV 头数 = query 头数 |
| GQA/MQA | $H_{kv}/H$（1/8、1/4 常见；MQA=1/H） | 接近基线 | 存储换精度代价小，工程最简单，主流部署默认 |
| MLA（DeepSeek） | ≈ 1/10 且与序列无关的低秩 latent | 等效或更好 | K/V 联合低秩压缩 + RoPE 解耦（nope/rope 两段），**decode 时把上投影吸收进 WQ/WO**，访存最优但实现复杂 |

MLA 细节（阿里常追问）：$c_{KV} = W_{DKV} h$（如 latent 512 维），读取时 $K = W_{UK}c_{KV}$；因 decode 时 $QK^T = Q(W_{UK}c)^T = (QW_{UK})c^T$，把 $W_{UK}$ 吸收进 Q 侧权重 → 只需读 $c_{KV}$，等效"MQA 的访存 + MHA 的质量"。数值对拍实现见 [04](./04-attention与kvcache.md) Q3/Q5 与 `solutions/python/src/answers/attention/mla.py`。

## Q10. Flash Attention 的核心思想？如何优化注意力计算？（校 Q3）

核心是**用 tiling + online softmax 把注意力做成 IO-aware 的单 kernel**（详见 [04](./04-attention与kvcache.md) Q1/Q2）：

1. 分块装载 Q/K/V tile 到 shared memory，计算 tile 级 $S=QK^T$；
2. online softmax：维护运行中的 max $m$ 与归一化和 $l$，新 tile 到来时重标定旧累加值 $O \leftarrow O\cdot e^{m_{old}-m_{new}}$，增量更新——不需要看到整行也能数值稳定地归一化；
3. $L×L$ 的注意力矩阵**从不物化到 HBM**，显存从 $O(L^2)$ 降到 $O(L)$，HBM 访问从 $O(L^2+Ld)$ 降到 $O(L^2d^2/M)$（M 为 smem 大小）；
4. 长序列下既有显存收益又有速度收益（attention 从 memory bound 变为 compute bound 边缘）。

v2 改 Q 为外层循环（并行度随序列增长）、寄存器驻留；v3 走 Hopper warp specialization + TMA + 低精度 GEMM。手写实现（与 SDPA 对拍）：`solutions/python/src/answers/attention/flash_attention.py`。

## Q11. 除 Flash Attention 和 KV-Cache 外，还有哪些注意力优化方法？（校 Q4）

按"改存储/改计算/改结构"归类：

- **改 KV 存储**：GQA/MQA/MLA（Q7/Q8）、PagedAttention、KV 量化、滑窗/StreamingLLM、token 淘汰（H2O/SnapKV）、prefix cache；
- **并行拆分**：Flash Decoding（序列维切 K/V 并行、最后 combine）——长序列 decode 专用；
- **稀疏/拓扑限制**：sliding window、dilated attention、DSA/NSA/MoBA 等可学习稀疏（对比见 [07 分布式训练](./07-分布式训练.md) Q9）；
- **线性化/近似**：linear attention（kernel 化 $O(L)$）、Performer、Mamba/ RWKV 状态空间模型；
- **解码策略**：speculative decoding（draft+verify）、MTP（见 Q18）、medusa 多头并行预测。

## Q12. 量化的基本原理与具体实施流程？（实一二·一面 Q3）

**原理**（详见 [06 量化](./06-量化.md) Q1）：把 FP 权重/激活映射到低精度整数网格，$q = \mathrm{clamp}(\mathrm{round}(x/s)+z)$，反量化 $x \approx s(q-z)$；对称量化 $z=0,\ s=\max|x|/127$，非对称 $s=(x_{max}-x_{min})/255,\ z=\mathrm{round}(-x_{min}/s)$。粒度 per-tensor/per-channel/per-group（group=128 是 W4 标配，离群值越多粒度越细）。

**实施流程**（PTQ 主线）：

1. 备好**校准集**（512~2048 条与部署分布一致的数据，只跑 forward 不需要标签）；
2. 逐层统计激活/权重分布（min/max、分位数、KL）；
3. 选方案：W4A16 用 AWQ/GPTQ（[06](./06-量化.md) Q3 对比），W8A8 用 SmoothQuant，或 QAT 保精度；
4. 执行量化并导出：packed 权重 + scale/zero + 布局重排（见 Q14）；
5. **验证**：逐层 cosine/MSE → 全模型 ppl → 下游 benchmark（MMLU/GSM8K）→ 敏感 case（长文本/重复/代码缩进）；超阈值的层回退高精度（混合精度）；
6. 接推理引擎 kernel（AWQ→Marlin/GPTQ kernel、W8A8→cutlass INT8）上线压测。

## Q13. FP32、FP16、INT8 的底层存储格式与差异？（实一二·一面 Q2）

| 格式 | 位构成（符号-指数-尾数） | 范围/表示 | 说明 |
|---|---|---|---|
| FP32 | 1-8-23 | ±3.4e38，有效数字 ~7 位 | 训练默认、精度基准 |
| FP16 | 1-5-10 | 最大 65504，最小 normal 6.1e-5 | **指数位少→动态范围窄**：上溢（loss 大）下溢（梯度小）都常见，需 loss scaling；尾数 10 位精度够 |
| BF16 | 1-8-7 | 范围同 FP32，精度 ~3 位 | 指数位与 FP32 对齐→免 loss scaling，LLM 训练主流 |
| INT8 | 8bit 补码整数 | -128~127 | 无动态范围概念，必须配 scale/zero（量化）；算力 2× FP16（Tensor Core） |

要点：浮点数在指数位均匀、尾数位不均匀（对数分布），定点整数均匀——这是量化离群值问题的根源（[06](./06-量化.md) Q6）；FP16→BF16 的取舍 = 精度换范围。追问常带 TF32（1-8-10，mantissa 截断的 FP32）与 FP8 E4M3/E5M2（[06](./06-量化.md) Q5）。

## Q14. 【重点】AWQ 路线 W4A16 量化的具体实现：Linear 改造、数据结构、内存布局、正确性验证（云二1 Q4）

这是阿里云二面高频深水题，按四段答：

**① 原理与离线量化流程**。AWQ 观察：约 0.1%-1% 的**激活离群通道**对输出贡献大，对应权重不该被"均等"量化。做法是等价缩放：$W' = W\cdot\mathrm{diag}(s),\ X' = X/s$（FP 下输出不变），s 按 $s=x_{max}^{\alpha}$ 在 $\alpha\in[0,1)$ 网格逐层搜索、取层输出 MSE 最小者。不修改权重本身、不需要反向传播。

**② Linear 层改造**。`nn.Linear` 替换为 `W4A16Linear`：

- **数据结构**：`qweight: int32[out, in/8]`（8 个 int4 打包进一个 int32；也有 int8 打包 2 个的实现）、`scales: fp16[out, in/group_size]`、`qzeros` 同形（group=128 时每 128 个输入通道共享一组 scale/zero，非对称量化 $q\in[0,15]$）、bias 保留 fp16。显存 ≈ 权重的 1/4 + 千分之几的 scale 开销；
- **forward**：`y = (x/s_act) · dequant(W_q)`——把搜索到的 per-channel 缩放 $s$ 折叠进权重（量化的是 $W\cdot s$），运行时输入除以 $s$；更进一步可把 $1/s$ 折叠进**上游 RMSNorm 的 gamma**，forward 零额外算子；
- **kernel 语义**：解包（位操作 unpack 4bit→FP16）内嵌在 GEMM 的权重装载路径里，寄存器/smem 内完成反量化 + mma，**解包结果不写回 HBM**（Marlin 是标杆：还做全局布局重排 + LOP3 三指令解包，小 batch decode 接近 4× FP16 cuBLAS，见 [06](./06-量化.md) Q2）。

**③ 内存布局**。打包方向必须与 kernel 解包约定一致（本实现：偶数元素在低半字节）；生产 kernel 里还按 tile 访问模式**预重排**（线程交错、K 维交错），让一次 128bit load 恰好取到 mma 片段需要的连续 int4；group scale/zero 与对应权重 tile 同址放置（L2 友好），对齐 16B。

**④ 正确性验证**。三层：单层对拍（量化前后输出 cosine sim > 0.99 / 相对误差阈值，用真实校准数据）；全模型 ppl 与下游任务回归（W4 典型掉点 <1% ppl）；端到端服务灰度对比。工程上还要测边界（极端激活、长序列）与 kernel 级单测（随机 shape + 边界 shape 对拍，compute-sanitizer 查越界）。

**配套可运行实现**（AWQ 全流程：缩放搜索 → per-group 非对称 INT4 → 位打包 → W4A16 Linear，模拟"装载即解包"语义）：

- 代码位置：`solutions/python/src/answers/alibaba/awq_w4a16.py`（`awq_search_scale` / `quantize_int4_asymmetric` / `pack_int4` / `AWQLinear` / `awq_pipeline_report`）
- 验证命令：`cd solutions/python && python -m pytest tests/test_alibaba.py -q -k awq`
- 实测（3090，随机 Linear 64×256 + 20% 离群通道）：AWQ 输出 MSE 相对 naive W4 **降到 0.3× 以下**、余弦相似度 >0.99，权重存储压缩 **3.8×**（fp16 32KB → 8.5KB）。

## Q15. 【项目】部署量化流程与 GridSample 算子优化、算子的底层定义（实一二·一面 Q7）

**GridSample 底层定义**：给定输入 $X$（NCHW）与采样网格 $G$（$x_{src} = a\cdot x_{dst} + b$ 的逆仿射/透视映射坐标），对每个输出位置做可微采样：坐标归一化（align_corners=True/False 改变映射公式：`False` 时 $x \mapsto (2x+1)/W-1$）、按 padding_mode 处界（zeros/border/reflection）、双线性插值 = 相邻 4 像素的面积加权。它不是线性算子（含索引与 max/clamp），但插值部分对输入是局部线性组合。

**量化部署要点**：① 坐标必须保 FP16/FP32（整数化坐标会引入半像素抖动），可量化的是输入特征与权重类；② 输出分布受插值平滑，per-channel INT8 通常友好，校准时覆盖大位移/出界 case；③ ONNX/ATen 下沉时注意 align_corners 与 PyTorch 版本语义一致性。

**算子优化点**（GPU）：输出像素并行（每线程一个 dst 像素 × 通道循环或向量化）；访存上把 4 邻居载入寄存器、channel 维连续读（NCHW 时改 NHWC/CHW 交错）；越界判断向量化（clamp 后统一寻址）；邻近插值降采样走 texture 硬件单元（hardware bilinear filter 一条指令完成）。

## Q16. 什么是访存密集型算子？举例（实一二·一面 Q1）

算术强度 AI = FLOP/Byte 低于机器平衡点（3090 FP32 ≈38）的算子，性能由 HBM 带宽决定（[03 GEMM 与算子优化](./03-gemm与算子优化.md) Q1 的 Roofline）。例：elementwise（add/激活/dropout）、LayerNorm/RMSNorm（行统计+缩放）、Softmax（行内归约）、Embedding gather、reshape/transpose/类型转换（纯搬运）、小 batch decode 的 GEMV（每读 2 字节权重只做 2 次乘加）。优化三板斧：**融合**（消灭中间张量的 HBM 往返）、**向量化装载**（128bit）、**提高并行度摊满带宽**；本质不是增加计算而是减少访存。手写实现与实测带宽见 `solutions/python/src/answers/triton_kernels/`（fused softmax 825 GB/s）与 `solutions/cuda/src/norm.cu`。

## Q17. Tensor Parallelism 中 AllReduce 需要执行多少次？如何推导？（控 Q3）

以 Megatron 单层 Transformer、TP=N 为例（推导见 [07 分布式训练](./07-分布式训练.md) Q1/Q4）：

- **Attention 块**：QKV 投影按列切（每个 rank 算 $H/N$ 个头，头内自洽无需通信），输出投影 $W_O$ 按行切 → 每 rank 持有部分和，前向 **1 次 AllReduce**（f = 1/g 聚合）；
- **MLP 块**：$W_1$ 列切（SiLU 后仍是各 rank 局部），$W_2$ 行切 → 前向 **1 次 AllReduce**；
- 合计**前向 2 次/层，反向对应梯度再各 1 次 → 4 次/层**（若反向用 Reduce-Scatter+AllGather 组合则通信量不变、次数等价）；embedding（列切）与序首/序尾各再加 1 次。
- 数字例：Llama-7B 32 层 → 前向 64 次 AllReduce。Ring AllReduce 单次通信量 $2(N-1)/N \cdot V$，TP 通信发生在每层关键路径上 → 这就是 TP 必须困在 NVLink 域内（8 卡）的原因。

## Q18. DeepSeek-MTP 用于训练阶段还是推理阶段？工作流程？（云二 Q4、云二2 Q3）

**两者都用，且训练为推理服务**。MTP（Multi-Token Prediction）模块串接在主模型后：embedding 共享 + 线性投影 concat（主模型隐状态与上一深度 token 的 embedding）+ 若干 Transformer 层 + 共享 output head，预测第 $i+2, i+3,\dots$ 个 token。

- **训练**：把语料按深度 $D$ 平移切出多组 (input, target)，主损失 + 各深度 MTP 损失（交叉熵）加权求和；一次前向同时监督多个未来 token，表征学到更长程的结构（DeepSeek-V3 报告 MTP 头还能改进主模型分布）。
- **推理（speculative decoding）**：主模型产出 1 个 token 后，MTP 模块顺序草拟 $k$ 个候选；主模型对"1+k"个 token 做一次并行 forward 验证；从左到右接受概率匹配/贪心一致的最长前缀，首个不一致处之后丢弃，重打分继续。接受长度平均 >2 即有净收益（验证一次的并行成本 ≈ 1 个 token 的 decode 步）。DeepSeek-V3 用 1 个 MTP 模块实测吞吐 ~1.8×。
- 关键区分：MTP ≠ 独立小模型 draft（如 EAGLE 是独立训练的 draft head）；MTP 与主模型联合训练、embedding/head 共享，接受率高。
