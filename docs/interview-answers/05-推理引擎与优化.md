## Q1. Prefill 与 Decode 的差异及各自的主流优化（综合-3 Q3）

| 维度 | Prefill | Decode |
|---|---|---|
| 计算 | GEMM 大 M，**compute bound**，一次算整个 prompt | 每 step 1 token，GEMV/瘦 GEMM，**memory bound**（权重+KV 读取主导） |
| 延迟来源 | FLOPs ∝ S² | 带 宽（权重 + KV ∝ S） |
| 优化 | FA、TP 并行、chunked prefill、投机解码冷启动 | KV Cache（GQA/MLA/量化）、PagedAttention、continuous batching、CUDA Graph、 speculative decoding、MTP |

矛盾点：两者 SLO 不同（prefill 要 TTFT 低、decode 要 TPOT 低），混跑互相干扰 → chunked prefill 切小块 + 调度器交错、或直接 **PD 分离**。

## Q2. vLLM 核心设计理念（字节 AI-Infra-1/2、综合-7 Q1）

三大支柱：

1. **PagedAttention**：KV 分页管理（见《Attention 与 KV Cache》Q6），显存利用率 >90%，支持 copy-on-write 与 prefix 共享。
2. **Continuous Batching（iteration-level scheduling，源自 Orca）**：调度粒度是**每步迭代**而非整个 sequence——某请求完成立刻让新请求插队，没有 padding 浪费、没有等最慢请求的气泡；配合 slot mapping 把逻辑 token 映射到物理 KV 块。
3. **吞吐导向执行**：chunked prefill（把长 prompt 切成与 decode 交错的小块，平衡 TTFT/TPOT）、prefix caching、CUDA Graph 按 batch 分档消除 decode launch 开销。

调度器要点（京东-校招追问）：waiting/running 双队列；准入条件 = 剩余 KV 块；显存不够触发抢占（swap 到 CPU 或 recompute）；新请求优先级与 FCFS。

## Q3. Chunked Prefill 动机与语义（腾讯-实习-一面-1、京东）

把长 prompt 的 prefill 切成固定 token 预算的块，逐块与 decode 步交错执行：

- **动机**：长 prompt 一次 prefill 数百 ms，同卡 decode 请求的 TPOT 被拉高（尾延迟）；分块后每步调度点变密，decode 不被饿死，GPU 始终有活干。
- **语义细节**：块内 causal mask 只对本块可见（前面的块已在 KV 里，通过读取历史 KV 实现"块间因果"）；首 token 在最后一块结束时输出；attn 对前缀的读取 = KV cache 读，天然支持。
- **代价**：小块 GEMM 效率略降、调度开销增加；预算(chunk size)是 TTFT-TPOT 的权衡旋钮（vLLM/SGLang 可配）。

## Q4. Mooncake：以 KV-Cache 为中心的 PD 分离（综合-1 基础 4）

架构（Kimi/月之暗面）：

- **分离集群**：Prefill/Decode 各自独立扩缩容（prefill 吃算力、decode 吃带宽，硬件异构配置）。
- **KVCache 池**：全局分布式缓存（CPU DRAM + SSD 分层），以 **前缀哈希（prefix-based LRU）** 为索引，请求级复用多轮对话/公共前缀的 KV。
- **传输层**：zero-copy RDMA + topology-aware 传输，prefill 完成后把 KV 推给 decode 节点（to-token 级流式）。
- **全局调度器**：按缓存命中与负载选副本，缓存感知路由提高命中率。

收益：高吞吐场景下解码集群的 KV 缺失率低、TTFT/TPOT 双降。要点回答"为何 KV 传输开销仍值得"：见 Q5。

## Q5. 多机 PD 分离引入 KV 传输开销，为何仍必要（综合-3 Q6）

1. **SLO 结构不同**：TTFT 与 TPOT 目标冲突，同机混跑互拖；分离后各自按 SLO 扩容。
2. **硬件效率**：prefill 是 compute bound（H100 高 FLOPs 利用率）、decode 是 memory bound（带宽/显存越大越好）——分离可异构部署（decode 用大显存卡、prefill 用高算力卡），机器利用率都更高。
3. **KV 传输量可控**：KV 只在 prefill 结束传一次（O(S)），远小于把权重/中间激活来回传；RDMA/NVLink 直连 + 拓扑感知下传输时间可被流水线隐藏（与下一块 prefill 重叠）。
4. **缓存复用摊薄**：多轮对话/共享前缀场景下，第二次起 prefill 直接命中 KV 池，传输近乎归零。
5. **弹性与容错**：decode 崩溃不影响 prefill 队列；独立滚动升级。

## Q6. 跨 SM 的 PD 分离与 AF 分离如何看待（综合-3 Q8）

更细粒度的"分离"（SM 级共址）：

- **SM 级 PD**：同一 GPU 上不同 SM 分组分别跑 prefill 与 decode 流（通过 MPS/MIG 或 warp 级隔离），消除跨机网络但共享带宽互相干扰——适合中小规模、避免 kv 传输但调度复杂。
- **AF 分离（Attention/FFN 分离）**：把层内 attention 与 FFN 放到不同设备/SM 组，KV 访存与权重读取解耦——理论上带宽分桶利用，但引入中间激活传输与流水线气泡，工程收益依赖拓扑（NVLink 域内可行）。
- 评价框架：把"分离"视为**资源解耦的粒度选择**——机间→卡间→SM 间，粒度越细传输延迟越低但隔离性/调度复杂度越差；选择依据是干扰成本 vs 传输成本。

## Q7. DiT 推理框架与 LLM 推理框架的异同（综合-1 基础 5）

**相同**：都吃 transformer backbone（attention+FFN）、都需要 KV cache（视频/图像 token 的时空注意力）、量化/kernel 优化（FA、TensorRT）通用、continuous batching 思想可迁移。

**不同**：

| | LLM（AR） | DiT（Diffusion） |
|---|---|---|
| 迭代结构 | 自回归 1 token/步 | 全序列迭代去噪 T 步（如 20-50 步） |
| cache | KV 随步追加 | KV 每步重建（相同 token 集重算 attention）；CFG 使 batch×2 |
| 调度 | iteration 级插入 | 一个样本 T 步整体占用；步间可打断（不同样本不同 t） |
| 调度单位收益 | decode 换步快 | 步间 timestep-condition 权重切换（ Streaming/patch 并行） |
| 优化热点 | KV 管理、投机解码 | 多步冗余消除（cache 跨步复用、CFG distill）、并行采样（step 并行/pixel 并行） |

## Q8. Diffusion 训练/推理步骤；timesteps=1000 而 inference 40 步（综合-1 基础 7、综合-2 PyTorch 编程 3）

- **训练**：随机采 $t\sim U[0,T]$、加噪 $x_t=\sqrt{\bar\alpha_t}x_0+\sqrt{1-\bar\alpha_t}\epsilon$，网络回归噪声 ε（或 v-prediction/速度场）；t 离散化为 1000 档仅为训练采样覆盖密度，并非必需。
- **推理**：从噪声出发，按 ODE/SDE 求解器迭代去噪到 t=0；步数 20-50。
- **为什么训练 1000 推理 40 就够**：训练学的是**任意 t 下的条件去噪算子**（连续时间上的函数拟合），采样步数只是数值积分的步长——40 步的 ODE 积分误差已可接受；训练档位密是为了算子在整个 t 轴上拟合得准，与推理步数解耦。进一步的步数压缩：蒸馏（LCM/Consistency）、更高阶求解器（DPM-Solver++）、蒸馏到 1-4 步。
- Flow Matching 变体（综合-2 基础 4/编程 3）：训练回归条件速度场 $u=x_1-x_0$（线性路径），采样欧拉积分 $x_{t+dt}=x_t+v_\theta dt$。可运行端到端 demo：`solutions/python/src/answers/torch_impl/flow_matching.py`（含训练 loss 与 40 步采样，测试验证收敛到目标双簇分布）。

## Q9. dLLM 与 AR 模型的本质区别（综合-1 基础 8）

- **AR（自回归）**：从左到右逐 token 生成，$p(x)=\prod p(x_i|x_{<i})$，一次前向一个 token；推理受 memory bound 制约，天生流式。
- **dLLM（离散扩散 LLM，如 LLaDA/Mercury）**：以"掩码-恢复"方式并行生成——初始全 mask，多轮迭代并行去掩码（每轮可改多个位置），$p(x)$ 由掩码率调度下的并行预测器定义。
- 本质区别：生成方向的图结构不同——AR 是严格因果链（链式分解），dLLM 是**迭代式并行细化**（任意改写顺序、天然双向上下文）；训练目标从 next-token 交叉熵换成 masked 预测的 ELBO；推理计算量与轮数（而非序列长度）相关，单轮吞吐高但多轮迭代、KV 无法增量复用。
- 工程含义：dLLM 更适合并行采样/长文本一次性生成，AR 仍主导流式对话。

## Q10. torchrun 启动参数与批量杀进程（综合-1 基础 10）

常用参数：`--nproc_per_node`（每机进程数=gpu 数）、`--nnodes`/`--node_rank`（多机）、`--master_addr/--master_port`（rendezvous 地址）、`--rdzv_backend=c10d`（弹性）、`--rdzv_endpoint`、`--max_restarts`（elastic 重启）、`-m`（模块方式）、`--local-ranks-filter`、env 注入 `LOCAL_RANK/RANK/WORLD_SIZE/MASTER_ADDR`。

批量杀进程（Linux）：

```bash
pkill -f torchrun          # 匹配命令行
ps -ef | grep torchrun | grep -v grep | awk '{print $2}' | xargs kill -9   # 兜底
# 最好按进程组杀: torchrun 的子进程与其同 pgid
kill -9 -<PGID>            # 注意 kill 负号 = 进程组
```

追问点：只 kill 主进程会留下孤儿 GPU 进程（显存不释放），要用 `--spawn-method=forkserver` 思路或按 pgid 杀；`nvidia-smi --query-compute-apps=pid --gpu-bus-id` 查残留。

## Q11. 训练耗时估算：由 token 量推总时间（综合-3 Q2）

核心公式：

$$T = \frac{N_{tokens} \times 6 N_{params}}{FLOPs_{peak} \times MFU \times N_{gpu}} + T_{comm} + T_{io}$$

- 每 token 前向 2N、反向 4N → 6N FLOPs/token（N 为参数量）；
- 例：7B 模型、1T tokens、MFU 40%、H800（989 TFLOPS BF16）、单机 8 卡 → T = 1e12×6×7e9 / (9.89e14×0.4×8) ≈ 1.33e6 s ≈ **15.3 天**。
- 修正项：激活重算（+33%）、梯度累加不省计算、checkpoint 保存开销；通信与 IO 理想情况被 MFU 吸收。

## Q12. 大模型推理主流加速方案综述（综合-7 Q1/8、百度-校招-1）

按层次：①图/编译（融合、TensorRT/torch.compile）；②kernel（FA、cutlass GEMM、量化 kernel W4A16/W8A8/FP8）；③执行（CUDA Graph、continuous batching、chunked prefill）；④算法（投机解码/MDM/MTP、KV 压缩、prefix cache、蒸馏小模型）；⑤系统（PD 分离、KV offload、多级缓存）。面试最好各举一例并给出量级（如 W4A16 显存减 4×、投机解码 2-3×、continuous batching 吞吐 2-20×）。

## Q13. QwenImage 中的 time shift 如何计算（综合-2 基础 5）

Diffusion 训练时的 **timestep shift**：把均匀采样的 t 重映射到目标噪声调度：

$$t' = \frac{s \cdot t}{1 + (s-1)\cdot t}\quad(s=1 \text{ 退化为恒等})$$

- **动机**：高分辨率图像加噪的"信噪比走线"与低分辨率不同——同样的 t 下有效噪声更强，需要 shift 保证训练-推理噪声调度对齐（SD3 论文引入，Flow Matching 家族通用）。
- **计算流程**：训练时 $t\sim U[0,1]$ → 按 shift 映射 t′ → 用 t′ 的 α/σ 加噪；推理时对离散调度表同样应用 shift。QwenImage/Flux 类高分辨率模型常用 `shift≈3`（分辨率越高越大）。
- 实现参考：一行 `t_shift = shift * t / (1 + (shift - 1) * t)`；Flow Matching 的完整训练+采样在 `solutions/python/src/answers/torch_impl/flow_matching.py` 可运行验证。
