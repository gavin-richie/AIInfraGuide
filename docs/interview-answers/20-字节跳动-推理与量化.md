## Q1. KV Cache 的工作原理及常见优化策略（AI-Infra-1 推理优化 1、AI-Infra-2 推理优化 2）

同《04 Attention 与 KV Cache》Q7（含显存估算公式与 GQA/MQA/MLA/量化/淘汰/offload 全景），此处只补字节常追问的三个点：

1. **为什么能 cache**：decoder-only 因果 mask 使得第 $t$ 步的 attention 只读 $K_{\le t}, V_{\le t}$，历史 token 的 K/V 与未来无关 → 增量计算后保留复用，把每步 $O(t^2)$ 的重算降为 $O(t)$。
2. **一句话公式**：$\text{bytes} = 2 \cdot L \cdot n_{kv} \cdot d_h \cdot B \cdot S \cdot \text{dtype}$（2 = K 与 V），能现场代入 Qwen-7B 算出 B=1/S=2048/fp16 ≈ 1.07GB（见 04 篇）。
3. **字节追问"prefill 阶段要不要 cache"**：要——prefill 算出的整个 prompt KV 就是 decode 阶段的初始 cache，chunked prefill 下逐块追加。

## Q2. PagedAttention 的核心思想，如何提升显存利用率（AI-Infra-1 推理优化 2、AI-Infra-2 推理优化 1、校招-1 推理优化 4、AML 一面 3）

同《04 Attention 与 KV Cache》Q6。字节高频追问角度：

- **两类碎片的消解**：预留 max_len 造成的内部碎片（实际生成远短于预留）+ 反复分配释放不同长度造成的 external fragmentation，分页后都消失，利用率 20-40% → >90%；
- **block table 与 kernel 寻址**：`k_pool[block_table[req][i//block_size], i%block_size]`，逻辑连续物理离散，配套实现见 `solutions/python/src/answers/attention/paged_attention.py`（含 BlockAllocator，测试验证交错写入后 decode 与稠密 attention 一致）；
- **copy-on-write**：beam search 多候选共享 prompt 前缀时块只读共享，某条路径写新 token 才复制该块——OS fork 的 COW 思想；
- **追问"块大小怎么选"**：vLLM 默认 16。太大 → 内碎片回升（最后一个块平均浪费一半）、粒度粗；太小 → block table 与查表开销上升。16 是"token 数 × dtype × 2KV"对齐到 KB 级的折中。

## Q3. FlashAttention 的实现原理与优势（AI-Infra-1 推理优化 3、AI-Infra-2 推理优化 3）

同《04 Attention 与 KV Cache》Q1（tiling + online softmax + fusion 三件套，v1→v2→v3 演进表）。字节常追问的"核心技术点"口径：**不是近似算法，是精确 attention**，省的是 HBM 访存（$O(N^2)$ 矩阵读写 → 按块装载的 $O(N^2 d/B)$ 读 + $O(N)$ 写）与显存（不物化 $N\times N$ 矩阵）。手写实现：`solutions/python/src/answers/attention/flash_attention.py`（v1/v2 与 SDPA 对拍 <1e-4）。

## Q4. vLLM 框架的核心设计理念（AI-Infra-1 推理优化 4）

同《05 推理引擎与优化》Q2。要点串联：**以 KV Cache 显存管理为中心**——PagedAttention（显存利用率）+ continuous batching（吞吐）+ 前缀复用 + HF 模型无损接入；调度器每一步在"新请求 admission / 运行中请求推进一步 / 抢占换出"间做决定，token 级调度把 batch 维持在显存允许的最大值。

## Q6. 系统资源调度与并发处理的要点（AI-Infra-2 高性能计算 4）

1. **调度粒度**：request 级（static batching，队尾阻塞）→ iteration/token 级（continuous batching，每步重组 batch，Orca 首创，见 Q9）；prefill 与 decode 的资源画像完全不同（compute vs memory bound），混跑互相拖累 → chunked prefill / PD 分离。
2. **准入与抢占**：准入看剩余 KV block 数；显存不足时抢占——swap（换出到 CPU）或 recompute（丢弃 KV 重算），vLLM 默认 recompute（PCIe 带宽常比重算贵）。
3. **并发与隔离**：多租户下 MPS/MIG 切卡隔离；单卡多实例间 batch 与 KV 配额；长尾请求用优先级调度防饥饿。
4. **指标**：TTFT（首 token 延迟，prefill 主导）、TPOT/ITL（每 token 延迟，decode 主导）、吞吐（tokens/s）、SLO 达标率——调度策略是这些指标的加权博弈。

## Q7. 量化技术分类与权重/激活/KV 三类量化的收益（校招-1 推理优化 2/3）

分类同《06 量化》Q1-Q4（GPTQ/AWQ/SmoothQuant、粒度、校准）。三类收益口径是字节特色问法：

| 量化对象 | 主要收益 | 附带收益 | 代价/风险 |
|---|---|---|---|
| 权重（W4A16 等） | 显存 ↓（权重占大头），可放大 batch | 装载时间 ↓，冷启动快 | per-group scale 校准；dequant 开销 |
| 激活（W8A8） | 带宽与显存同降，GEMM 真提速 | — | 异常值通道难量化（SmoothQuant） |
| KV Cache | KV 显存 ↓ → batch/上下文 ×N | decode 延迟 ↓（memory bound 直接受益） | attention score 对量化最敏感，需 per-block/per-channel 校准 |

"量化收益怎么算、何时无收益"同《06 量化》Q7。**优势一句话**：以可控精度损失换显存、带宽、能耗的同比例下降，且推理期免训练（除 QAT）。

## Q8. Prefix Cache 的机制与适用场景（校招-1 推理优化 5）

**机制**：多条请求的公共前缀（system prompt / few-shot / 多轮对话历史）算出的 KV block 不必重算——以 token 前缀为键缓存 KV，新请求先做最长前缀匹配，命中部分直接跳过 prefill。工程实现（SGLang）用 **radix tree**：公共前缀共享节点、分叉存储，配合叶子优先的 LRU 淘汰（中间节点被多条请求共享不能删）；粒度与 PagedAttention 一致按 block 对齐。

**适用场景**：system prompt 固定且长（客服/agent 工作流）、多轮对话（每轮追加）、few-shot 批量评估、beam search/采样多条候选。**不适用**：前缀几乎不共享（每次随机 prompt）——纯开销；此时应关闭。

**代码**：`solutions/python/src/answers/bytedance/prefix_cache.py` —— `RadixPrefixCache`（块粒度 match/insert、叶子优先 LRU 淘汰）与 `simulate_hit_rate`（回放请求序列算命中率，测试验证：4 块共享前缀 + 1 块私有的 10 条请求，命中率 = 9×16/(10×20) = 0.72，稳态 0.8，冷启动首条为 0）。

## Q9. Orca 迭代级请求调度的设计思路（AML 一面 4）

Orca（OSDI'22）两点核心：

1. **iteration-level scheduling（调度粒度到单步）**：不等整批完成，每个 decoder step 结束后重组 batch——完成的请求移出、等待的请求塞入、其余继续。对比 static batching：batch 尺寸动态钉在 GPU 允许的最大值，短请求不陪跑长请求，吞吐提升数倍。
2. **selective batching（选择性批处理）**：不同请求在同一 step 的输入长度不同，且有些操作（attention 各自处理自己的 KV）无法简单 batch——在能 batch 的算子（linear/LayerNorm）上拼接处理，attention 等按请求分别算，"选择"在哪一层批、哪一层不批。

它是 vLLM continuous batching 的前身；vLLM 在其上叠加 PagedAttention 解决 KV 碎片。追问点：**为什么 Orca 还不够**——连续预留 KV 显存利用率低，这正是 PagedAttention 补的位。

## Q10. 大模型推理的主要性能瓶颈（AML 一面 1）

1. **decode 阶段 memory bound**：每 token 要读全部权重 + 全部 KV，计算密度低（batch=1 时 GEMM 退化成 GEMV）——最核心瓶颈；TPOT 由带宽决定。
2. **prefill 阶段 compute bound**：长 prompt 一次算完，TTFT 由 FLOPS 决定；prefill/decode 混跑互相干扰（chunked prefill 缓解）。
3. **调度与排队**：批组装等待、请求间互相阻塞、抢占重算。
4. **kernel 与框架开销**：小 kernel launch 开销（CUDA Graph 消除）、非融合算子的中间落盘、Python 开销（编译图/overlap scheduler 消除）。
5. **并发与通信**：TP 的卡间通信、PD 分离的 KV 传输。

定位顺序：先看 SLO 指标分布定阶段（TTFT or TPOT），再上 profile（Nsight / 框架级的 step time 分解）。

## Q12. MoE 模型的推理优化实践经验（实习-一面-1 推理优化 6）

基础同《03 GEMM 与算子优化》Q10（RL 场景 MoE：小 batch、专家负载倾斜）。字节追问集中在：

- **访存特征**：decode 时每个 token 只激活 top-k 个专家，但仍需读 router + 激活专家的权重；小 batch 下"激活专家数 × batch"不足以摊平权重读取 → **专家权重读取是瓶颈**，优化方向是更大 batch / 专家并行缓存 / fused MoE kernel（把 gate+dispatch+expert+combine 融合，避免反复搬运激活）。
- **RL 场景特殊性**：rollout 并发大（同 prompt 多采样）→ 前缀 KV 复用收益高；reward 与 KL 计算占用可观，可与 rollout 重叠。
- **all-to-all 通信**：EP（专家并行）下 token dispatch/combine 是 all-to-all，小消息时延迟主导 → 折叠成更大消息、计算通信重叠。

## Q13. 如何判断 MoE 确实学到了专家分工，而非把 dense 拆开（实习-一面-1 推理优化 7）

一套可量化的体检指标（配 `solutions/python/src/answers/bytedance/moe.py` 的 `diagnose_routing`）：

1. **负载分布 $f_e$**（`expert_utilization`）：各专家承接 token 占比。真分工：基本均匀（aux loss 约束下）；假分工/坍缩：集中于少数专家。
2. **路由熵**（`routing_entropy`）：均匀随机 = $\ln N_e$，one-hot = 0。**低熵 + 负载均匀** = 分工（每个 token 明确地选专家，但整体均衡）；**高熵** = router 没学到东西（近似均匀随机）；**低熵 + 负载倾斜** = 坍缩。熵必须和负载联合解读——这是本题陷阱。
3. **专家激活的语义聚类**（最硬的证据）：按 token/样本域统计各专家激活分布，看专家是否对领域（代码/数学/多语言）、token 类型（数字/标点/术语）形成聚类——Switch 论文的专家可视化做法。
4. **反事实对照**：固定 expert 数但随机初始化不训 router vs 正常训练，比较下游损失；或把 router 换成均匀分配，若性能不掉说明分工是假的。
5. **aux loss 曲线**：`load_balance_loss`（Switch 公式 $N_e\sum_e f_e P_e$，均匀时 =1）训练中应稳定在略高于 1。

**代码验证**：`tests/test_bytedance.py::TestMoE` —— 均匀路由 aux=1 的解析校验、坍缩（one-hot 路由）被 `diagnose_routing` 正确判 `collapsed=True`、熵上下界（uniform=ln N，one-hot=0）。

## Q14. RL + MoE 训练中 reward 导致 routing 退化（请求集中到少数 expert）如何处理（实习-一面-1 推理优化 8）

现象机理：RL 目标（如可验证奖励）只优化最终输出，router 若因初始化/奖励信号偏差把某类样本都送去少数专家，这些专家变强 → 正反馈 → 负载坍缩，其余专家"饿死"，等效容量退化为小 dense。

处理手段（训练侧 → 路由侧 → 监控侧）：

1. **负载均衡损失**：Switch/DeepSeek aux loss（$N_e\sum f_e P_e$，可导近似），RL 阶段保持不撤；
2. **router z-loss**（`router_z_loss`）：惩罚 logsumexp(logits)²，防 logits 爆炸、softmax 饱和后梯度无法纠正路由；
3. **路由温度与噪声**：训练期对 router logits 加噪声/温度退火，维持探索；
4. **capacity factor 与 token dropping**：超容 expert 丢 token，硬性逼流量分流（dropping 率要监控）；
5. **监控报警**：每 N 步输出 `expert_utilization` 分布 + 路由熵（`diagnose_routing().collapsed`），倾斜早发现早回滚（RL checkpoint 漂移快）；
6. **奖励侧排查**：确认不是 reward 对某类输出模式系统性偏置（先看 reward 分布按专家分组是否倾斜，再动路由）。

**代码验证**：`moe.py` 的 aux/z-loss 与指标全部带解析对拍（见 Q13 的测试）。

## Q15. 构建一个 AI Agent 应用需要哪些核心模块（校招-1 推理优化 6）

开放题，按"感知—规划—执行—记忆"给结构，面试加分点是每个模块落到一个具体技术选型：

1. **模型底座**：LLM 推理服务（vLLM/SGLang 部署、prefix cache 复用 system prompt 与工具说明、流式输出）；
2. **规划（Planning）**：任务分解（ReAct / plan-and-execute）、反思重试（Reflexion）、多轮迭代控制（最大步数/预算）；
3. **记忆（Memory）**：短期=对话上下文（KV cache 与滑动窗口管理）、长期=向量库检索（RAG，embedding + ANN 索引）；
4. **工具（Tools/Action）**：函数调用协议（JSON schema 描述 + 参数校验）、代码解释器、检索、外部 API；工具结果回灌的 token 预算控制；
5. **编排与状态**：状态机/图执行引擎（LangGraph 类）、并发与子 agent 分发、错误传播；
6. **评测与安全**：轨迹回放评测、工具调用成功率、越权/注入防护、成本与延迟监控（token 计量、缓存命中率）。

字节特色追问：**延迟预算**（多步 agent 每步都是一次 prefill+decode，prefix cache 命中率直接决定响应速度）与**并发**（会话态路由到同实例提升缓存命中）。
