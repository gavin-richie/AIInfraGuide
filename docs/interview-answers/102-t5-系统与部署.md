## 一、网络与协议（中科类脑重点题）

### Q1. AI 推理框架中常用的通信协议有哪些？（类脑 Q1）

分三层答（外部服务 / 内部组件 / 集合通信）：

| 层 | 协议 | 用途与理由 |
|---|---|---|
| 对外 API | **HTTP/1.1 + REST(JSON)**、**HTTP/2 gRPC(Protobuf)**、WebSocket(SSE)流式 | OpenAI 兼容 API 是 HTTP JSON；gRPC 二进制序列化小、多路复用、强 schema——服务间调用主流；SSE/WS 做流式 token 输出 |
| 进程/节点内 | **UCX、ZeroMQ、共享内存 + Unix Domain Socket** | tokenizer↔engine 高频小消息走 UDS/共享内存（vLLM V0 的引擎通信用 ZMQ 消息队列） |
| GPU 集合通信 | **NCCL（Run:RPC/verbs）、RDMA(RoCE/IB)、TCP fallback** | TP all-reduce、PD 分离 KV 传输（NIXL/UCX）；跨机走 RDMA 才能吃到带宽 |
| 服务发现/编排 | HTTP + JSON（K8s API）、etcd(gRPC) | 副本管理、健康检查 |

答题先分层再各举一例并说"为什么这层选它"（序列化开销/延迟/吞吐/流式语义）。

### Q2. 多路复用技术有哪些？在推理框架中如何应用？（类脑 Q2）

**IO 多路复用**：一个线程监听多个 fd 的就绪事件——`select`（fd 数量上限 1024、O(n) 轮询）→ `poll`（无 1024 限制仍 O(n)）→ **`epoll`**（Linux，红黑树注册 + 就绪链表回调，O(1) 事件通知，边缘/水平触发）；BSD/macOS 对应 kqueue；Windows IOCP 是完成端口模型（异步 IO 而非就绪通知）。再加 POSIX 的 `AIO`、Linux io_uring（真正的异步、批量提交）。

**推理框架中的应用**：① **API server 单线程管成千上万的流式连接**——asyncio（底层 epoll）同时服务 N 个客户端的 SSE 流（每 token 推一段），不按连接开线程；② **engine 与 worker 间**：ZMQ/UDS 的多路消息（请求入队、输出发散、metrics）；③ **批量聚合**——多路复用收集"当前就绪的请求"组成一个 batch（continuous batching 的输入侧）；④ 多卡监控（子进程 stdout/状态 fd 聚合监听）。epoll + 非阻塞 IO 是 C10K+ 并发的标准答案；io_uring 是新趋势（更高 IOPS、批量系统调用）。

### Q3. HTTP/2.0 相较 HTTP/1.1 的核心改进？（类脑 Q3）

1. **二进制分帧**：报文拆成 frame（HEADERS/DATA...），解析高效、错误域小（1.1 是文本行解析）；
2. **多路复用（核心）**：一条 TCP 连接上多个 stream 并行交错传输，**消除 HTTP/1.1 的队头阻塞**（1.1 里前一个大响应不完成，后面请求都得等；pipelining 也串行响应）——但 TCP 层丢包仍会阻塞所有 stream（TCP HoB），HTTP/3(QUIC) 才解决；
3. **头部压缩 HPACK**：静态表 + 动态表 + 哈夫曼编码，重复 header（cookie 等）几乎零成本——对话式 API 每次都带大 header 时收益明显；
4. **服务端推送**（Server Push，实践中被 Chrome 弃用）、**流优先级与依赖**（DATA 帧可标 priority）；
5. **流量控制**：连接级 + 流级两层 window（WINDOW_UPDATE）。
   对推理服务的意义：gRPC 基于 HTTP/2——多客户端并发请求复用少量 TCP 连接、header 小、双向流式（unary/server-streaming 正好对应 LLM 的 token 流）。

### Q4. 视频会议通常采用什么通信协议？（类脑 Q4）

信令与媒体分离：**信令**用 SIP（会话发起）或 H.323、现代 WebRTC over HTTPS（SDP offer/answer 协商）；**媒体传输**用 **RTP/RTCP over UDP**（实时性优先——TCP 重传抖动不可接受；RTP 载荷音视频、RTCP 传质量反馈丢包率/抖动）；**加密**SRTP（RTP + DTLS 密钥协商）；**NAT 穿透**ICE/STUN/TURN；**丢包对抗**FEC 前向纠错 + NACK 重传 + PLC 丢包隐藏、抖动缓冲（jitter buffer）；带宽自适应（REMB/transport-cc）。编解码 H.264/H.265/VP8/VP9/AV1 + Opus。答题框架：**UDP 上的 RTP/SRTP 传媒体、SIP/WebRTC 做信令、FEC/NACK/抖动缓冲保实时**。

### Q5. Linux 内存管理机制的核心内容？（类脑 Q5）

1. **虚拟内存与页表**：每进程独立虚拟地址空间，多级页表（x86-64 四级 PGD→PUD→PMD→PTE）+ TLB 缓存；大页（THP/hugetlb）减 TLB miss——GPU 训练常锁大页；
2. **物理页管理**：伙伴系统（buddy，2 的幂次阶分配解外碎片）+ **slab/slub**（内核对象缓存解内碎片，kmalloc 基于 slab）；
3. **进程地址空间**：代码/数据/BSS/堆（brk）/mmap 区/栈；匿名页 vs 文件页；
4. **缺页与换页**：demand paging（访问才映射）、major/minor fault、swap（换出到磁盘）、页回收（LRU 链表 active/inactive、watermark、kswapd 后台回收）；
5. **Copy-on-Write**：fork 后共享物理页，写时复制——推理服务多 worker 共享权重页；
6. **OOM**：内存耗尽按 oom_score 杀进程（容器 cgroup memory limit 触发 OOM kill 常见）；
7. 其他：mmap 共享内存、hugepage、NUMA 策略。与推理相关落点：GPU pinned memory（页锁定不被换出）、KV offload 用大页、OOM 排查看 dmesg/cgroup。

### Q6. Docker 的 namespace 隔离机制如何工作？（类脑 Q6）

Namespace 让进程看到"独立的系统资源视图"——`clone(CLONE_NEW*)` 创建：

| namespace | 隔离内容 |
|---|---|
| **pid** | 进程号（容器内 PID 1 起，看不到宿主其他进程） |
| **net** | 独立网络栈：网卡、IP、路由表、iptables、端口空间（veth pair 连宿主网桥） |
| **mnt** | 挂载点（容器自己的 rootfs，联合挂载 layered fs） |
| **uts** | 主机名/域名 |
| **ipc** | System V IPC/POSIX 消息队列 |
| **user** | UID/GID 映射（容器 root ≠ 宿主 root） |
| **cgroup**（ns） | cgroup root 视图 |

容器 = 同一内核上被 namespace 包住的一组进程（`docker run` → runc 按 bundle 配置 clone 出这些 ns 并 exec 入口进程）。验证：`lsns`、`nsenter -t <pid> -n` 进入某进程网络 ns。配套的 cgroups 负责**资源限制**（namespace 管"看得见什么"、cgroup 管"用多少"）。

### Q7. Docker 容器间通信的方式有哪些？（类脑 Q7）

1. **bridge（默认）**：每容器一个 veth 接到 docker0 网桥，同主机的容器经网桥二层互通（容器名做 DNS 由 embedded DNS 解析，`--link` 已废弃）；
2. **自定义 bridge 网络**：`docker network create`——隔离广播域 + 自动 DNS（服务名互访，推理服务 compose 里 api→engine 就这么配）；
3. **host 网络**：容器直接用宿主网络栈（无 NAT、性能最好、端口冲突风险）；
4. **none**：无网络（lo only）；
5. **container 模式**：`--network container:<id>` 共享另一容器网络栈（sidecar）；
6. **overlay 网络**：跨主机（VXLAN 封装，Swarm/K8s CNI flannel/calico 类似）；macvlan/ipvlan 直挂物理网；
7. 不走网络：**共享 volume / IPC(`--ipc=host` 或 shareable，共享内存队列)/unix domain socket volume 挂载**——同主机高性能路径。

### Q8. Docker 的底层实现原理？（类脑 Q8）

三大基石：

1. **Namespace**：视图隔离（上题六种 ns）；
2. **Cgroups**：资源限制（CPU shares/quota、memory limit、blkio、pids），保证"用多少"；
3. **联合文件系统（UnionFS/overlay2）**：镜像分层——只读层（image layers）+ 读写层（container layer）+ init 层；写时复制（CoW：改文件先 copy-up）、whiteout 删文件。镜像=分层的 tarball（registry 存 blob）。

启动链路：`docker run` → dockerd 解析镜像/配置 → containerd（gRPC）→ containerd-shim → **runc** 按 OCI bundle（config.json + rootfs）`clone(CLONE_NEW*) + cgroup + pivot_root` 创建进程，之后 runc 退出、shim 接管（容器生命周期与 dockerd 解耦）。GPU 容器额外把 `/dev/nvidia*`、driver 库、`nvidia-container-runtime`（now CDI）注入——面试常追问"容器怎么用 GPU"：本质是设备节点挂载 + 驱动用户态库挂载，内核驱动共享宿主。

### Q9. Linux 替换文本内容的常用方法；vim 常用命令（类脑 Q9/Q10）

**替换文本**：① `sed -i 's/old/new/g' file`（`-i` 原地；`s///g` 全局；`sed '1,10s/a/b/'` 范围；`-E` 正则）；② `tr 'a-z' 'A-Z' < in > out`（单字符映射）；③ `awk '{gsub(/old/,"new"); print}'`（按列/条件替换更灵活）；④ `perl -pi -e 's/old/new/g' file`；⑤ 批量：`find . -name '*.md' | xargs sed -i 's/a/b/g'`；⑥ vim 内 `:%s/old/new/gc`。注意 `-i` 直接改文件，重要文件先备份或用 `sed -i.bak`。

**vim**：模式（normal/i 插入/v 可视/: 命令）；移动 `hjkl 0 ^ $ gg G { } w b :n`；编辑 `i a o x dd yy p u Ctrl-r`；查找替换 `/pat n N :%s/a/b/gc`；可视化块 `Ctrl-v`（列编辑，批量注释）；多窗口 `:vsp :sp Ctrl-w w`；保存退出 `:wq :q! ZZ`；其他实用 `:set nu`、`:%!xxd`（十六进制）、`. `（重复上一个修改）。答题给 10-15 个高频命令即可。

### Q10. 进程间通信（IPC）的方式有哪些？（类脑 Q11）

详见 [09 C++ 与系统基础](./09-cpp与系统基础.md) IPC 题：**管道（匿名 pipe/命名 FIFO）、消息队列、共享内存（shm/mmap，最快，需配信号量/互斥锁同步）、信号量、信号 signal、socket（Unix 域/TCP）**。推理框架选型注释：同机高频大块数据（KV 块、图片）→ 共享内存；控制消息 → UDS/ZMQ；跨机 → gRPC/TCP。

### Q11. 如何对协程数量进行限制？（类脑 Q12）

协程虽廉价也不能无限开（每个占栈内存、调度与内存压力、下游被打爆）：① **信号量**（`asyncio.Semaphore(N)` 包住任务提交，`async with sem:` 控制并发上限——最常用）；② **协程池/工作队列**：固定 N 个 worker 协程从队列取活（生产者-消费者）；③ **批量分批**（gather 分批/`Semaphore` + gather）；④ Go 侧：channel 容量天然限流 + `runtime.GOMAXPROCS` 控线程；⑤ 全局层：令牌桶/限流器（对"请求级并发"而非"协程数"限流）；⑥ 背压：队列满时拒绝/降级。示例一句话：`sem = asyncio.Semaphore(100); await asyncio.gather(*[run(i, sem) for i in range(10**6)])`——百万任务并发不超 100。

### Q12. 开闭原则在实际编码中如何体现？（类脑 Q13）

开闭原则（OCP，对扩展开放、对修改关闭）：新增行为靠**新增代码**而非改老代码。落地手法：① **策略模式**替代 if-else 链——新量化算法/新 scheduler 策略实现同一接口、注册进工厂，调用方不动；② **注册表/插件机制**（推理框架的算子注册、模型 registry：`@Registry.register("my_op")`，加算子零侵入——vLLM/TRT 都这么干，对应曙光 YAML 注册题见 Q26）；③ 依赖倒置：高层依赖抽象接口，测试用 mock 注入；④ 模板方法/钩子：骨架固定、步骤可覆写。反例：在 scheduler 主流程里硬编码新策略的 if 分支（每次加策略都改核心文件、回归风险扩散）。答"为什么"：隔离变更影响面、可测性、并行开发不冲突。

### Q13. 并发编程有哪些常见实现方式？OpenMP 与 MPI 的区别和场景（类脑 Q14、海康 Q7）

按抽象层次：① **多进程**（隔离好、开销大——Python 绕 GIL 的路）；② **多线程**（共享地址空间，锁/原子保护——C++ std::thread、Python 受 GIL 限制 CPU 并行为 1）；③ **协程/异步 IO**（单线程事件循环，asyncio/Go goroutine——IO 密集）；④ **线程池/任务队列**（复用、控制并发度）；⑤ **锁无关结构**（无锁队列 CAS、RCU）；⑥ **并行框架**（OpenMP 指令级、TBB、Ray/Joblib 分布式）。选型口诀：CPU 密集→多进程/多核/向量化；IO 密集→异步/协程；混合→池 + 队列。见 [09](./09-cpp与系统基础.md) 并发题与下题。

**OpenMP vs MPI**：OpenMP 是**共享内存**并行——编译制导（`#pragma omp parallel for`）派生线程，fork-join 模型，线程间靠变量共享+同步，只跑单机，改造成本极低；MPI 是**分布式内存**消息传递——显式 `MPI_Send/Recv/Bcast/Allreduce`，进程级隔离，跨节点扩展（超算主流），但通信要自己编排。场景：单机多核 CPU 循环并行（算子 CPU 版、数据预处理）用 OpenMP；多机集群（训练 all-reduce、HPC）用 MPI；两者可叠加（节点内 OpenMP + 节点间 MPI，hybrid）。对应关系：GPU 世界的"TP within node + 跨机集合通信"同构。

## 二、锁与并发（海康实习）

### Q14. 互斥锁与无锁操作的区别；互斥锁的风险（海康实习 Q1/Q2）

**互斥锁**：进入临界区前 `lock`，拿不到就**睡眠让出 CPU**（futex 系统调用），保证互斥但引入上下文切换（微秒级）、优先级管理、锁竞争的队列排队。**无锁（lock-free）**：基于硬件原子指令（CAS/LL-SC、fetch-add）+ 重试循环（或无等待 wait-free 每步有进展）——不睡眠、无死锁、竞争小延迟低；代价：实现难（ABA 问题、内存序）、高竞争下自旋烧 CPU、不总是更快。**适用**：临界区短（几条指令、计数器/指针交换/队列）→ 无锁或原子；临界区长/会睡眠（IO、大计算）→ 互斥锁。

**互斥锁的风险**：① **死锁**（循环等待——按全局顺序加锁、`std::scoped_lock` 多锁一次获取、try-lock 超时回退）；② **优先级反转**（低优先级持锁阻塞高优先级，火星探路者事故——优先级继承 `PTHREAD_PRIO_INHERIT`）；③ **性能**：上下文切换、锁竞争串行化（热点锁限制扩展性）、伪共享；④ 忘记解锁（异常路径）→ RAII（lock_guard/unique_lock）；⑤ 递归死锁（非递归锁重入）；⑥ 锁粒度不当：太粗并发低、太细易死锁难维护。

### Q15. 自旋锁与互斥锁的区别；线程拿不到互斥锁时 OS 做什么？（海康实习 Q3/Q4）

**自旋 vs 互斥**：自旋锁拿不到就**忙等（轮询）**——不切上下文、一旦释放立刻拿到，但空转烧 CPU；互斥锁拿不到则**睡眠排队**。**适用**：临界区极短（< 两次上下文切换开销 ~几 µs）且持锁者不会睡眠 → 自旋（内核中断上下文必须自旋）；临界区长或可能睡眠 → 互斥。混合形态：**adaptive/mutex 自适应**（先自旋若干次再睡眠，pthread `_NP` / Linux mutex 大多数时候 futex 短等）。

**拿不到互斥锁时 OS 的动作**（以 Linux futex 为例）：① 用户态先试一次原子 CAS（快路径，无系统调用）；② 失败 → `futex(FUTEX_WAIT)` 系统调用：把当前线程状态置 TASK_INTERRUPTIBLE、挂到该锁的**内核等待队列**，触发**上下文切换**（保存寄存器/换地址空间若跨进程/调度别的线程）；③ 释放方 `futex(FUTEX_WAKE)` 唤醒队首（按调度类/优先级选），被唤醒线程进就绪队列、等 CPU 后**从内核返回用户态重试 CAS**；被信号打断可提前返回 EINTR。要点：**睡眠-唤醒 + 等待队列 + 两次上下文切换**，这就是"为什么短临界区用自旋"。

## 三、体系结构与排障（讯飞）

### Q16. 大端序与小端序；主流架构用哪种？（讯飞校面 Q2）

小端（little-endian）：低字节放低地址（x86/ARM 默认）；大端（big-endian）：高字节放低地址（网络字节序、老 PowerPC/SPARC）。例：`0x12345678` 小端内存 `78 56 34 12`。判断：C 里 `*(char*)&x == LSB`；Python `sys.byteorder`。工程意义：网络协议用大端（`htons/ntohs`）、跨平台文件/权重序列化必须固定字节序（numpy/safetensors 显式声明）、按字节 cast 的 SIMD kernel 在两种端序下写法不同。主流 CPU（x86-64、Apple/高通 ARM、RISC-V 默认 LE）都是小端。

### Q17. 设计一个 CPU 需要考虑哪些方面？指令集与流水线各阶段的作用？（讯飞校面 Q3）

**设计维度**：① 指令集架构 ISA（RISC 精简定长 vs CISC 复杂变长；寄存器数量/宽度、寻址模式、向量/加密扩展）；② **流水线设计**（级数、冒险处理）；③ **存储层级**（L1/L2/L3、一致性协议 MESI、TLB/页表）；④ 分支预测（BHT/BTBT，猜错代价）；⑤ 乱序执行（Tomasulo 保留站、重命名寄存器）与超标量/SMT；⑥ 功耗与频率（DVFS、电源门控）；⑦ 缓存一致性/多核互联；⑧ 中断与异常、安全（MMU 隔离、TrustZone）。

**经典五级流水线**：**取指 IF**（从 PC 取指令入指令队列）→ **译码 ID**（解析操作码/寄存器号，读寄存器堆）→ **执行 EX**（ALU 运算/地址计算）→ **访存 MEM**（load/store 读写数据缓存）→ **写回 WB**（结果写寄存器堆）。流水线提升吞吐（每周期完成一条指令的稳态），带来**冒险**：结构冒险（资源冲突——哈佛结构分离 I/D cache）、数据冒险（RAW——前递/旁路 forwarding、load-use 插气泡）、控制冒险（分支——预测/延迟槽）。答完补一句现代 CPU 在五级之上加深（14-20 级）加宽（超标量 4-8 发射）加乱序，GPU 则走多线程掩盖延迟的另一条路。

### Q18. 用户态与内核态的区别；如何切换？（讯飞校面 Q4）

**区别**：CPU 特权级（x86 ring0/ring3，ARM EL0/EL1）——用户态只能访问受限指令与自己的地址空间，内核态可执行特权指令（IO、页表修改、关中断）、访问全部内存；隔离是保护操作系统与其他进程的根基。**切换的三种入口**：① **系统调用**（trap 指令 `syscall`/`svc`，主动）；② **中断**（硬件：网卡/时钟，异步）；③ **异常**（缺页/除零/非法指令，同步）。**切换流程**：保存用户上下文（PC/寄存器入内核栈或 TLS）→ 切到内核态与内核栈 → 执行处理程序 → 恢复上下文 `sysret/eret` 返回。代价：几十 ns 到 µs 级（上下文 + cache/TLB 污染）——所以高性能 IO 才有 mmap/vDSO/零拷贝/IO 复用（一次 syscall 管多个 fd）。

### Q19. 显存越界问题的常见排查方法？（讯飞校招 Q4）

排查工具与路径：① **compute-sanitizer**（原 cuda-memcheck）：`memcheck`（越界读写/未初始化）、`racecheck`（smem 竞态）、`initcheck`、`synccheck`——定位到 kernel 名 + 行号，首选；② 编译加 `-G -lineinfo` 保留行号（release 用 `-lineinfo` 不掉优化）；③ `cuda-gdb` 断点/单步看非法访问现场；④ `CUDA_LAUNCH_BLOCKING=1` 同步执行让报错对准 kernel（异步报错常滞后到下一个同步点）；⑤ 常见成因自查：线程索引算错（`blockIdx*blockDim` 漏乘/越界）、smem 数组越界、变长 batch 未 clamp、KV cache 块表越界、指针别名/悬空（free 后用、stream 生命周期）；⑥ 越界的"延迟爆炸"现象： Illegal memory access 之后 context 损坏，后续所有调用报错——先 `CUDA_LAUNCH_BLOCKING` 复现；⑦ PyTorch 侧：`PYTORCH_NO_CUDA_MEMORY_CACHING=1`（关缓存分配器定位真实 OOM 位置）、torch.cuda.memory._record_memory_history 看 OOM 时的分配栈。

## 四、Linux 系统与网络编程（小光子/小厂）

### Q20. Linux 内核虚拟地址空间的布局与机制；计算机内存分级体系（小光子 Q1、小厂实面 Q1）

**用户空间布局**（x86-64，从低到高）：`.text`（代码，r-x）→ `.data`/`.bss`（已初始化/零初始化全局）→ **堆**（brk 向上增长，malloc 小块）→ **mmap 区**（文件/匿名映射，向下增长——malloc 大块、共享库 so 加载在这里）→ **栈**（向下增长，函数帧/局部变量，8MB 默认）→ 内核空间（高 128TB，用户不可直接访问）。机制：缺页中断按需分配（demand paging）、写时复制（fork）、页表+TLB、ASLR 随机化偏移。经典追问"一个 8GB 的程序能在 4GB 内存的机器上跑吗"——可以（虚拟地址空间 + 按需调页 + swap）；"static 局部变量在哪"——.data/.bss。

**计算机内存分级体系**：寄存器（<1ns）→ L1（~1ns，几十 KB）→ L2（~4ns）→ L3（~10-40ns，MB 级共享）→ 内存 DRAM（~100ns，GB）→ SSD/HDD（µs-ms）——容量换速度的层级，程序局部性（时间/空间）是它能工作的前提；GPU 侧对应寄存器→smem/L1→L2→HBM（见 [101](./101-t5-量化与算子.md) Q23）。

### Q21. 零拷贝技术的原理与应用场景？（小光子 Q2）

**问题**：传统 read+write 文件发送要 4 次拷贝（DMA→内核页缓存→用户 buf→socket 缓冲→DMA）+ 4 次用户/内核切换。**零拷贝消除 CPU 参与的冗余拷贝**：

1. **mmap+write**：文件映射进用户空间（省一次拷贝），适合需要修改部分数据的场景；
2. **sendfile**（`sendfile(out_fd, in_fd, ...)`）：内核内完成页缓存→socket 的传送，2 次切换 0 次 CPU 拷贝（带 scatter-gather/DMA 的网卡连内核内拷贝都省）；Kafka/RocketMQ/Nginx 的标配；
3. **splice**（管道缓冲区中转）、tee（管道复制）；
4. **MSG_ZEROCOPY**（send flag，大数据块用户态缓冲 DMA 直出——模型分发/日志上传）；
5. 相关：`O_DIRECT` 绕过页缓存（数据库自管缓存）、mmap 加载模型权重（多个 worker 共享同一份物理页，CoW）。

应用场景：静态文件服务、消息队列持久化读盘、模型权重加载（mmap 共享）、GPU 场景 pinned memory + `cudaHostRegister`（DMA 直达显存，H2D 零冗余）。

### Q22. Socket 编程的完整流程？（小光子 Q3）

**服务端**：`socket(AF_INET, SOCK_STREAM, 0)` 创建 → `setsockopt(SO_REUSEADDR)` → `bind(ip:port)` 绑定 → `listen(backlog)` 被动打开（半连接/全连接队列）→ `accept()` 取出连接得到 conn_fd（阻塞点）→ `read/recv` ↔ `write/send` 读写 → `close()`。**客户端**：`socket` → `connect(ip:port)`（三次握手）→ 读写 → `close`（四次挥手，TIME_WAIT 在主动关闭方）。工程要点：并发模型（每连接线程 / epoll+线程池 / reactor）；`SO_REUSEADDR` 防 TIME_WAIT 绑定失败；`TCP_NODELAY` 关 Nagle（低延迟流式输出要开）；粘包处理（长度前缀/分隔符——SSE 用 `\n\n`）；`select/poll/epoll` 多路复用管大量连接（见 Q2）；UDP 则 socket(SOCK_DGRAM) + recvfrom/sendto 无连接。

### Q23. 线程同步的常用机制（南湖 Q10）

① **互斥锁 mutex**（临界区互斥，RAII）；② **条件变量 condvar**（`wait(lock, pred)` / `notify_one/all`——等待某个条件成立，经典生产者消费者，必须配锁防丢唤醒）；③ **读写锁**（读多写少）；④ **信号量**（资源计数，N 个许可证）；⑤ **原子变量/fence**（`std::atomic` CAS，无锁计数/标志）；⑥ **barrier**（阶段同步，CUDA `__syncthreads` 的 CPU 版）；⑦ **future/promise/async**（一次性的结果同步）；⑧ 事件/文件描述符就绪（epoll 跨线程唤醒，eventfd）。选型：互斥+条件变量覆盖 90% 场景；读写锁慎用（写者饥饿）；高频短临界区用 atomic。Python 侧 threading 同名原语 + asyncio 用事件循环天然单线程（`asyncio.Lock/Event/Queue`）。

### Q24. CUDA Stream 的使用要求；设备端操作重叠（南湖 Q11）

Stream 是 GPU 上的操作队列，同 stream 内严格串行，**不同 stream 可并发**（前提是资源未占满）。使用要求：① 所有操作带 stream 参数（kernel launch、`cudaMemcpyAsync`）；② **异步拷贝必须用 pinned memory**（页内存在 DMA 直达，普通可分页内存会退化成同步）；③ 跨 stream 依赖要**显式事件同步**（`cudaEventRecord` + `cudaStreamWaitEvent`），没有隐式顺序；④ 资源竞争：计算与拷贝用同一引擎/内存带宽，重叠收益取决于 SM/拷贝引擎是否都吃满（小 kernel 重叠明显，大 kernel 顺序执行）；⑤ stream 生命周期与销毁（`cudaStreamDestroy` 前确保任务完成）。**重叠模式**：H2D 拷贝（stream1）∥ 前一批计算（stream2）∥ D2H（stream3）三段流水（数据并行分块）；或多卡 per-device stream；优先级 stream（`cudaStreamCreateWithPriority`）让 decode 先行。详见 [01 CUDA 基础与体系结构](./01-cuda-基础与体系结构.md) Stream 题。

### Q25. Git 多人协作的工作流程（南湖 Q13）

标准 **feature branch 工作流**：① 从最新 main 切分支 `git checkout -b feat/xxx origin/main`；② 小步提交（规范 message：feat/fix/docs/refactor）；③ 远程同步：`git fetch` + `git rebase origin/main`（线性历史）或 merge；④ push 到自己的远端分支，开 **PR/MR**：CI（构建+测试）+ code review；⑤ review 通过 merge 进 main（squash/merge commit 按团队规范）；⑥ 删分支、本地清理。冲突处理：rebase 时 `git status` 找冲突文件 → 手工解决 → `git add` → `git rebase --continue`。协作纪律：不直接 push main、提交前 pull --rebase、大改动拆 PR、锁住敏感文件（CODEOWNERS）。加分：说清 rebase vs merge 的取舍（线性可读 vs 保留真实拓扑）、`git reflog` 救命、cherry-pick 回移 hotfix。

## 五、C++/Python 语言基础（南湖/小厂/传音）

### Q26. Python 垃圾回收机制；循环引用如何处理（南湖 Q1/Q2）

Python GC = **引用计数为主 + 分代标记-清除为辅**：

1. **引用计数**（主要）：每个对象 `ob_refcnt`，增减即时，归零立刻释放—— deterministic、快；缺点：**循环引用**（a.b=b, b.a=a 计数互不归零）与每次赋值的计数开销；
2. **分代回收**（补循环引用）：0/1/2 三代，新对象在 0 代；阈值触发（分配减释放超 700）或 `gc.collect()` 时，**从根集合（全局/栈/活动帧）做可达性标记**，只扫描容器类对象（list/dict/tuple/自定义类——int/str 不参与）；不可达的循环垃圾被清除，幸存者晋升老年代（老代扫描频率低）；
3. **循环引用的处理细节**：标记阶段先对疑似环做**试探性减引用**（从 refcnt 里扣除容器间引用），归零者即纯环垃圾；有 `__del__` 的环历史上无法安全回收（Python 3.4 起 PEP 442 finalizer 可安全处理，任意顺序调用 `__del__`）；
4. 实务：`weakref` 打破缓存环（LRU cache 持弱引用）、`gc.disable()`（性能敏感服务禁分代 GC 只靠计数）、`tracemalloc`/`objgraph` 查泄漏。

### Q27. 函数内联何时导致性能下降；inline 的作用域影响；除 inline 外还有什么机制触发内联（南湖 Q3/Q4/Q5）

**内联何时变慢**：① **代码膨胀（code bloat）**——inline 展开使二进制变大，指令缓存（I-cache）命中率下降、指令预取失效，大热点循环里尤为明显；② 大函数内联后寄存器压力上升 → 溢出到栈；③ 跨翻译单元重复实例化（模板/头文件函数）拖链接与加载；④ 递归/超长函数内联被编译器拒绝或部分内联反增分支；⑤ 异常处理表膨胀。本质：内联省的是**调用开销**（几 ns）+ 开启跨函数优化，代价是**指令体积**——小而热的函数收益为正，大而冷的函数为负。

**`inline` 关键字**：现代语义主要是**链接属性**（ODR 豁免：允许同一函数在多个翻译单元重复定义，链接器去重），不再是"强制内联"（编译器自行决定）；对作用域的影响：`inline` 函数可定义在头文件被多处 include 而不违反单一定义规则；`inline` 变量（C++17）同理可在头文件定义全局变量。真正建议内联的是 `__attribute__((always_inline))`/`__forceinline`（慎用）。

**其他触发内联的机制**：① **模板实例化**（隐式 inline 语义，定义必须在头文件）；② **类内定义的成员函数**（隐式 inline）；③ **constexpr/consteval 函数**（编译期求值必然展开）；④ **链接时优化 LTO/LTCG**（跨翻译单元内联，函数可见性足够时）；⑤ **匿名 namespace/静态函数**在同一 TU 内自由内联；⑥ 编译器自动内联（`-O2` 起，基于成本模型：调用点频度/函数大小）。

### Q28. 完美转发的概念与实现；右值引用的应用场景（南湖 Q6、小厂一 Q2）

**右值引用 `T&&` 的应用**：① **移动语义**（`std::move` 把左值转右值，接管资源：unique_ptr 传递、vector 扩容时搬 buffer——深拷贝变 O(1) 指针转移）；② **完美转发**；③ move-only 类型（thread/future/unique_ptr 的所有权流）；④ RVO 之外的返回值优化补充。

**完美转发**：泛型代码（工厂/包装函数）把参数**原封不动（保持左/右值性、cv 限定）转发**给内部目标——右值不被提前变成左值（否则移动退化为拷贝）。实现三件套：

```cpp
template <typename T, typename... Args>
std::unique_ptr<T> make(Args&&... args) {           // 1. 万能引用（T&& 且 T 待推导）
    return std::unique_ptr<T>(new T(std::forward<Args>(args)...));  // 2. forward 按 T 的推导结果还原左右值
}
```

工程化对拍（左值拷贝/右值移动的 tracer 计数断言）：`solutions/cpp/tests/test_language_basics.cpp`。

原理：**引用折叠**（`T& && → T&`，`T&& && → T&&`）——传左值时 `Args=T&`，`forward` 返回 `T&`；传右值时 `Args=T`，返回 `T&&`。`std::move` = 无条件转右值（`static_cast<T&&>`），`std::forward` = 有条件转（按推导类型）。陷阱：万能引用必须是**待推导的 `T&&`**（类成员 `Widget&&` 不是）；参数用过一次后右值性即失效（再转发要再 forward）。

### Q29. C++ 专题速答：模板/反射/工厂/static/内存泄漏/char 范围/同名符号/堆栈/指针引用/野指针（小厂一 Q2-Q9、小厂实面 Q4/Q5、传音 Q1-Q3）

- **模板编程**（小厂一 Q3）：编译期泛型——函数/类模板、特化/偏特化、SFINAE 与 `if constexpr`（C++17）、变参模板、概念 constraints（C++20）；值模板参数可做编译期计算（TMP）；实例化在用时发生、定义须可见（放头文件，隐式 inline 语义见 Q27）。
- **反射机制**（小厂一 Q4）：C++ 原生静态反射要到 C++26；现行实现：① **宏注册**（声明+注册宏展开生成元信息——`REGISTER_OP(...)` 打表，推理框架算子注册的通用做法）；② 模板 + 函数签名推导（`typeid`/`__PRETTY_FUNCTION__` 取类型名）；③ 代码生成（protobuf/反射库 RTTR）；④ external tool（clang AST 扫描生成元数据）。答"为什么框架需要"：按字符串名字构造对象/序列化字段。
- **工厂模式**（小厂一 Q5）：创建与使用解耦——简单工厂（switch 返回子类）→ 工厂方法（每产品一个工厂类，符合 OCP）→ 抽象工厂（产品族）；配合注册表实现"按名字创建"（`map<string, function<unique_ptr<Base>()>>` + 自注册静态变量），框架插件化的标准姿势（对应 [100](./100-t5-推理引擎.md) Q8 vLLM 模型注册）。
- **static 变量初始化时机**（小厂一 Q6、小厂实面 Q4）：**局部 static** 首次执行到时初始化（C++11 起线程安全，双检锁由编译器保证——Meyers 单例的基础），生命周期到程序结束（析构在 atexit 链）；**全局/类 static** 在 main 前静态初始化（常量零初始化→动态初始化按翻译单元顺序，**跨 TU 顺序未定义**——static initialization order fiasco，解法是函数内 static 包装）；类 static 成员需类外定义（inline 变量 C++17 免）。
- **内存泄漏常见原因与解决**（小厂一 Q7）：new 无 delete、异常路径漏释放、共享指针循环引用（weak_ptr 打破）、基类析构非虚（子类资源漏）、容器持有裸指针清空不释放、线程持有闭包延长生命周期。工具：valgrind、AddressSanitizer（`-fsanitize=address`，开销小首选）、`__mingw`/dr.memory；结构上 RAII + 智能指针 + 所有权明确。
- **有符号/无符号 char 范围**（小厂一 Q8）：`signed char` -128~127、`unsigned char` 0~255；`char` 本身符号依实现（x86 有符号、ARM Linux 无符号）——**序列化/哈希字节处理用 `unsigned char` 或 `uint8_t`**（符号扩展会污染值，`char c=0xFF; int i=c;` 得 -1）。
- **链接两个库有同名函数时调用谁**（小厂一 Q9）：取决于**链接顺序与符号可见性**——静态链接时按命令行顺序搜索，先找到的库被绑定（后续库的同名符号被忽略）；动态库同名则依装载顺序（`LD_PRELOAD` 抢先——这就是钩子/打桩原理）；C++ 无命名空间 + 非 extern "C" 会有 mangling，同名不同签名可重载共存，真正冲突时可能链接错误（duplicate symbol）或**静默绑定到先者**（最阴险）。工程规范：命名空间隔离、`-fvisibility=hidden`、版本符号（`.symver`）。验证：`nm -D lib.so | grep func`、`ldd`、`LD_DEBUG=bindings`。
- **堆与栈的区别**（小厂实面 Q5、传音 Q2）：栈——编译器自动管理、随函数帧分配释放、快（移动栈指针）、容量小（MB 级）、生存期=函数作用域；堆——手动/智能指针管理、分配慢（分配器查找/锁/系统调用）、容量大（受内存限制）、生存期自由、易碎片与泄漏。使用准则：小且生命周期随作用域→栈；大/动态生存期/跨线程→堆（make_unique/make_shared）。
- **指针 vs 引用；野指针与智能指针**（传音 Q1/Q3）：指针可空可重绑、有算术、占 8 字节；引用必须初始化不可重绑（语法糖+非空语义，编译器可优化）。野指针成因：未初始化、free/delete 后继续用（dangling）、返回局部变量地址、多线程释放竞态——避免：初始化为 nullptr、释放即置空、RAII。智能指针用法：`unique_ptr` 独占（默认选择）、`shared_ptr` 引用计数共享（线程安全的是计数不是对象）、`weak_ptr` 打破环/缓存；`make_shared` 一次分配对象+计数；`enable_shared_from_this`；手写版见 [10 C++ 编程题](./10-cpp编程题.md)。

### Q29b. 回调函数的实现原理（讯飞校招 Q3）

回调 = **把函数（指针/std::function/闭包）作为参数交给被调方，在特定时机由被调方"反过来"调用**——控制反转（IoC）：库代码不认识业务逻辑，留个钩子让业务注入。C 实现：函数指针 `void (*cb)(int)` 存进结构体，事件发生时 `if (cb) cb(arg)`；C++：`std::function<void(int)>` + lambda（可捕获状态）、模板参数传回调（编译期内联零开销——`std::sort` 的比较器）；Python：函数一等公民直接传。底层机制：函数指针就是代码段地址，调用即压参-跳转-执行-ret；注册-触发通常是**事件表/观察者模式**（map<event, vector<callback>>）。使用注意：回调在哪个线程执行（跨线程需投递回原线程——异步 IO 完成回调在事件循环线程）、生命周期（捕获对象先死 → 悬垂，weak_ptr 防）、异常边界（C ABI 回调里不能抛）。推理框架实例：CUDA `cudaLaunchHostFunc`、TensorRT/NCCL 回调、vLLM 逐 token 输出回调。

## 六、PyTorch 工具链与测试（曙光）

### Q30. PyTorch 常用的性能分析工具与方法（曙光 Q1）

① **torch.profiler**（PyTorch profiler with tensorboard）：记录 CPU 算子/GPU kernel/显存，`profile_memory=True`，Chrome trace 导出（`export_chrome_trace`）看时间线与 kernel 耗时分布、tensorboard 的 plugin 看火焰图；② **torch.autograd.profiler**（`record_function` 自定义区间标注）；③ **Nsight Systems**（端到端时间线：CPU gap/流重叠/nccl）+ **Nsight Compute**（单 kernel 深挖：roofline/bank conflict/occupancy）——详见 [08 编译器与性能分析](./08-编译器与性能分析.md)；④ 快速三板斧：`torch.cuda.synchronize()` + `time.perf_counter()` 计时（防异步假象）、`torch.cuda.memory_summary()`、`nvidia-smi dmon`；⑤ 训练侧：`torch.utils.bottleneck`、DDP 的 `torch.distributed` 调试、MFU 估算（见 [104](./104-t5-其余公司杂题.md) RL 训练题）；⑥ `TORCH_LOGS`（2.0+ 的 logging 系统）、`torch.__config__.show()`。答法：先说 profiler（工具面）再说"看什么"（kernel top、CPU launch gap、通信占比、显存增长曲线）。

### Q31. DDP 在多机多卡场景下如何优化？（曙光 Q2）

详见 [07 分布式训练](./07-分布式训练.md) DDP/NCCL 题。要点清单：① **梯度 bucket 重叠**（bucket_cap_mb 调大减少 allreduce 次数、反向计算与通信重叠）；② **通信后端**：NCCL + RDMA（`NCCL_IB_HCA`/SOCKET），多机优先 IB；③ **DDP 与梯度累积**：`no_sync()` 下累积步不 allreduce，最后一步同步（省通信）；④ 混合精度（bf16 + GradScaler）减通信量一半；⑤ 拓扑感知：同机 NVLink 快、跨机慢——`NCCL_PXN`/分层 reduce（先机内后跨机，`cross-device overlap`）；⑥ 大模型换 FSDP/ZeRO 或 TP+PP（DP 每卡全量权重显存受限）；⑦ `find_unused_parameters=False`（免图遍历）、静态图 `static_graph=True`；⑧ 其它：`torch.compile`、`pin_memory`+`non_blocking` 数据加载、避免每步 `.item()` 同步、均衡数据切分（防长尾 rank 等待）、NCCL 超时与悬挂排查（`NCCL_DEBUG=INFO`、`TORCH_NCCL_BLOCKING_WAIT`）。

### Q32. 分布式训练中 batch size 设置的注意事项？（曙光 Q3）

① **与学习率耦合**：线性缩放规则（bs×k → lr×k，大 batch 常配 warmup 防初期发散；bs 很大时 sqrt 缩放更稳）；② **收敛性**：太大 batch 梯度噪声不足、泛化变差（临界 batch size 观点），太小通信/launch 开销占比高；③ **梯度累积等效大 batch**：显存不够时 local bs×accum = 有效 bs，但 BN 统计不等价（GN/LN 无此问题——这也是 LLM 全用 LN 的原因之一）；④ 显存约束：bs 受激活显存限制（重算/ZeRO 可腾空间换 bs）；⑤ 通信效率：DDP 每 step 一次 allreduce——小 bs 多 step 通信占比高；⑥ 数值稳定性：大 batch 的 loss 平均（reduce mean）与 per-GPU loss 归一化一致性；⑦ 数据吞吐：DataLoader worker/prefetch 要跟上 bs 消费速度；⑧ 与序列长度的联合调节（LLM 训练常用 token 预算 = bs×seq_len 恒定的思路）。

### Q33. PyTorch 的图优化机制；PyTorch 2.0 的关键新特性（曙光 Q4/Q5）

**图优化机制**：eager 模式基本无图优化（逐算子调度）——优化发生在：① **torch.compile（2.0+）**：TorchDynamo 捕获字节码级图（FX graph，含控制流 guard），Inductor 生成 Triton（GPU）/C++（CPU）代码并做融合、内存规划；graph break 处自动回退并分段；② JIT/TorchScript（旧路线，trace/script 后可做融合与常量折叠，已被 compile 取代）；③ AOTAutograd/functionalization（梯度与视图语义处理）；④ `torch.inference_mode`/`no_grad`（去 autograd 图）、`torch.fx` 手写 pass 的入口。详见 [08 编译器与性能分析](./08-编译器与性能分析.md)。

**PyTorch 2.0 关键特性**：① **torch.compile**（`mode="max-autotune"` 等，1.3-2× 训练加速，动态 shape 支持）；② **TransformerEngine/FP8 支持**（Hopper）、bf16 全面成熟；③ **scaled_dot_product_attention**（fused/flash/mem-efficient 三后端自动选择）；④ CUDA Graph 更好用（`make_graphed_callables`、reduce-overhead mode）；⑤ `torch.func`（functorch 合入：vmap/grad/functional 化）；⑥ BetterPerf 杂项（pin memory diagonal、2-bit optimizer、DDP 静态图默认化）；⑦ 新部署路线（executorch 前身）。一句话总结："**eager 易用性 + 编译器性能**"。

### Q34. pytest 的常用参数（曙光 Q6）

`pytest tests -v`（详细）`-q`（安静，只出进度点）；`-k "expr"` 按名过滤（`-k "fp8 or mla"`）；`-m mark` 按 marker（`@pytest.mark.slow`，需注册）；`-x` 首错即停、`--maxfail=3`；`-s` 显示 print/stdout（`-s` = `--capture=no`）；`--lf`（last-failed 只跑上次失败）、`--ff`（failed first）；`--durations=10` 最慢用例排名；`-n auto`（xdist 并行）；`--cov=src --cov-report=term-missing`（覆盖率，pytest-cov）；`--tb=short/long/no`（回溯详略）；`--html=report.html`；`-rA`（显示所有 summary）；`--fixtures`、`--collect-only`（dry-run 列用例）。fixtures/参数化是考点常客：`@pytest.fixture`、`@pytest.mark.parametrize`。

### Q35. PyTorch 中如何基于 YAML 配置实现算子注册？（曙光 Q7）

设计题，两层：**代码侧注册表 + YAML 侧声明装载**：

1. 注册表：全局单例 `map<string, Creator>`，宏 `REGISTER_OP(name, cls)` 在静态初始化时插入（见 Q29 工厂/反射）；
2. YAML schema：op 名、后端（cuda/cpu/npu）、输入输出 shape/dtype 约束、kernel 选择参数（tile/bucket）、量化配置；
3. 加载流程：启动时 yaml.safe_load → 逐条校验（schema/pydantic）→ 查注册表拿 Creator → 用 YAML 参数实例化算子对象（构造时据此选 kernel 模板/编译 tile）→ 挂进执行图；
4. 未注册项报错列出可用名；热加载可用版本号 + 原子换表。
   好处：新增算子/换 kernel 配置不改代码（开闭原则，对应 Q12）；注意类型安全（YAML 无类型，须显式校验）与默认值兜底。

### Q36. 跨平台环境下系统级算子的测试策略？（曙光 Q8）

① **对拍（golden test）**：统一 CPU 高精度参考实现（fp64），各平台（CUDA/NPU/ARM/不同 SDK 版本）输出与之比阈值（atol/rtol 按算子类别定——归约类宽容、分段函数严格）；② **输入生成**：随机 + 边界值（0/NaN/Inf/极大极小/subnormal、空 tensor、奇数 shape 对齐边界）+ 回归语料（线上失败样本入库）；③ **确定性测试**：原子类算子多次运行方差上界（或强制确定性版本）；④ **shape 矩阵**：枚举/采样形状（含 bucket 边界），CI 矩阵跑多平台多版本（硬件不够用仿真器 + nightly 真机）；⑤ **性能回归**：每平台基准（防某次改动对某平台劣化）；⑥ **故障注入**：显存不足/OOM、非法输入报错语义；⑦ 分层：单算子单测 → 图级集成（融合后数值） → 端到端模型指标（精度不倒退）；⑧ 工程用 fixture 参数化平台、`pytest -m cuda` 分离 GPU 用例。

## 七、部署与端侧工程（海康/小厂）

### Q37. ncnn 的交叉编译流程；对 ncnn 源码的了解（海康 Q8/Q9）

**交叉编译流程**（以 aarch64 Android/板卡为例）：① 准备目标平台的 NDK/交叉工具链（`aarch64-linux-gnu-gcc` 或 ndk 的 clang）；② 拉源码 + 子模块（glslang/yaml-cpp）；③ cmake 指定工具链文件：`cmake -DCMAKE_TOOLCHAIN_FILE=$NDK/build/cmake/android.toolchain.cmake -DANDROID_ABI=arm64-v8a -Dncnn_VULKAN=OFF -Dncnn_BUILD_TOOLS=ON -DNCNN_SIMPLEOCV=ON ..`（Linux 板卡则 `-DCMAKE_C_COMPILER=aarch64-linux-gnu-gcc`）；④ `make -j && make install` 得到 `libncnn.a` + include；⑤ 用 ncnnoptimize 转模型（onnx→ncnn：onnx2ncnn 或 pnnx，量化 int8：ncnn2int8 + 校准表 imfind）；⑥ 目标板上 adb/scp 部署，`NDK_STACK`/addr2line 解栈。要点：选项按板子裁剪（Vulkan/GPU、simpleocv 免 opencv 依赖、LTO）、静态库省部署。

**源码了解点**（按层次答）：① **layer 体系**：所有算子继承 `Layer`（虚函数 forward），注册表 `DEFINE_LAYER_CREATOR` + `layer_type` 枚举，`net.load_param` 按字符串名实例化——对应 Q12/Q35 的注册模式；② **blob 内存**：`Mat` 引用计数 + 通道打包（C 方向对齐 8/16，为 NEON pack 做准备）；③ **CPU 后端**：每层的 arm 实现（arm64 neon 汇编微内核，conv 4×8/6×16 tile）与 x86（avx2）版本；④ Vulkan 后端：SPV shader；⑤ 图优化：`ncnnoptimize` 做 fusion（conv+bn+relu、conv+pooling）与 fp16 存储；⑥ 推理流程：load_param/load_bin → extractor → forward（blob 按名取）。说明白"层注册 + Mat 内存 + NEON 内核"三层即可过关。

### Q38. 为什么选 RK3588？环境搭建与模型部署的完整流程（小厂实4 Q5）

**选型理由**（答成本/生态/算力三角）：端侧 SoC 里 8nm 工艺、6 TOPS NPU（三核 RKNN）、4×A76+4×A55 CPU、8K 视频编解码、LPDDR4x 带宽够跑中型检测模型；Rockchip 生态（rknn-toolkit2/rknn-llm）相对成熟、社区大、价格低于 Jetson——适合多路视频结构化的成本敏感项目（若答"为什么不用 Jetson"：Orin 贵，功耗预算 10-15W vs 30-60W；RKNN 算子覆盖差些但 CV 检测够用）。

**流程**：① 板卡烧固件（USB/-maskrom 刷 Debian/Ubuntu for RK），装 rknn 运行时（librknnrt.so）；② x86 主机装 rknn-toolkit2（模型转换/量化工具链在 PC 上）；③ 模型训练（PyTorch）→ 导 ONNX（opset 匹配、简化 onnxsim）；④ `rknn.config`（mean/std、量化类型 i8/i16、目标平台 rk3588）→ `rknn.build(do_quantization=True, dataset='calib_list.txt')`（校准图片列表）→ `rknn.export_rknn`；⑤ 板上 C/Python API：`rknn_init` 加载 → NPU zero-copy 输入（`rknn_create_tensor`）→ run → 解码后处理（NEON 加速 NMS）；⑥ 精度对拍（mAP 衰减 <1% 目标）+ 性能（每核 TOPS 利用、多核绑定跑多路）；⑦ 常见坑：不支持算子替换（SiLU→HardSwish）、量化掉点回 i16 或混合量化、多线程 init 竞态。端侧 LLM 场景对应 rknn-llm（int4 量化 + CPU/NPU 混合执行）。
