## 一、蚂蚁

### Q1. 如何判断一个算子是否需要优化？（蚁实1 基础 1）

三步：**①热点**：整网 profiling（torch profiler / 自研 timing / Nsight Systems）按总耗时排序，只动 top（Amdahl：优化 1% 时间的算子再快 10× 总收益 <0.1%）；**②瓶颈类型**：实测耗时 vs Roofline 理论值——算术强度 (FLOPs/Bytes) 与机器平衡点 (FLOPS/BW) 比较，低于平衡点是访存受限、高于则是算力受限；再排除第三类：launch/调度开销（kernel 很短但数量多，看 profiler 里 gap 占比）；**③性价比**：优化空间 = 理论下界/实测（如 3× 以上值得做），还要看调用频次与形状分布（固定 shape 值得特化，动态 shape 要走库或模板）。判断"不需要优化"同样重要：已达理论带宽 85%+ 或占比过低的算子直接跳过。详见 [03 GEMM 与算子优化](./03-gemm与算子优化.md) Q1/Q4。

### Q2. 面对未量化的模型，如何系统地推进量化？（蚁实1 基础 2）

工程流程题，按阶段答：

1. **模型结构分析**：扫全部算子类型与占比（transformer 层 = 大量 GEMM + norm/rope/softmax），标出不能量化的（embedding/lm_head 常保留高精度、层间 residual 等）；
2. **部署目标确定**：显存上限/带宽目标/精度红线（ppl 与下游 benchmark 的可接受损失）决定量化位宽与对象：decode 受限选 W4A16，吞吐受限选 W8A8，训练/低延迟选 FP8；
3. **粒度选择**：W8 用 per-channel 即可，W4 必须 per-group(64/128)，激活 per-token（动态）或 per-tensor+SmoothQuant；
4. **校准方式**：按数据可得性选 PTQ（minmax/percentile/KL/MSE 网格；GPTQ/AWQ 需要 128 条左右校准样本）→ 不达标再上 QAT；
5. **迭代验证**：逐层敏感度分析（sensitivity scan：逐层量化看输出误差），敏感层回退混合精度；每一轮同时测精度（ppl→下游任务）与性能（kernel 基准），两个指标共同收敛才收工。

### Q3. AWQ 加了反量化步骤为什么整体仍加速？（蚁实1 基础 3）

同 [06 量化](./06-量化.md) Q2：decode 阶段是**带宽受限**，时间 ≈ 权重读取量/带宽 + 计算。W4 把权重读取量降到 1/4，反量化是寄存器内的位操作（解包 4bit→FP16 与 mma 融合，不写回 HBM），开销远小于省下的访存时间——**省的是 3/4 的显存带宽，花的是少量 ALU 指令**，净收益为正（Marlin 类 kernel 可达 FP16 cuBLAS 的 ~3-4×，batch 小时）。边界条件：batch 很大（计算受限）时收益消失，甚至因解包变慢。

### Q4. 静态图与动态图：为什么融合前要转静态图？转换开销怎么处理？（蚁实1 基础 4）

- 动态图（PyTorch eager）：算子逐个解释执行、python 开销大、图结构运行时才知，**跨算子优化（融合、内存规划、常量折叠）没有全局视野**；
- 静态图（TS/TF/XLA）：先 trace/编译拿到完整图，才能做依赖分析、算子融合、内存复用、kernel 自动生成；
- 转 static 的开销（trace + 编译，秒~分钟级）用**缓存**解决：按模型+形状+版本缓存在磁盘（torch.compile 的 FX graph cache、TRT 的 engine 序列化），生产部署一次编译多次执行；动态形状用 dynamic shape/mark_dynamic 或分桶（bucketing）+ padding 处理。

### Q5. vLLM 推理调度与 KV Cache 管理的核心设计？（蚁实1 基础 5）

调度三层（详见 [05](./05-推理引擎与优化.md) Q2）：**continuous batching**（iteration 级调度，请求随时进出）、**prefix-aware 调度**（优先调度命中 prefix cache 的请求）、**抢占与重算/换出**（KV 满时按策略抢占，swap 或 recompute 恢复）。KV 管理：PagedAttention 分页（block 16 token、物理块按需映射、>90% 利用率）+ prefix cache 的引用计数与 LRU 淘汰。蚂蚁的追问点通常在"多轮会话的显存增长为什么不会无限涨"——因为 block 有 TTL/LRU 淘汰，且 prefix 复用避免重算。

### Q6. 长轮次推理显存异常增长与随机崩溃怎么排查？（蚁实1 项目 6、蚁实2 项目 7）

排障方法论（面试考察的是链路完整性）：

1. **先定界**：显存增长是 KV Cache（随会话线性涨，正常）还是泄漏（fragmentation/未释放 buffer/引擎内部 cache 无淘汰）——开 `--kv-cache-dtype` 统计、对比理论 KV 增长曲线与实际曲线；
2. **碎片**：长时间运行后 allocator 碎片化，表现为"总显存够但分配失败"——PyTorch `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`；block size 与分配粒度对齐；
3. **随机崩溃根因**：常见是并发竞争（多 stream 读写同一 buffer 无同步）、越界（变长序列 padding/offset bug）、精度（fp16 溢出 NaN 触发 assert）——开 compute-sanitizer / CUDA_LAUNCH_BLOCKING 定位；
4. **修复**：给缓存加淘汰上限与 TTL；预分配 + 内存池复用；异步操作加事件同步；回归测试用随机长度长跑（soak test）复现。

### Q7. Timing 插件的底层实现？为什么不用 Nsight/NCU？（蚁实1 项目 7）

自研轻量 timing = **CUDA Event 对**（`cudaEventRecord` 夹住目标区间）+ 可选 `nvtx` range 打标，随推理循环在线输出每算子/每层耗时直方图。不用 NCU/Nsight 的理由：①NCU 会 serial化/重放 kernel，**改变时间行为**（锁频、禁并发），测不出真实并发下的瓶颈；②离线工具不能 7×24 挂在生产链路上，而 timing 插件开销 μs 级可持续运行；③需要业务语义（模型名/请求 id 维度聚合），profiler 只有 kernel 名。方法论：**线上用 event timing 找异常，线下用 Nsight 深挖单点**，两者互补（详见 [08 编译器与性能分析](./08-编译器与性能分析.md) Q5）。

### Q8. 不同模型本地部署和量化差异？（蚁实1 项目 8）

差异来自结构：①GQA/MQA/MLA 决定 KV Cache 大小与 attention kernel 选择（MLA 要权重吸收后的 kernel，不能直接用标准 paged attention）；②MoE 模型权重巨大但激活稀疏，量化要考虑 expert 均衡与分组（per-expert scale）、部署要考虑显存放不下需 EP 或 offload；③激活分布：老模型（LLaMA 系）有 systemmatic outlier（SmoothQuant 处理），Qwen 系离群较温和；④小模型（<3B）对量化更敏感（冗余度低），W4 常要 QAT 兜底；⑤非 LLM（CV/DiT）多为 conv/normalization 为主，量化走 TensorRT 生态而不是 GPTQ/AWQ。

### Q9. 图优化的选取策略与开发流程？（蚁实1 项目 9、蚁实2 项目 8）

选取（与 Q13 融合判据同源）：频次 × 收益 - 开发成本。优先做**通用模式**（横向融合的 elementwise 链、norm+act、gemm+bias+act）与**业务高频子图**（如 decode 的 add+norm+rope）。流程：profiling 找 top 子图 → 在 IR 上写 pattern（匹配-替换 pass）→ 数值对拍（融合前后输出 atol/rtl 一致）→ 性能回归（不许变慢，见 [03](./03-gemm与算子优化.md) Q7 融合变慢的坑）→ 灰度上线。静态图里筛选融合组合：从 DAG 做拓扑序，对每个节点检查"单生产者-单消费者、无外部引用、无副作用"，满足则候选融合，再按形状/数据类型估计收益排序。

### Q10. W8A8 与 W4A16？为什么 4-bit 权重时激活还要高精度？（蚁实2 基础 1）

符号：W8A8 = 权重与激活都 INT8（计算也 INT8，吃 Tensor Core 整数算力翻倍），W4A16 = 权重 INT4、激活与计算 FP16（weight-only）。激活必须保高精度的原因：①**激活有离群通道**（LLM 的 systematic outlier，可到权重几十倍），低比特表示动态范围不够；②量化误差直接进入后续每一层的计算并被放大，而权重量化误差相当于给固定的矩阵加小噪声、可被校准吸收；③W4A16 的收益本来就来自权重读取（decode 带宽受限），激活量化不解决瓶颈。反过来 W8A8 用于大 batch prefill（计算受限）时才划算。详见 [06 量化](./06-量化.md) Q1。

### Q11. 均匀量化与非均匀量化？（蚁实2 基础 2）

- **均匀**：量化步长一致（$x_q = round(x/s)+z$），整数运算/硬件 GEMM 直接支持、scale/zero 只需每组 2 个数——工程主流；
- **非均匀**（如 NF4、对数量化、kmeans 码本）：每个量化电平独立间距，同样的比特数能更好拟合分布（钟形权重分布用非均匀电平更省误差，QLoRA 的 NF4 以 4bit 拟合到接近 fp16 的训练效果）；
- **代价**：①计算复杂——查表（LUT）而不是移位乘加，无法直接进整数 mma，需要先反量化；②存储/传输 scale 表（每电平一个映射）；③硬件加速适配差（Tensor Core 只吃均匀整数/FP8），通常只在 weight-only + 反量化融合 kernel 里可用。

### Q12. 推理链路性能瓶颈如何分析？优化后仍有差距，差距来自哪？（蚁实2 基础 3）

分层定位（自上而下）：请求级（排队、调度、批组装）→ 模型级（每 step 耗时分布：prefill/decode、attention vs GEMM 占比）→ kernel 级（带宽利用率 vs 算力利用率）→ 系统级（CPU-GPU 同步、内存拷贝、多卡通信）。**最有效手段**按统计规律：decode 场景 80% 的情况是 KV/权重带宽——量化 + paged KV + CUDA Graph 三件套；prefill 则是 attention 计算与 batch 组装。剩余差距来源：①理论带宽达不到（实际只有 spec 的 70-85%）；②调度空泡（batch 不满、请求到达不均匀）；③kernel 长尾（非热点但数量多）；④框架 overhead（python 前处理、采样、tokenizer 在 CPU 侧）；⑤通信与多卡负载不均。这一问要能说出"我用 A 指标确认了 B 层是瓶颈，做了 C，之后 D 指标从 x 到 y"的完整闭环。

### Q13. 算子融合的判断标准？（蚁实2 基础 4）

融合有收益的判据（详见 [03](./03-gemm与算子优化.md) Q6）：①**访存占比高、计算轻**的算子链（elementwise/norm/act）：融合省的是中间 tensor 的 HBM 读写；②**单生产者-单消费者**且中间结果无外部引用；③**高频出现**（每层都有的模式，一次优化全网收益）；④形状友好（融合后 kernel 的 tile 划分仍能吃满 SM）。不适合融合：中间结果被多分支引用、融合后寄存器/smem 压力导致 occupancy 掉、动态 shape 导致每形状都要特化编译。频次 × 每次节省 = 总收益，减去开发与编译成本再做决策。

### Q14. 性能 profiling 重点看哪些指标？（蚁实2 基础 5）

- **总时间拆分**：kernel 时间 / gap（launch、同步）/ 通信 / CPU 段各占多少；
- kernel 内部（NCU）：**带宽利用率**（DRAM Throughput % 与理论值比）、算力利用率（SM %）、**warp divergence**（活跃线程占比，分支导致的串行化）、occupancy、L1/L2 命中率、smem bank conflict；
- 多流/并发场景：**流水线效率**（各流 busy 重叠度、事件时间线的空泡）、拷贝与计算的 overlap；
- 稳定性：多次运行的方差（时钟浮动、邻居干扰），取 p50/min。
见 [08](./08-编译器与性能分析.md) Q5。

### Q15. 单算子优化：手写替换为高性能库怎么落地与测试？（蚁实2 项目 6）

落地：确定接口语义（dtype/布局/shape 集）→ 候选库（cuBLASLt/cutlass/TensorRT/自研）按 shape 拐点做**自动选择表**（小 shape 用 A 大 shape 用 B）→ fallback 保底（原实现）。测试三层：①**单测对拍**：与参考实现在随机/边界 shape（1、奇数、超大 K）上 atol/rtol 一致 + 确定性（同输入同输出）；②**性能回归**：基准 shape 集不劣化超过阈值；③**整网测试**：端到端输出误差在累计容忍内（逐层误差会叠加，单算子 atol 要按整网预算倒推）、吞吐/延迟指标不回退。

### Q16. CUDA Histogram：朴素原子的问题与 smem 私有化（蚁实2 编程 9）

同 [02 CUDA 编程题](./02-cuda-编程题.md) Q5：全局原子在 bucket 少、冲突率高时串行化严重（本例 0-9 共 10 桶，256 线程几乎每次原子都冲突）。优化：每个 block 在 smem 里建**私有直方图**（block 内先原子累加到 smem——同 block 内 smem 原子冲突远小于全局，且可配 bank 无冲突布局），block 结束一次性原子加到全局。3090 实测 19.9× 加速（`solutions/cuda/src/histogram_scan.cu`，`ctest` 可复现）。进阶：多 smem 副本进一步降冲突、聚合（warp 内先 reduce 同值）。

### Q17. INT8/FP8 方案与 FP8 两种格式、训练推理适用差异（蚁三 基础 1）

见 [06 量化](./06-量化.md) Q5：**E4M3**（4 指数 3 尾数，范围 ±448，精度高）→ 权重与前向激活；**E5M2**（范围大、精度低）→ 梯度。训练用 FP8 需要 delayed scaling（amax 滑动窗口）+ per-tensor scale 管理（Transformer Engine）；推理上 FP8 几乎无损且有 Hopper FP8 Tensor Core 加速。INT8 训练基本不用（反量化误差在梯度上不稳定），推理上 INT8 W8A8 依赖 SmoothQuant 类离群迁移。回答时补充：A100 无 FP8 硬件、H100 起（1979 TFLOPS dense）、Blackwell 是 FP4。

### Q18. KV Cache 大小如何计算？（蚁三 基础 2、华实2 训练 2）

$$\text{KV bytes} = 2 \times L \times H_{kv} \times d_{head} \times b_{dtype} \times B \times S$$

（2=K 与 V；GQA 下 $H_{kv}$ 是 KV 头数）。代码 `answers/t1/memory_model.py::kv_cache_bytes`，例：Qwen3-8B（36 层 × 8 KV 头 × 128 维）单请求 8K 上下文 BF16 = 603 MB；LLaMA-2-7B 单请求 4096 token = 2 GiB。追问方向：KV 量化（FP8 减半）、MLA（每层只存 latent 576 元素/token）、并发反解（`fit_max_concurrent_requests`：24GB 卡 4096 上下文 ≈ 11 并发，KV FP8 翻倍到 22）——都有 pytest 覆盖。

### Q19. 大模型推理为什么需要 KV Cache？本质作用？（蚁三 基础 3）

自回归生成每步的 attention 要读全部历史 token 的 K/V。**K/V 对历史 token 是不变的**（causal attention 下新 query 才扩展），缓存后每步只算新 token 的 QKV 投影，把每步 attention 计算从 $O(L^2 d)$ 降到 $O(Ld)$、总生成从 $O(L^3)$ 降到 $O(L^2)$。本质：**用 O(L) 显存换掉重复计算**，同时把每步的访存模式变成"顺序读一段连续 KV"，是 decode 阶段带宽预算的主要去向（优化见 [04](./04-attention与kvcache.md) Q7）。训练不用它：teacher forcing 下整段并行，K/V 本来只算一次（详见 [60](./60-t1-快手与美团.md) Q11 的训练/推理对比）。

### Q20. 如何理解 Attention？为什么 Attention 量化比权重量化更难？（蚁三 基础 4）

Attention = 按 query-key 相似度对 values 做加权求和：$\mathrm{softmax}(QK^T/\sqrt{d})V$，是**内容寻址的信息路由**（对比 conv/FC 的固定权重）。量化难的根源：

1. **softmax 的指数放大**：pre-softmax logits 的小量化误差经 exp 放大成概率的大偏差，且 logits 范围随序列/训练状态漂移，scale 难校准；
2. **离群值集中在 K 的少数通道**（systemmatic outlier），per-tensor/per-channel 都不够，常要 per-block 或对 QK 分别处理；
3. **误差会被 value 路由扩散**：attention 权重的误差改变了信息的组合方式，比 GEMM 权重噪声的影响更"结构化"；
4. KV Cache 还在**动态增长**，量化 scale 只能静态校准或在线统计。
实践：KV FP8 近无损；INT4 KV 要非对称 + K 按通道、V 按 token 的 KIVI 式分离；QK^T 计算保持高精度、只量化 KV 存储是折中路线。

### Q21. MLA 相比 MHA 的优势与权重吸收的问题（蚁校 基础 1/2）

优势（见 [04](./04-attention与kvcache.md) Q3 与 [62](./62-t1-小米oppo-vivo-网易等.md) Q2）：KV Cache 每层每 token 只存 $d_{latent} + d_{rope}$（DeepSeek-V3：576 元素，FP8 576B），相当于 **2.25 个 GQA KV 头**（`memory_model.py::mla_equivalent_gqa_heads` 实测换算），比 128 头 MHA 压缩 ~57×；精度接近 MHA（低秩压缩保住主要能量）。

权重吸收（$W_{UQ}, W_{UK}$ 与 $W_{KV}$ 下投影相乘合并，推理时 query 直接与 latent 算）的问题：①**矩阵变得稠密且大**：吸收后 per-head 的投影维数 = $d_{latent}+d_{rope}$，GEMM 形状改变，标准 paged attention kernel 不能直接用，要重写 decode kernel；②**RoPE 位置相关的部分不可吸收**（旋转矩阵逐 token 不同，必须拆出 rope 分量单独处理，这也是 KV 分两段缓存的原因）；③吸收后的矩阵在线计算量略增（decode GEMV 变大），小 batch 下需评估"省的 KV 读带宽 vs 多算的 FLOPs"；④数值上低秩分解+融合的误差累计要重新对拍。

### Q22. KV Cache 离线预计算、卸载与加载（蚁校 基础 3）

- **离线预计算**：对固定语料（长 system prompt、文档库、历史会话）提前跑 prefill 把 KV 序列化落盘，在线直接加载——RAG/多轮场景把 TTFT 的 prefill 时间换成 IO 时间；工程要点：与引擎的 block 布局/精度（可同时量化）一致、版本与模型 hash 绑定、增量追加；
- **低频 KV 的卸载/加载**：分层存储（HBM → 主机内存 → NVMe/对象存储），命中时异步预取 + 与计算重叠（Mooncake 的 KVCache 池就是把它做成全局服务，见 [05](./05-推理引擎与优化.md) Q4）；加载路径用 RDMA/分层 pipeline 摊平带宽差；淘汰策略 LRU + 优先级（付费/活跃会话驻留 HBM）。
- vLLM 对应机制：CPU swap、prefix cache 的磁盘持久化、`--block-size` 与预取窗口。

### Q23. 除上述外还有哪些 KV Cache 优化？（蚁校 基础 4）

按"少存、存密、存好、复用"四类（[04](./04-attention与kvcache.md) Q7 全景）：结构上少存（GQA/MQA、MLA、跨层共享 cross-layer/YOCO）；存密（FP8/INT4 量化、KIVI 离群分离）；存好（PagedAttention 分页、prefix cache）；复用/淘汰（滑窗、H2O/SnapKV 等注意力淘汰、KV 池化压缩）。蚂蚁场景常追问多轮 agent 会话：滑窗+摘要+prefix 混合。

## 二、华为

### Q24. LAMB 优化器原理与特点（华2 训练 1）

Layer-wise Adaptive Rate Scaling（You et al., 2019，为超大 batch 训练设计）：在 Adam/LARS 基础上做**分层信任比**更新：

$$u_t = \phi(\|w^l\|)\cdot\frac{m^l}{\|m^l\|+\epsilon}，\quad w^l \leftarrow w^l - \eta \frac{\|w^l\|}{\|u_t\|} u_t \ \Rightarrow\ \Delta w^l \propto \eta\|w^l\|$$

即每层更新方向是归一化的 m/v，**模长与该层权重范数成正比**——各层更新尺度自动匹配各层尺度，等效学习率与权重范数解耦。特点：①支持**超线性 batch 扩展**（batch 32k 训 BERT、6万+ 训 ResNet 不掉精度），大 batch 下无需精调 lr；②对 lr 和 warmup 相对鲁棒；③代价是每层多算两次范数 + 逐层归一化与分布式实现耦合（分层 reduce）。对比 AdamW：AdamW 更新尺度由 m/√v 逐元素决定，大 batch 小步数下欠拟合，LAMB 用"方向归一 + 按层缩放"解决。优化器家族总览见 [11 深度学习与训练](./11-深度学习与训练.md) Q14。

### Q25. 增大 batch size 时学习率如何调整？模型很大但 batch 不变呢？（华2 训练 2）

- **线性缩放规则**（Goyal et al.）：lr ∝ batch size（梯度方差不变的要求：大 batch 梯度均值方差 ~1/k，等效步长不变需 lr×k；实践中常用 sqrt 缩放置信度不足时）；需配合 warmup（前几个 epoch 从小 lr 线性升，避免初期发散）；
- **模型变大、batch 不变**：大模型本身梯度噪声更小、损失面更平滑，**lr 通常随模型增大而下调**（经验：参数量 ×4 → lr 减半量级），并保持 warmup + cosine/倒数平方衰减；Muon/类正交优化器时代按谱归一，敏感度不同（见 [07](./07-分布式训练.md) Q7）；
- 本质：lr 的安全上界由"梯度噪声比 + 损失面曲率"决定，batch 影响噪声项、模型规模影响曲率项。

### Q26. 并行切分策略总览（华2 训练 3、华实2 训练 5 部分）

| 维度 | 切什么 | 通信原语 | 频率 | 适合 |
|---|---|---|---|---|
| DP/ZeRO | 数据 | AllReduce/RS+AG | 每 step | 一切场景的基底 |
| TP | 层内权重矩阵 | AllReduce ×2/层 | 每层 fwd+bwd | NVLink 域内（≤8卡） |
| SP | 序列维（LN 等激活） | RS+AG 替代 AR | 每层 | 与 TP 配套压激活 |
| PP | 层间（按 depth） | point-to-point | 每 micro-batch | 跨机扩展深网络 |
| EP | 专家 | All-to-All | MoE 层 | MoE 模型 |
| CP | 长序列 | 环形 KV 交换 | attention 层 | 超长上下文 |

选择顺序：先 DP 吃满单机 → TP 压单卡放不下的层 → PP/EP 跨机 → CP 长序列。详见 [07](./07-分布式训练.md) Q4/Q5 与 Q30 的 3D 并行。

### Q27. ZeRO 各阶段与 P 卡显存分配推导（华2 训练 4、华实2 训练 5）

见 [07](./07-分布式训练.md) Q3。华为追问"ZeRO-1 如何在 P 卡分配"：参数量 N、FP16 混合精度（Adam FP32 m/v + FP32 master 12N、FP16 梯度 2N、FP16 参数 2N，共 16N）：

- ZeRO-1：**优化器状态按 P 卡均分**——每卡持 $12N/P$（自己负责的参数分片）+ 完整梯度 2N + 完整参数 2N = $4N + 12N/P$；更新时每卡只更新分片，再用 AG 广播（或保持 RS 后的桶式同步）；
- ZeRO-2：梯度也分片 $2N/P$（RS 直出分片，省掉 AG）→ $2N + 14N/P$；
- ZeRO-3：参数分片 $2N/P$，前向每层用前 AG 临时聚合 → $16N/P$。
- FP32 vs FP16 影响：参数/梯度 FP16 减半，但**混合精度训练的优化器状态仍是 FP32**（数值稳定），所以 16N 里 12N 是 FP32；纯 FP32 训练则参数 4N+梯度 4N+状态 8N=16N，两者总账相同、分布不同。

### Q28. PP 下每卡显存/计算量是否相同？激活分布？（华2 训练 5）

不同。①**计算量**：各 stage 层数相同时计算量近似相等（每卡跑完整 micro-batch 的自己那段），但第一/末 stage 各少一次通信侧计算（首无输入梯度、末无反向传播起点），实际最后一 stage 最重（反向起点+损失计算）；②**显存**：权重/优化器状态各卡只存自己层（可均分）；**激活显存按 stage 位置递增再递减**——1F1B 调度下第 j 个 stage 最多驻留 $p-j$ 个 micro-batch 的激活（首卡最多、末卡最少，模拟器 `zero_bubble.py` 的 `peak_activations=[p, p-1, ..., 1]` 可验证），不均衡时用 **virtual pipeline stage（VPP，stage 交错拆两段）** 或 cap 重排缓解；③Zero-Bubble 调度显存分布另见 [60](./60-t1-快手与美团.md) Q39。

### Q29. 3D 并行的组合方式与适用场景（华2 训练 6，重点）

$DP \times TP \times PP$（再加 EP/CP 是 4D/5D）。**组合的黄金法则：TP 在机内（NVLink），PP 跨机（点对点通信量小），DP 在最外层**。以 64 卡训 175B 为例（Megatron 论文口径）：TP=8（单机 8 卡 NVLink，每层 2 次 AllReduce 吃 900GB/s），PP=8（8 台机器串 8 个 stage，每 micro-batch 只传边界激活，通信量最小、对跨机带宽最不敏感），DP=1→外层再扩数据副本。

- 为什么 TP 不跨机：TP 通信量 = 每层 2×AllReduce(激活)，频率太高，跨机 IB（~50-400Gbps）会成为硬瓶颈；
- 为什么 PP 跨机好：PP 只传 stage 边界激活（隐藏维 × batch），micro-batch 流水起来后通信被计算掩盖；
- DP 放最外层：梯度同步每 step 一次，可用大桶+分层 AllReduce 优化；
- 调度细节：micro-batch 数 m ≥ 4×p 压气泡、1F1B 保激活、interleaved/VPP 压显存不均；加上 ZeRO-1（优化器按 DP 组分片）进一步省显存。
- 场景对应：单机放不下但 8 卡 NVLink 能放下一个 TP 组 → TP8+PP；模型大到要跨机 → TP8×PPn；数据量巨大模型中等 → DP 为主 + ZeRO；MoE 加 EP（All-to-All 要 NVLink 域内 dispatch）。

### Q30. DCU 与华为昇腾（NPU）的架构/生态/通信库差异（华2 HPC 7）

- **DCU**（海光/AMD 系）：GPU-like 架构（GCN/CDNA 血统），栈接近 ROCm/HIP——CUDA 代码可用 HIP 工具迁移；生态有 ROCm 的 hipBLAS/RCCL 对应 cuBLAS/NCCL；
- **昇腾 NPU**（达芬奇架构）：AI Core 由 Cube（矩阵）+ Vector + Scalar 组成，AI Cube 原生 int8/fp16 矩阵单元；软件栈 CANN（对标 CUDA）：ACL 接口 + 图引擎（GE）+ 算子库（AscendCL/ATC 转换模型）+ **HCCL** 集合通信库（对应 NCCL 原语，支持对等通信 HCCP）；编程模型是 Ascend C / TBE（算子用 Python/DSL 写，走 AI Compiler 编排）而非 SIMT CUDA C；
- 差异总结：DCU = "兼容 CUDA 生态的类 GPU"；NPU = "编译器/图驱动的专用 AI 架构"，算子开发范式（SIMT kernel vs 纯结构化算子）、内存模型（NPU 显式多级 buffer）、通信库（RCCL vs HCCL）都不同；迁移工作量主要在自定义算子与性能调优层。

### Q31. DDP 与 DeepSpeed 的异步保存（checkpoint）机制（华2 HPC 8）

- **DDP（PyTorch）同步保存**：rank0（或所有 rank 各存分片）`torch.save`——大模型下全卡停训、rank0 聚合 100+GB，分钟级停顿；
- **异步保存思路**：①先把参数/优化器状态**移到 CPU/NVMe（后台线程 DMA 拷贝）再序列化**，GPU 立刻恢复训练；②各 rank 并行写自己的分片（ZeRO 下天然分片，各存各的），元数据由 rank0 统一记录；③与 step 解耦：在 N+i 步保存 N 步的状态需要短暂停顿或版本化 buffer；
- **DeepSpeed**：`async_save` 支持参数搬 CPU 后异步落盘；ZeRO-3 下每 rank 存本地分片（load 时再聚合）；配合 `universal checkpoint`（分片格式互通）；恢复时惰性加载（load 分片到对应卡）。
- 要点：一致性（step 对齐、优化器状态与参数同版本）、断点续训精度（RNG/dataloader 状态也要存）、失败恢复演练。

### Q32. T5 与 GPT-2 架构差异（华2 基础 11）

| | GPT-2 | T5 |
|---|---|---|
| 结构 | decoder-only | encoder-decoder |
| attention | causal self-attn | enc 双向 + dec causal + **cross-attn** |
| 归一化 | LayerNorm（GPT-2 用 pre-LN，置于残差分支前） | 简化 LayerNorm（去 bias、去均值中心的简化版，T5 论文式样） |
| 位置编码 | 学习式绝对位置 | **相对位置 bias**（桶化相对距离查表，每层共享） |
| 激活 | GELU | ReLU |
| 目标 | 语言建模（next token） | span corruption 去噪（mask span 预测） |
| 缩放 | 深度堆叠 | 缩放维度/深度/ffn 与 dropout 系列（t5-small~xxl） |

高频考点：T5 的相对位置编码让其可迁移到不同长度任务、encoder-decoder 对翻译/摘要类 seq2seq 的优势；GPT-2 的 decoder-only + next-token 是现代 LLM 的直系祖先。

### Q33. Transformer 整体结构与残差作用（华2 基础 12/13）

结构：输入 embedding（+位置）→ L × [pre-LN → 自注意（QKV 投影→缩放点积→投影）残差 → pre-LN → FFN（升维 4×→非线性→降维）残差] → 最终 LN → lm_head。残差连接作用：①**梯度高速路**（恒等映射让深网梯度不消失，等价于学习残差增量 F(x)=H(x)-x，优化更易）；②**隐式集成**（各层可跳过的 ensemble 效应）；③与 LN 配合（pre-LN）让千层网络可训；④从信息论看保留原始信息逐层精炼。详细见 [04](./04-attention与kvcache.md) 与 [11](./11-深度学习与训练.md)。

### Q34. 部署与推理的参数量/显存估算（华实2 推理 1）

权重显存 = 参数量 × 字节（FP16 2B、INT8 1B、INT4 0.5B）+ KV Cache + 运行时余量。代码 `answers/t1/memory_model.py::inference_memory_report`：Qwen3-8B BF16 = 权重 15.3GB + KV（8K×1 并发）0.6GB + 激活/引擎 ~2.5GB ≈ **18.4GB**（24GB 卡可部署，11 并发@4K）；INT4 权重后总 ~10.4GB，单卡并发翻倍。估算题的答法：分项列公式 → 代入配置 → 给余量说明（CUDA Graph、TP 通信缓冲）。

### Q35. Prefill vs Decoding 与 Temperature/Top-k/Top-p（华实2 推理 2/3/4）

- Prefill/Decode 差异与 KV 计算：[05](./05-推理引擎与优化.md) Q1 + 本篇 Q18；
- **Temperature 数学原理**：对 logits 除 T 再 softmax——$p_i \propto \exp(z_i/T)$。T→0 退化为 argmax（贪心），T=1 原分布，T>1 拉平（熵增大、更随机）。本质是**重新参数化分布的集中度**（对 Gibbs 分布的逆温度），等价于在 log 域缩放分布的"锐度"；
- **作用顺序**：logits →（repeat penalty 等可选）→ **Temperature 缩放** → **Top-k 截断**（保留 k 个最大）→ **Top-p 截断**（按累积概率保留）→ 从剩余分布采样。先温度再截断：温度改变排序不变但改变累积概率，工程上均如此（vLLM/HF）；top-k 与 top-p 同时给时取交集。

### Q36. 4 卡如何分布式计算 A×B（华实2 训练 6）

按切分维度推导（与 [07](./07-分布式训练.md) Q4 同源）：

- **行切 A（A=[A1;A2] 按行 2 份）× 列切 B（B=[B1,B2]）**：C 的 (i,j) 块 = Ai×Bj，4 卡各算一块，无通信直接得到分块结果（适合后续 AllGather 拼接）——"行×列"组合零冗余零通信；
- **A 列切 × B 行切**（2×2）：Ci = Σ A_i×B_i 部分和，需 **AllReduce/ReduceScatter** 求和；
- 显存视角：每卡只存 A/4 + B/4；大 K 时部分和累加可流水（RS 分桶）。
- 面试加分：指出 transformer TP 用的就是这个——QKV 投影列切（输出拼接）、FFN 第二层行切（部分和 AllReduce），见 [60](./60-t1-快手与美团.md) Q3。

### Q37. 通信算子/集合通信原语（华实2 HPC 7）

Broadcast / Scatter / Gather / Reduce / **AllReduce**（DP 梯度同步）/ **ReduceScatter**（ZeRO-2 梯度分片）/ **AllGather**（ZeRO-3 参数聚合）/ **All-to-All**（EP dispatch/combine、序列重排）/ Send-Recv（PP）。语义、Ring 实现与通信量推导见 [07](./07-分布式训练.md) Q1/Q2。

### Q38. Qwen 系列架构与训练方法（京东实 基础 1）

架构（以 Qwen2/2.5/3 为主线）：decoder-only + **GQA**（32 Q 头配 8 KV 头）+ **RMSNorm + pre-NLN**（Qwen3 norm 化 QK）、**SwiGLU** FFN、**RoPE**（Qwen3 长上下文用 YaRN 外推 + 双 chunk 注意力 DCA 可选）、QKV bias（Qwen2 起仅 Q bias 省参数）、词表 ~152K（多语）、tie embedding（小模型）、Qwen3 引入 **QK-Norm、无 bias 的 GQA、思考/非思考双模式（thinking mode 由 <think> 标记）**、MoE 版本（Qwen3-30B-A3B 等，细粒度专家+共享专家）。训练三阶段：pretrain（~36T tokens 多语/代码/数学）→ post-train：SFT（长 CoT 数据合成 + 普通指令混合）→ **RL**（GRPO 为主，数学/代码/通用推理分难度课程式训练 + 强度可调的 thinking budget）。答题框架："结构上与 LLaMA 同源，差异点是 GQA 配比、RoPE 细节与 QK-Norm；训练是 pretrain→SFT→RL 三段，Qwen3 特色是混合推理模式与大规模 GRPO"。

### Q39. PPO / DPO / GRPO 的区别（京东实 基础 2，重点）

代码：`answers/t1/rl_basics.py`（三个 loss 都有 pytest 对拍）。

| | PPO | DPO | GRPO |
|---|---|---|---|
| 框架 | actor+critic，on-policy RL | 离线偏好优化，免 RL | on-policy RL，无 critic |
| 优势 A | GAE(λ)：$\delta_t = r + \gamma V(s') - V(s)$，$A_t=\Sigma(\gamma\lambda)^l\delta$ | 隐式（偏好对的奖励差） | **组内对比**：同 prompt 采 G 条，$A_i = (r_i - \bar r)/\mathrm{std}$ |
| 目标 | $\min(rA, \mathrm{clip}(r,1\pm\epsilon)A)$ | $-\log\sigma(\beta(\Delta\pi_w - \Delta\pi_l))$ | PPO 式裁剪 + KL(k3) 直接进 loss |
| 资源 | 4 模型（actor/critic/ref/reward） | 2 模型（policy/ref） | 3 模型（policy/ref/reward），省 critic 显存一半量级 |
| 敏感度 | 超参多、易不稳 | 稳但上限受偏好数据约束 | 中等，G 要够大（8-64） |
| 适用 | 通用 RL，游戏/机器人 | 偏好对齐、快速迭代 | LLM 推理 RL（DeepSeek-R1 路线） |

DPO 推导要点：reward 最优解代入 KL 约束可得 $r^* = \beta\log\pi/\pi_{ref}$，偏好概率 $p(w\succ l)=\sigma(r_w-r_l)$ → 直接变成 policy 的损失。GRPO 的组基线把"绝对 reward 好坏"转成"组内相对好坏"，天然适合可验证任务（数学/代码对了没）。

### Q40. 熵、交叉熵与 KL 的联系（京东实 基础 3）

$$H(p,q) = H(p) + \mathrm{KL}(p\|q) \geq H(p)$$

交叉熵 = 自信息期望 + 分布差异；KL ≥ 0（Gibbs 不等式）且不对称（距离的平方项不满足，是"方向性散度"）。语言模型训练 = 最小化 $H(p_{data}, q_\theta)$（one-hot 下等于 NLL）；RL 阶段的 KL 惩罚（π vs ref）防 reward hacking 漂移。GRPO 用 k3 估计器（$0.5\log^2 r - \log r$）逐 token 无偏估计 KL，避免全词表 softmax。代码：`rl_basics.py` 的 `shannon_entropy/cross_entropy/kl_divergence` + 恒等式测试 `test_entropy_ce_kl_identity`。

### Q41. 分类为什么不用 MSE？（京东实 基础 4）

①**梯度消失**：sigmoid+MSE 对 logit 的梯度含 $\sigma'(z)=\sigma(1-\sigma)$，错得越自信越饱和（$z=-10, y=1$ 时梯度 ~4.5e-5，而 CE 梯度 $=\sigma(z)-y\approx-1$，见 `mse_vs_ce_gradient_demo` 的对拍数据）；②**概率语义错位**：MSE 假设高斯噪声（回归），类别是离散分布，匹配的似然是 multinomial → CE；③CE + softmax 得到残差形式的简洁梯度（$p - y$），优化面更对称。代码与实测断言见 `rl_basics.py`。

### Q42. DeepSpeed / DDP / FlashAttention 核心功能（京东实 训练 5）

DDP：数据并行的梯度桶化 AllReduce（overlap 计算）+ no_sync 梯度累积；DeepSpeed：ZeRO 1/2/3 + offload + 混合精度 + PP + MoE + activation checkpointing（[07](./07-分布式训练.md) Q12）；FlashAttention：分块 online softmax 的精确 attention，IO-aware 把 HBM 读写从 $O(S^2)$ 降到 $O(S)$、显存常数级（[04](./04-attention与kvcache.md) Q1）。

### Q43. PPO 的 Advantage 与 Critic 更新（京东实 训练 6）

Advantage 用 GAE(λ)（`compute_gae`）：$\delta_t$ 是 TD 误差，$A^\lambda$ 在 bias（λ=0 只有单步 TD）与 variance（λ=1 蒙特卡洛高方差）间插值，λ≈0.95 常用。Critic 更新：**回归 returns** $R_t = A_t + V(s_t)$，MSE 损失（`critic_loss`），配 value function clipping（限制 V 的单步变化）与 GAE 的 stop-gradient。训练细节：actor 与 critic 可共骨干分层头（LLM RL 里常是两个独立模型）、critic 要预热否则初期 A 噪声大。

### Q44. Qwen3-8B 推理显存估算（京东实 推理 7）

见 Q34：`inference_memory_report(QWEN3_8B)` 给出 BF16 权重 15.26GB + KV 603MB@8K + 引擎/激活余量 ≈ **18-19GB**；W4 量化 ~10.4GB、A100-80G 单卡 4K 上下文可跑 ~110 并发（`fit_max_concurrent_requests`）。答这类题把"权重/KV/激活/引擎开销"四项分开列再谈量化与批大小敏感性，就超过大多数人。

### Q45. RAG 流程与优化（京东实 推理 8）

流程：query 理解（改写/扩写/HyDE）→ 检索（embedding 召回 + BM25 混合 → rerank 重排）→ 上下文组装（分块策略、去重、压缩）→ 生成（引用约束）→ 后处理。优化：①**检索侧**：混合检索+RRF 融合、嵌入式 rerank（bge-reranker）、分块用语义/父子块、元数据过滤、图谱增强；②**生成侧**：lost-in-the-middle 对策（重排上下文顺序、relevant 置首）、上下文压缩（map-reduce 摘要）、引用溯源减少幻觉；③**系统侧**：向量库 ANN 参数（HNSW ef）、KV/prefix 复用（文档 KV 预计算，见本篇 Q22 的离线 KV）、缓存热点 query；④评测：召回率/MRR + 端到端忠实度（faithfulness）双链路。

### Q46. 奖励函数设计与 GRPO 冷启动（京东实 实习 9）

奖励设计（RLHF/GRPO for LLM）：①**可验证奖励**（ORM→PRM 的过程演进；数学等值判断、代码单测通过率、格式合规）——稀疏但可靠；②**模型奖励**（reward model 偏好打分）——稠密但有 reward hacking 风险，需要 KL 约束；③**混合**：结果奖励为主 + 格式/长度软约束 + 过程奖励辅助；④课程：难度分层采样（能做对 30-70% 的题学信号最足）。冷启动（GRPO 前的必要阶段）：SFT on 长 CoT 数据（蒸馏强模型推理链）教会基础格式与推理模式，否则 RL 初期组内全对/全错 → advantage 全 0（`test_grpo_group_advantage` 里全相同奖励的组零梯度），训练无法启动；随后小 lr、高 entropy bonus 防过早坍缩，逐步放开难度。

### Q48. PD 分离中调度队列如何实现？（京校 推理 4，重点）

分离式部署（DistServe/Mooncake/vLLM disaggregated）的核心数据结构：**全局请求路由器 + 两个独立池各自的就绪队列**：

1. **入口路由**：请求进入全局队列，路由器按 SLO（TTFT/TPOT 目标）与两池负载（队列深度、KV 水位）决策——goodput 最大化（在 SLO 内的吞吐）而非简单负载均衡；
2. **Prefill 池**：就绪队列按到达序/最短处理时间优先，产出 KV；完成后把 KV **分块传输**到分配的 decode 实例（传输与后续 prefill 重叠），登记 transfer 完成事件；
3. **Decode 池**：维护"等待 KV 到达"的 staging 队列 + 运行队列；KV 齐全才进入 continuous batching 的运行环；
4. **迁移与故障**：decode 实例掉线 → 请求回退 prefill 队列重算（或从 KV 池恢复）；负载迁移 = KV 复制 + 版本切换；
5. 实现细节：队列用 lock-free MPSC；两池间心跳与配额（防 decode 排队导致 prefill 空转）；KV 传输走 RDMA 零拷贝（Mooncake 的 transfer engine）。

### Q49. Chunked Prefill 的语义辨析（京校 推理 5）

指**不同请求之间**的插入：把长 prompt 切成 chunk，与**其他请求的 decode step** 混在一个 batch 里调度，不是同一请求自己的 prefill/decode 交叉（同一请求必须 prefill 完才能开始 decode）。动机与实现见 [05](./05-推理引擎与优化.md) Q3：避免长 prefill 的长 kernel 让同批 decode 的 TPOT 抖动，TTFT 略降换整体 SLO 平滑。此题是概念精确性考核，答错方向（说成同请求交叉）即扣分。

### Q50. C++ 多态与虚函数机制（京校 基础 6/7）

编译期多态（重载/模板）vs 运行期多态（虚函数）。虚函数机制：**每个多态类一张 vtable**（虚函数地址数组，按**基类声明顺序**排列——这是由 Itanium ABI 规定的：基类先声明的虚函数槽位靠前，派生类 override 填同一槽，新增虚函数追加尾部；多继承/虚继承有 offset-to-top 与多张表）；对象头部藏 **vptr**（构造时由最底层派生类设置），调用 `p->f()` 编译为 `(*(p->vptr)[slot])(p)`——两次间接寻址。代价：间接跳转（分支预测）、无法内联、对象 +8B。详见 [09 C++ 与系统基础](./09-cpp与系统基础.md) Q8（含虚析构、构造期虚调用等高频追问）。
