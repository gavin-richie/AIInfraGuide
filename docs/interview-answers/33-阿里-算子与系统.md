## 一、Kernel 与算子优化

### Q1. Hopper Warp Specialization 的机制原理与底层实现（AI-Infra-1 Q8）

详见《GEMM 与算子优化》Q8。要点复述 + 底层实现补充：

- **机制**：block 内 warp 分角色——producer warp 专职 TMA 异步装载（`cp.async.bulk.tensor` 全局→smem），consumer warp 专职 mma 计算，经 **mbarrier**（mbarrier.arrive / mbarrier.try_wait.parity）同步，smem tile 多缓冲轮转；
- **底层实现细节（阿里追问的"底层"）**：①TMA 是**独立 DMA 引擎**（不经 SM 的 LSU），一个 warp 发一条 bulk 指令搬整个 tile，描述符（tiled layout 的张量形状/stride）由 host 预构建；②mbarrier 是硬件屏障对象（smem 中 8 字节），支持 expect-tx 事务计数——producer 发起 TMA 时 barrier 关联搬运字节数，DMA 完成自动 arrive，consumer wait 的是"数据真到了"而不是"指令发完了"；③寄存器按 setmaxnreg 动态重分配——producer 少给寄存器（不需要累加器）、consumer 多给，缓解 warp 分化后的占用率失衡；④异步流水线深度 = smem 缓冲数（典型 4-8 级），CPU/GPU 侧的 pipeline 状态机（CUTLASS PipelineAsync）管理 phase 翻转。

### Q2. 去掉 Warp Specialization、只保留 tile 分块与 smem，性能下降反映在哪些维度？（AI-Infra-1 Q4）

《GEMM 与算子优化》Q8 末尾的同款追问。按 ncu 指标维度答（展示会量化）：

1. **访存-计算重叠消失**：同步版所有 warp 先 `__syncthreads()` 等装载完成再计算，装载期间 tensor core 空转——SOL 段 SM%（pipe tensor）下降、出现内存等待 stall（long scoreboard 上升）；
2. **装载占用 ALU/寄存器**：无 TMA 时 cp.async/LDG 由 warp 自己发，地址计算与搬运指令挤占 mma 发射带宽——指令吞吐（inst issued/mma 比例）变差；
3. **屏障粒度变粗**：全 block barrier vs producer-consumer 的 mbarrier，warp 间锁步更紧，尾延迟（最后到达的 warp 拖全体）放大；
4. **寄存器分配变差**：所有 warp 都要同时保活装载缓冲指针 + 累加器，寄存器压力上升 → 占用率下降或溢出 local memory。

典型量级：Hopper GEMM/FA3 去掉 WS 掉 **20-40%**；但如果 kernel 本身 smem 压力小、tile 小（装载占比低），退化可能 <10%——答题要给"取决于访存/计算比"的条件判断。

### Q3. CuTe DSL 或手写 CUDA 做 fusion 的经验；fusion 技术方案倾向；融合后变差的原因（AI-Infra-1 Q5/Q6/Q10）

三题同族，分别见《GEMM 与算子优化》Q5（选型：Triton 迭代快 / CuTe layout 代数 / 手写控制力）、Q6（模板生成 vs 手写的工程判断：先估访存收益再决定投入）、Q7（变差六因：寄存器压力、并行度匹配、向量化损失、smem 超限、divergence、本就非访存瓶颈）。阿里追问的补充：

- CuTe 的实际体感：layout 组合子（`make_tile`/`local_tile`/`partition_fragment`）把 smem staging 与 mma 片段分发写成类型级代码，编译期检查形状——比裸 mma + 手写 swizzle 少一类"index 算错"的 bug，但编译错误信息长、迭代慢于 Triton；
- fusion 的量化决策公式（面试写出来加分）：$\text{收益} \approx \frac{2 \times \text{中间张量字节}}{\text{两 kernel 总耗时}} \Big/ BW$，先算理论省时占比再动手。

### Q5. MLIR 与 TVM 的设计理念及主要差异（AI-Infra-2 Q1）

基础见《编译器与性能分析》Q1（TVM 思想）与 Q2（MLIR 与多面体）。对比框架：

| 维度 | MLIR | TVM |
|---|---|---|
| 定位 | **编译基础设施**（可复用基础设施，供人构建领域编译器） | **端到端深度学习编译栈**（Python 前端→硬件代码） |
| IR 组织 | 多层 **Dialect**（linalg/affine/vector/scf...）+ 渐进 lowering，允许自定义方言嵌进同一系统 | 两级 IR：Relay（图级）+ TIR（张量程序级），各自独立 |
| 可扩展性 | 一切皆方言：新前端（torch-mlir）、新硬件（自定义 dialect + pass）插件式接入 | 扩展新后端靠 target 注册与 schedule 模板，改动面大 |
| 调优 | 无内置 autotuning（由下游/IREE/可组合生态补） | **AutoTVM/Ansor** 调度自动搜索是核心资产 |
| 社区走向 | LLVM 生态，硬件厂商普遍基于它做工具链 | 自身演进 Relax/Unity（混合借鉴了 MLIR 的统一 IR 思想） |

一句话：MLIR 卖"**造编译器的乐高**"，TVM 卖"**开箱即用的模型优化器**"；做新硬件工具链选 MLIR，做模型部署优化用 TVM 生态更快。关系上不是纯竞争：TVM 的 TIR 生成可下沉到 MLIR 后端。

### Q6. TVM 中 Relay 与 TIR 调度原语各自的角色与区别（AI-Infra-2 Q2）

- **Relay（图级 IR）的"调度"**：作用在**计算图**上——算子融合（fuse_ops，dominator 树分析）、布局转换（layout rewriting，NCHW↔NCHWc）、算子内联/展开（inline/let 消除）、图重写（alter_op_layout、canonicalize）、常量折叠、to_basic_block_normal_form。目标：图级优化 + 决定哪些算子合并成一个 kernel（fusion 是核心）；
- **TIR（张量级 IR）的 schedule 原语**：作用在**循环程序**上——`split/reorder`（循环变换）、`tile`（分块进 smem）、`bind`（thread 绑定 gpu threadIdx）、`vectorize`（向量化）、`unroll`、`parallel`（CPU）、`cache_write/cache_read`（插入 smem/寄存器 staging）、`compute_at/compute_inline`（计算位置调度）、`reduce_axis` 变换（split-k、rfactor 并行归约）。目标：单个算子（stage）的代码生成调优；
- **区别**：抽象层级（DAG vs 循环嵌套）、作用对象（算子间关系 vs 算子内循环）、使用者（编译器 pass 自动 vs 调优工程师/Ansor 搜索空间）。衔接关系：Relay fusion 决定"哪些算子进同一个 TIR PrimFunc"，TIR schedule 决定"这个融合体怎么跑得快"。

### Q7. 单算子性能优化的常见方法（AI-Infra-2 Q3）

通用方法论见《GEMM 与算子优化》Q3（GEMM 六层：算法层→并行结构→访存→指令→布局→autotune）与 Q4（profiling 流程）。Conv 专项补充（追问常见）：

1. **算法层**：im2col+GEMM（通用，复用 GEMM 库）/ Winograd（3×3 s=1 乘法 36→16）/ FFT（大 kernel）/ direct conv（小 batch 有时更优）——详见《GEMM 与算子优化》Q14 推理框架卷积实现；
2. **结构层**：implicit GEMM（im2col 地址计算内嵌装载、不物化展开矩阵）、NHWC + fp16/tf32 tensor core、K 分割 split-k 补并行度；
3. **访存层**：smem tile 输入/权重复用（input tile × filter tile）、寄存器滑窗（跨 tile 数据复用）、cp.async 双缓冲；
4. **特化**：1×1 conv = 纯 GEMM、depthwise conv = 通道独立（访存型，向量化+合并访问主导）。

答题结构："先 profiling 判瓶颈类型（roofline/SOL）→ 按瓶颈选武器：compute bound 上 tensor core/低精度/算法替换，memory bound 上融合/tiling/向量化"。

### Q8. 从工程角度对一个算子做性能优化：思路、收益评估、极限分析（云-实习-二面-1 Q3）

以"RMSNorm 前置的 QKV 投影融合"或"GEMV W4A16"为例的工程框架：

1. **基线与测量**：固定 benchmark 协议（shape 矩阵、warmup 次数、CUDA event 计时、锁频），先测 baseline 与理论极限——**极限分析**：算术强度 AI = FLOPs/Bytes，roofline 上限 $P = \min(P_{peak}, AI \times BW)$，例：4096×4096 fp16 GEMV：FLOPs = 2×16M = 33.5M，Bytes = 32MB+ → AI≈1，3090 上限 ≈ 936 GFLOPS（纯带宽换算）→ 时间下限 ≈ 36μs。**实测与下限的比值就是优化空间**；
2. **优化路径**（按性价比排序）：消除无用开销（精度转换、多余同步）→ 访存优化（合并访问、向量化 128bit、smem staging、融合消除中间读写）→ 并行结构（grid/block 形状、occupancy）→ 指令级（unroll、ILP、tensor core、异步流水）；
3. **收益评估**：microbenchmark（kernel 级）+ **端到端验证**（Amdahl：$\text{端到端加速} = 1/((1-f) + f/s)$，f 是该算子占比——kernel 5× 但占比 2% 时端到端只快 1.03×，要如实报告）；
4. **停止准则**：达到理论极限的 85-90%（带宽型）或连续两个优化手段收益 <3% 即收手；文档化：优化记录（改动/数据/回归）沉淀为 checklist。

### Q9. 算子优化效果如何传导到整网？如何与多卡互联、Profiling、软硬件协同衔接？（云-实习-二面-1 Q7）

1. **kernel → 整网**：Amdahl 定律算端到端收益（Q8）；反向看——整网 profile（Nsight Systems 全模型 trace）找出 top-N 耗时 kernel 与 **gap 空泡**（launch/同步/数据传输），单算子优化让位给"消除空泡"（CUDA Graph、stream 并行、融合）时收益常大于算子本身提速；
2. **整网 → 多卡**：单卡提速后通信占比被动上升（计算时间缩短、AllReduce 时间不变）→ 需要通信-计算重叠（bucket 分桶、PP/DualPipe 气泡填充）、通信量削减（ZeRO 梯度预分桶、FP8/BF16 压缩通信）、拓扑感知（NVLink 域内 TP、跨机 EP 的 all-toall 走 rail-optimized）配套，否则单算子收益在多卡被吃掉；
3. **Profiling 体系**：三级工具链（Nsight Systems 时间线 → Compute kernel 指标 → `-lineinfo` SASS 定位），加上持续性能回归（CI 跑 benchmark 基线，防性能劣化合入）；
4. **软硬件协同**：kernel 设计吃透硬件参数（smem 每 SM 容量、bank 宽度、warp 调度策略、L2 分区）——tile 尺寸按 smem/L2 容量选、数据布局按 bank 冲突特性排、双发射/指令 mix 对齐 SM 吞吐；新硬件（TMA/warp spec）早期迁移的收益最大（竞争少）。

### Q10. 什么是访存密集型算子？举例（实习-一二面 一面 Q1）

判定标准（roofline：算术强度 < 机器平衡点，详见《CUDA 基础与体系结构》Q22 与《GEMM 与算子优化》Q1）。例子按类型：

### Q13. CUDA 中并行性与并发性的区别（实习-一二面 二面 Q3）

- **并行（parallelism）**：**同一时刻**多个任务真正同时执行——需要多物理执行单元（GPU 的数千 core、多核 CPU）；CUDA 中 = 一个 kernel 内多线程同时算不同数据，或多 SM 同时跑不同 block；
- **并发（concurrency）**：**同一时间段**内多个任务交替推进，微观不同时——单核时间片轮转、I/O 等待期间的任务切换。CUDA 场景：多 stream 上多个 kernel **并发执行**（若 SM 资源足够则同时 = 并行；资源不足时分时复用 = 仅并发）、host 端异步 launch 与 device 执行重叠（经典的 host-device concurrency）、kernel 执行与 H2D 拷贝并发；
- 答题区分点：并行看"物理同时"（硬件资源决定上限），并发看"逻辑重叠"（调度决定）；GPU 上并发是手段（overlap 提利用率），并行是目的（吞吐）。

### Q14. CUDA 实现向量加法（实习-一二面 一面 Q10）

基础编程题，完整工程实现在 `solutions/cuda`（向量加 + CPU 对拍 + 合并访问验证）。核心与追问：

```cuda
__global__ void vec_add(const float* a, const float* b, float* c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;   // 全局索引
    if (i < n) c[i] = a[i] + b[i];                   // 越界保护（n 非块整数倍）
}
// launch: vec_add<<<(n + 255) / 256, 256>>>(a, b, c, n);
```

追问阶梯：①为什么 256 线程/block（warp 整数倍 32，寄存器/占用率平衡）；②大数组索引溢出（n > 2^31 时 grid-stride loop 或 64 位索引）；③float4 向量化（每线程 4 元素，带宽 ×4）；④错误检查（`cudaGetLastError` / launch 后 sync）；⑤为什么 memory bound（AI=1/3），优化=合并访问+向量化。仓库内 `solutions/cuda` 的 `vec_add` 测试即含这些变体。

### Q15. GridSample 算子的底层定义与优化（实习-一二面 一面 Q7 项目追问）

**定义**：`F.grid_sample(input[N,C,H,W], grid[N,H_out,W_out,2]) → output[N,C,H_out,W_out]`。grid 存每个输出位置的**归一化**采样坐标 (x,y)∈[-1,1]（align_corners=True 时 -1/1 对应角像素**中心**；False 对应边界半像素外沿——两个语义差半个像素，对齐错误是第一大坑）；输出值 = 输入图在该坐标处的双线性插值：坐标反归一化到像素坐标 (u,v)，取 4 邻域 $I_{i,j}$ 以距离平方权重加权。仿射变换（STN）、光流 warp、检测特征对齐都基于它。

**kernel 实现要点**：①输出像素间完全独立——每线程一个输出点（或一个 (h,w) 位置所有 C 通道，C 维向量化 float4/half2）；②坐标计算一次、C 通道复用（每 (h,w) 算一次 (i0,j0,i1,j1,wx,wy)）；③边界处理用 clamp（`min(max(u,0),W-1)`）而不是分支（padding_mode='border' 天然 clamp，'zeros' 需掩码但也可用乘 0/1 掩码消分支）；④**访存是难点**：相邻输出线程的采样点若 grid 行连续，其 4 邻域在 x 方向重叠率高（L1 命中）——把 grid 布局与线程映射按行主序对齐；⑤数值精度：归一化坐标乘 `(W-1)/2 + 0.5` 在 fp16 下误差放大，坐标计算用 fp32；⑥与上游融合（如 STN 的 affine 参数 → grid 计算 → 采样一个 kernel）省一次 grid 读写。验证：与 `F.grid_sample` 对拍两种 align_corners。

## 三、系统与 C++ 基础

### Q16. 锁的概念与常见类型（实习-一二面 二面 Q1）

基础详解见《C++ 与系统基础》Q14（mutex/条件变量/死锁四条件）。体系化补充：

- **为什么需要锁**：临界区（读-改-写非原子）的互斥访问；底层 = 原子指令（CAS/LL-SC）+ 失败时内核 futex 睡眠（避免自旋空耗 CPU）；
- **类型清单**：互斥锁 mutex（递归 recursive vs 非递归）、读写锁（shared_mutex，读多写少）、自旋锁（忙等，临界区极短/不可睡眠场景，CAS 实现）、条件变量（配合 mutex 的等待-通知）、信号量（计数资源）、RWM 乐观版本（seqlock）、RCU（读端无锁，内核/数据库用）；
- **粒度与层级**：粗粒度（简单但并发度低）→ 细粒度/分片锁（hash 分桶锁）→ 无锁（原子操作/CAS 链表，正确性难度高：ABA 问题、内存序 memory_order）；
- C++ 侧：`std::lock_guard/unique_lock`（RAII 防异常漏解锁）、`std::scoped_lock`（多锁一次获取防死锁）、`std::shared_mutex`、`std::atomic`。
- GPU 侧追问（CUDA 背景）：CUDA 锁 = 原子操作（atomicCAS 的 TTAS 自旋锁），块间互斥用全局内存原子 + `__threadfence()`，但锁的串行化使 SM 利用率塌陷——GPU 更倾向 lock-free 设计（原子归约、per-block 私有化，见《CUDA 编程题》直方图两种实现的对比）。

### Q17. UDP 与 TCP 的适用场景与优缺点（实习-一二面 一面 Q5）

| | TCP | UDP |
|---|---|---|
| 连接 | 面向连接（三次握手/四次挥手） | 无连接，-datagram |
| 可靠性 | 确认重传、按序、流控（滑动窗口）、拥塞控制 | 尽力而为，可能丢/乱序/重复 |
| 开销/延迟 | 头 20B+、重传与拥塞退避引入延迟 | 头 8B、延迟低、实时 |
| 传输单位 | 字节流（无消息边界） | 数据报（有边界） |
| 场景 | 网页/API/文件/数据库/训练参数同步 | 音视频通话、游戏、DNS、广播、传感器 |

深度追问：①QUIC 在 UDP 上重建可靠传输（HTTP/3）——取 TCP 可靠性 + 消除队头阻塞 + 0-RTT；②AI Infra 关联：NCCL 走 IB/RoCE（RDMA on UDP/Ethernet），IB 的可靠传输（RC）类似 TCP 语义、卸载到网卡；参数服务器大消息走 TCP，指标/日志小消息 UDP 合并；③选型逻辑：可靠+吞吐 → TCP（或 RDMA）；实时+容忍丢帧 → UDP（应用层 FEC/重传按需补）。

### Q18. Linux 查看磁盘使用情况的命令（实习-一二面 一面 Q6）

基础命令（背熟 + 组合套路）：

- `df -h`：文件系统级使用量/挂载点（`-i` 看 inode 是否耗尽——磁盘有空间但建不了文件的经典原因）；
- `du -sh /path`（`du -h --max-depth=1 | sort -h` 逐层定位大目录）；
- `lsblk`：块设备与挂载树；`fdisk -l` / `lsblk -f`：分区与文件系统；
- **IO 性能**：`iostat -x 1`（util/await）、`iotop`（按进程）、`vmstat`（b 列/wa 列）；
- 排查套路（追问）：`df -h` 发现满 → `du` 逐级定位 → 删除后 `df` 不降 → `lsof | grep deleted` 找已删除但仍被进程占用的文件句柄（`lsof +L1`）→ 重启或让进程释放；写满导致训练 checkpoint 失败的 case 里最常见的就是 deleted-but-open 日志文件。

### Q19. 链表环检测（实习-一二面 一面 Q9 编程题）

### Q20. 显存异常与长期稳定性问题的定位排查（云-实习-二面-1 Q2）

训练/推理长跑（天/周级）的显存类问题系统排查：

1. **现象分类**：确定性 OOM（启动即爆：模型/优化器放不下——看激活 vs 参数 vs 优化器态三段占用，`torch.cuda.memory_summary`）；**缓涨型**（跑几小时后 OOM——泄漏或碎片）；突发 spikes（特定 batch/序列长度）；`CUDA error: an illegal memory access`（越界访问，配合 `CUDA_LAUNCH_BLOCKING=1` 定位到具体 kernel）；
2. **缓涨排查**：`torch.cuda.memory_allocated` vs `memory_reserved` 曲线（allocated 涨=对象泄漏：检查张量被全局 list/闭包/cache 持有、autograd 图被意外保留（loss 带 graph 存日志）、未释放的中间结果）；reserved 涨 allocated 平 = **碎片化**（分配器预留不还）→ `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` 或 `max_split_size_mb` 缓解，或定期 empty_cache（有代价）；
3. **长稳（非显存）**：loss spike / NCCL timeout（前者查数据坏样本与 lr/梯度范数、后者见 Q4）、宿主内存泄漏（dataloader worker 累积、`psutil` 跟踪 RSS）、句柄泄漏（`ls /proc/<pid>/fd | wc -l`）、磁盘/日志写满、节点故障的自动检测与弹性恢复（torchrun --max-restarts、checkpoint 频率与断点续训设计）；
4. **方法论**：最小复现（缩规模保留现象）→ 二分（数据/代码版本/时间点）→ 观测先行（先加监控再改代码）；线上推理侧另有 KV cache 增长回归、多轮会话上下文泄漏（prefix cache 未命中）两类"显存缓涨"。
