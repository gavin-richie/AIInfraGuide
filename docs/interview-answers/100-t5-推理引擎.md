## Q1. vLLM 中 scheduler 的调度流程（小厂实1 Q1）

vLLM 调度器以 **decode step（一次前向迭代）** 为粒度调度，核心是 `waiting` / `running` 两个队列（V0 架构；V1 合并为单步调度但语义一致）：

1. **每步开始**：scheduler 从 `running` 队列取出一批可以继续 decode 的请求；若有多余 KV 配额，再从 `waiting` 队列按 FCFS 准入新请求（或 chunked prefill 请求的下一块）。
2. **准入条件**：`num_free_gpu_blocks ≥ prefill 需要的块数`。即显存反压——KV block 不足时新请求留在 waiting，**准入不看 batch 数上限而看 KV 配额**。
3. **组装 batch**：把 prefill 与 decode 请求合成一个 batch（或按 `--scheduler-policy` 分开）；prefill 请求计算 prompt KV，decode 请求各前进一个 token。slot_mapping 把逻辑 token 位置映射到物理 KV 块。
4. **执行**：worker（V0 是独立进程，经消息队列下发）执行前向，输出新 token。
5. **善后**：检测 EOS / max_len / stop string，完成的请求出队、释放 KV 块（prefix cache 命中的块引用计数减一）；未完成的留在 running 进入下一轮。

调度策略细节：`fcfs`（默认，公平、TTFT 稳定）vs `priority`（SLO 分级）；长 prompt 会"饿死"问题由 chunked prefill 缓解；prefix-aware 调度（V1）会在 waiting 中优先挑命中 prefix cache 的请求。答题结构建议：**两队列 → 准入条件（KV 配额）→ iteration 级调度 → 完成/释放**。

## Q2. vLLM 请求被抢占后的处理（小厂实1 Q2）

KV 显存耗尽且无请求完成时，scheduler 按 LADIES/RC（recompute）等策略**抢占 running 中的请求**：

- **抢占顺序**：通常抢占"最后进入 running、生成 token 最多（重算损失大反而要小心）"——vLLM 实现为从 running 队尾向前逐个暂停，直到腾出足够 KV 块。
- **两种恢复模式**：
  1. **swap**：把被抢占请求的 KV Cache 换出到 CPU 内存（Pinned memory），恢复时换回——省重算、付 PCIe 传输；
  2. **recompute**：丢弃 KV，只保留已生成的 token 文本，恢复时把它们当 prompt 重新 prefill——省显存传输、付 prefill 计算。若命中 prefix cache，重算代价大幅降低；默认策略会优先 recompute（配合 prefix cache 后代价小）。
- **语义**：被抢占请求回到 waiting 队列头部（保证最终公平），对客户端只是时延变长，无正确性影响。
- **什么时候触发**：典型是新请求 prefill 需要大量块、或 decode 中序列的 KV 增长超出水位线。抢占是吞吐（不拒绝请求）与时延（被抢占请求 TPOT 尖刺）之间的权衡，可通过 watermark、`preemption_mode` 配置。

## Q3. 投机采样：草稿模型与主模型的交互流程；vLLM 与 SGLang 实现差异（小厂实1 Q3）

**交互流程**（Leviathan/Chen 2023，无损）：

1. **draft 阶段**：小模型（n-gram / 小 LLM / MTP 头 / EAGLE 头）自回归快速生成 γ 个草稿 token（每次一个小前向，或 MTP 多头一次出多级候选）。
2. **verify 阶段**：主模型**一次并行前向**同时算出 γ+1 个位置的分布 p（草稿序列 + 下一位置）——大模型的权重读取被 γ+1 个 token 摊薄。
3. **逐 token 校验**：位置 i 的草稿 $x_i$ 以 $\min(1, p_i(x_i)/q_i(x_i))$ 的概率被接受；首个被拒的位置丢弃草稿，从残差分布 $\mathrm{norm}(\max(p_i - q_i, 0))$ 重采样一个 token 并停止；若全接受，从 $p_{\gamma+1}$ 采 bonus token。
4. **数学保证**：输出分布与直接采样主模型**严格相同**（期望接受数 $E = \frac{1-\alpha^{\gamma+1}}{1-\alpha}$，$\alpha = \sum_x \min(p_x, q_x)$）——draft 越准加速越高，draft 很差时至少不劣化太多（只多付 draft 开销）。

适合场景：decode 是 memory bound，单 token 前向"浪费"了带宽潜力——投机采样把多个 token 塞进一次前向，用少量额外计算换带宽利用率的提升。**对批次很大、GPU 已经吃满的离线场景收益趋近 0**（每 token FLOPs 已经很低），对在线小 batch 场景收益 2-3×。

**vLLM vs SGLang 实现差异**：

| 维度 | vLLM | SGLang |
|---|---|---|
| 候选组织 | 每个 request 独立 draft 链，batch 内各请求 γ 不同 | 同样 per-request，但调度与 overlap 更激进 |
| draft 后端 | n-gram/lookahead（免模型）、medula/Medusa、EAGLE 系列、**DeepSeek MTP**（V1 主打） | **EAGLE-2/3** 深度优化、MTP、**token-level 批量 verify** |
| 执行 overlap | V1 async scheduling 把 CPU 调度与 GPU 重叠；draft/verify 串行为主 | **overlap scheduler**：draft 模型前向与主模型上一步 verify 流水重叠，两份 KV（draft 有自己的 cache） |
| 采样语义 | 标准 accept/reject + 残差重采样 | 相同数学，工程上对 verify kernel 做了 tree/链式统一批处理 |
| 树形 draft | EAGLE 支持树（verify 用 attention mask 构造树因果） | EAGLE-3 + tree attention 更早工程化，命中率统计与动态剪枝更细 |

一句话对比：**vLLM 把投机采样当插件（算法多、接入广），SGLang 把它当一等公民（与 overlap scheduler/树 verify 深度耦合），所以在同款 EAGLE/MTP 下 SGLang 常测得更低的单请求时延**。

可运行验证：`solutions/python/src/answers/t5/speculative.py` 实现了完整的 accept/reject + 残差重采样，并用 4000 次蒙特卡洛验证输出分布与 target 的 TV 距离 < 0.05（无损性）：


## Q4. MLA 在 prefill 与 decode 阶段的复杂度差异；矩阵吸收原理（小厂实1 Q6）

MLA 基础（低秩压缩、KV Cache 只存 latent $c_{kv}$，576 元素/token/层）见 [04 Attention 与 KV Cache](./04-attention与kvcache.md) MLA 题；这里展开面试最深的追问——**为什么 decode 要做矩阵吸收而 prefill 不要**。

设头数 $n_h$、头维 $d_h$、latent 维 $d_c$（DeepSeek-V3：128/128/512），query 数 $S_q$，缓存长度 $S_{kv}$。attention 内核两条等价路径：

- **朴素路径**：先把所有缓存的 $c_{kv}$ 升维成 K/V（$2S_{kv} \cdot n_h d_h d_c$ MACs），再在 $d_h$ 空间做标准 MHA（$2S_qS_{kv} \cdot n_h d_h$）；
- **吸收路径**（矩阵乘结合律）：K 吸收进 Q——$q_h' = W_{UK,h} q_h \in \mathbb{R}^{d_c}$，直接与 $c_{kv}$ 点积；V 吸收进注意力——先在 latent 空间做注意力加权平均 $u = A c_{kv}$，最后一次升维 $o = u W_{UV}^{\top}$。MACs = $S_q n_h d_h d_c + 2S_qS_{kv} n_h d_c + S_q n_h d_c d_h$，**全程不物化 K/V**。

**Decode（$S_q=1$）**：吸收把每个缓存 token 的参与成本从 $n_h d_h d_c$（升维）降到 $n_h d_c$（点积），**约省 $d_h$ 倍（128×）计算**，还省掉 K/V 激活的显存读写；升维权重 $W_{UK}/W_{UV}$ 每步都要读一遍，吸收后读的是同样大的合并权重但每个 token 只算一次。实测模型（`mla_absorption.py`）：

```
decode: naive 68.9 GMAC → absorbed 0.55 GMAC，吸收加速 124×
```

**Prefill（$S_q = S_{kv} = 4096$）**：K/V 只需物化一次（$S_{kv} \cdot n_h d_h d_c$），之后 score/value 是 $(S_q \times d_h)$ 的大 GEMM，满血吃 Tensor Core；吸收路径的 score 变成 $(S_q \times d_c)$ 的大矩阵且 Q 侧折叠成本 $S_q n_h d_h d_c$ 线性涨——**反而更慢**：

```
prefill: naive 618 GMAC < absorbed 2268 GMAC（吸收慢 3.7×）
```

所以 SGLang/vLLM 的实现都是 **prefill 用非吸收（大 GEMM）+ decode 用吸收（访存最优）**，吸收版的等价性（两路径输出逐元素一致，atol 1e-5）与复杂度模型见 `solutions/python/src/answers/t5/mla_absorption.py`（`pytest tests/test_t5.py -k mla`，数值对拍 + 成本断言双向验证）。

## Q5. EPLB 的推理机制；DeepSeek V3.2 相较前代的创新点（小厂实1 Q5/Q7）

**EPLB（Expert Parallelism Load Balancer，DeepSeek 开源）**解决 EP 部署 MoE 时专家负载不均（实测不同专家激活频率差数倍，热专家所在 rank 成木桶短板）：

1. **统计**：离线汇总各 expert 历史负载（如 2 小时窗口 batch 平均），负载由路由概率与实际激活计数得到；
2. **冗余拷贝**：总物理专家数 = $N \times$ 冗余系数（如 1.5×），多出的拷贝按负载分给热专家——**冗余不是均匀的，谁的负载大谁多一份**；推理时路由到该 expert 的多个物理拷贝（按各拷贝所在 rank 的实时负载挑一个），权重训练时同步更新；
3. **重排（rebalance）**：把全部物理专家重排到各 GPU，最小化最大 rank 负载（带每层约束的均衡问题，用整数规划/贪心求解）；
4. **周期执行**：负载分布随请求变化（如白天代码/晚上聊天），每天低峰期 rebalance 一次，路由表 logical→physical 同步更新，配合 all-to-all 通信直接生效。

效果参考（`solutions/python/src/answers/t5/eplb.py` 模拟，256 expert / 8 rank / Pareto 负载）：无 EPLB 最大 rank 负载为均值 2.13×，EPLB 1.5× 冗余后降到 1.00×（`pytest tests/test_t5.py -k eplb`）。

**DeepSeek-V3.2 相较 V3 的创新点**：

- **DSA（DeepSeek Sparse Attention）**：核心技术升级。每层用轻量 indexer（两分支：细粒度压缩 token 表示 + 卷积位置编码）为每个 query 打分选出 **top-2048 个相关 KV token**，attention 只在这些 token 上做——把长序列 attention 的 $O(L^2)$ 降到 $O(L \cdot 2048)$，4096+ 长度显著省算省存；对历史 KV 做"压缩缓存"（关联记忆式压缩+增量更新），per-token KV 开销进一步降；训练成本可控（仅 indexer 引入少量参数，V3.1 增量训练 524B token 即得）。
- **NSA 谅承**：DSA 是 NSA（Native Sparse Attention，V3.1 时代论文）的工程落地——压缩/选择/滑窗三分支联合训练的可学习稀疏注意力。
- **推理框架协同**：V3.2 与 DeepSeek 推理引擎协同设计（稀疏 kernel、indexer 预取与 MTP 投机采样结合），官方 API 价格大幅下调。
- 其余延续 V3：MLA + DeepSeekMoE（细粒度专家+共享专家）+ MTP + FP8 混合精度 + DualPipe。

答题提示：先一句话定位"V3.2 = V3 + DSA 稀疏注意力"，再展开 indexer 选 token、top-K 稀疏计算、KV 压缩缓存三点，最后补"与 MTP/框架协同"的工程面。

## Q6. SGLang 多模态 TP 下 ViT image embedding 如何跨进程复用（小厂实1 Q8）

多模态模型（ViT encoder + LLM decoder）开 TP 时的问题：ViT 通常**不做 TP**（模型小、切分通信不划算），只在 LLM 侧 TP，于是 image embedding 只在 rank 0 产生（tokenizer/preprocessor 在主进程），但 LLM 的每个 TP rank 都需要完整的 input embedding。

SGLang 的做法（layers/tp 通信约定）：

1. **rank 0 算 ViT**：图像 token 仅由 tp_rank 0 前向得到 embedding（fp16/bf16）；
2. **broadcast 而非 all-gather**：把 `[batch, n_img_token, d_model]` 的 embedding 从 rank 0 **torch.distributed.broadcast** 到所有 TP rank（NCCL 集合通信，一次搞定；不做 TP 切分再 all-gather，因为 ViT 输出是按 token 而非按维度切的）；
3. **与 text embedding 拼接**：各 rank 把收到的 image embedding 按 multi-modal placeholder 的位置插入 input embeddings（`<image>` 占位 token 的 patch 位置表由 processor 给出），后续 LLM 前向各 rank 按列/行切分正常走；
4. **避免重复计算**：embedding 计算一次、广播一次，N 个 rank 不重复跑 ViT；对比"每个 rank 各自跑 ViT"省 $(N-1)/N$ 的 ViT 计算，且数值严格一致。

延伸答：vLLM 同族问题用 `BroadcastableTensors`/mapper 在 worker 间分发 multimodal 输入；若 ViT 也切 TP（大分辨率视频模型），则 embedding 按注意力头 dim 切分后 all-gather 拼接，通信量与 LLM TP 的 all-reduce 同量级。

## Q7. vLLM 与 SGLang 的差别；SGLang 为什么在推理类大模型上表现更好（Teleai Q6）

| 维度 | vLLM | SGLang |
|---|---|---|
| 定位 | 通用 LLM 推理引擎（吞吐导向） | 面向**代理/结构化应用**的高性能引擎 |
| 调度 | iteration 级 continuous batching；V1 单步调度 + prefix-aware | **overlap scheduler**（CPU 调度与 GPU 前向流水重叠，零 CPU 泡泡） |
| RadixAttention | prefix cache 用 block 哈希（LRU 块池） | **RadixAttention 前缀树**：以 radix tree 管理所有历史 KV，多轮共享前缀/分支采样命中率更高、淘汰更精细 |
| 投机采样 | 插件式（ngram/EAGLE/MTP） | 与 overlap/树 verify 深度耦合，EAGLE-3、MTP 工程化最激进 |
| 结构化输出 | xgrammar 后端 | **compressed FSM**（把正则/grammar 编译到有限状态机，逐 token 施加 mask），编程式生成（SGLang DSL）原生支持 |
| 多机 | PD 分离（NIXL）、TP/PP/EP | 同样支持，且在 large-scale EP（DeepSeek 类 MoE）上与 DS 官方协同优化多 |

**为什么 SGLang 在"推理类大模型"（指 reasoning/agent 负载，长 CoT、大量共享前缀、结构化工具调用）上更好**：① RadixAttention 对"同一 prompt 反复改写/多分支采样/多轮 agent"的 KV 复用率显著高于块哈希 LRU；② overlap scheduler 消除 CPU 调度间隙，长 CoT decode 每步都省；③ 压缩 FSM 让 JSON/工具调用这种"边推理边约束"的场景不必反复 parse/重试；④ 与 EAGLE/MTP 深度集成的投机采样对 reasoning 模型（草稿可由 CoT 前缀预测）命中率天然高。若负载是"一次性长文摘要、无共享前缀"，两者差距缩小，vLLM 生态/量化后端更全。

## Q8. vLLM 二次开发可从哪些模块入手；如何适配自研模型（Teleai Q5/Q9）

**二次开发切入点**（按从浅到深）：

1. **模型接入层**（`vllm/model_executor/models/`）：新增/修改模型结构——注册 `*ForCausalLM` 类（实现 `forward` 返回 logprobs）、`load_weights` 做权重名映射；自定义 attention 可替换为自研 kernel；
2. **调度与 KV 管理**（`vllm/core/scheduler.py`、`block_manager`）：改准入策略（SLO 分级、租户配额）、抢占策略、prefix cache 淘汰、KV 传输（PD 分离对接）；
3. **采样与后处理**（`vllm/sampling_params.py`、`processor/`）：自定义采样逻辑、结构化输出 grammar、logits processor（如业务侧 bad-word 过滤）；
4. **量化后端**（`vllm/model_executor/layers/quantization/`）：注册新量化格式（实现 replace 逻辑 + linear kernel 路由）；
5. **输入/多模态**（`inputs/preprocess`、`multimodal/`）：自定义 processor、embedding 输入直通；
6. **API 服务层**（`entrypoints/openai/`）：路由、限流、多 LoRA 服务、计费埋点。

**适配自研模型（如自研注意力/MoE）的最小路径**：

1. 继承/仿写一个 `MyModelForCausalLM`（参考最接近的开源模型实现），在 `Registry` 注册架构字符串；
2. attention 走 `vllm.attention` 抽象：实现自定义 `AttentionImpl`（metadata 构造 + core attention 调用），KV 布局（ heads/head_size）声明给 paged KV 管理器；自定义 KV 格式（如 MLA latent）可指定 `kv_cache_dtype` 与 block 语义；
3. `load_weights` 对齐 checkpoint 键名；MoE 自定义路由则实现 `FusedMoE` 的顶层（select experts + dispatch）；
4. 写单测对比 HuggingFace 参考实现 logits；最后跑 `benchmark_serving` 验证性能。

关键意识：vLLM 把"模型定义"与"调度/KV/采样"解耦，**90% 的模型适配只需动 model_executor 层**；只有新 KV 语义/新调度需求才下探 core。

## Q9. V100 显存多大？32B 模型 INT8 量化后能否在 V100 上跑？部署方案（Teleai Q10）

V100（16/32GB，无 FP8、无 Weight-only INT kernel 加速，Ampere 之前的 Volta）。

**算账**（用 `solutions/python/src/answers/t5/kv_cache_size.py::quantized_model_footprint`）：

- 权重：32B × 1B ≈ 32GB（INT8）——单卡 32GB V100 放不下（还要 KV、激活、CUDA context ~1-2GB）；
- 若 INT4（W4A16）：权重 ≈ 16GB + KV + 开销 ≈ 19-20GB，**单卡 32GB V100 可跑但很紧**（batch/上下文受限）；
- 注意 V100 **没有 INT8/FP8 Tensor Core 的 weight-only 加速收益**（Marlin/exllama 需要 Ampere+），INT8 在 V100 上主要省显存而非提速，甚至解压 kernel 更慢。

**方案**：① 2×V100 张量并行（`vllm serve --tensor-parallel-size 2`，INT8 权重每卡 16GB + 各自 KV，可行）；② 单卡换 W4A16（AWQ/GPTQ INT4）+ vLLM（Marlin 在 Volta 不可用，走 dequant GEMM，仍以省显存为主）；③ 降配：换 14B/7B 模型 INT8 单卡从容跑。答题要点：**先算账（权重+KV+开销）再谈量化收益的架构前提（V100 无 INT8/FP8 硬件加速）**。

## Q10. 高并发下如何对推理服务压测？监控哪些指标？（Teleai Q11）

**方法**：用 `vllm bench serve`（或 Locust/hey/wrk + OpenAI 兼容 API）固定请求长度分布（input/output token 数）、逐步加并发（并发 = 请求数或 ISLA 到达率），每个档位稳态跑 5-10 分钟，直到 SLO 违约率超阈值（如 P99 延迟超限）——**最大可用并发 = 违约前一档**。随机化 prompt（避免 prefix cache 全命中导致虚高）、预热后再测。

**关键指标**：

| 类别 | 指标 |
|---|---|
| 吞吐 | output tokens/s（服务级）、requests/s、batch size（实际 running 数）、GPU 利用率/显存 |
| 时延 | TTFT（P50/P99）、TPOT/ITL（每 token 间延迟）、端到端时延、排队长度与时间 |
| 正确性/稳定 | 产出 token 分布漂移（对比低并发输出）、错误率、KV cache 命中率、抢占次数 |
| 系统 | 队列深度、显存水位与 swap、网络/前置负载均衡饱和、引擎 version/多副本均衡度 |

调优回路：并发升 → 观察 TTFT（prefill 排队）与 TPOT（decode batch 变大）谁先劣化 → 对应调 `max_num_seqs`、`max_num_batched_tokens`（chunked prefill 预算）、GPU KV 水位，或多副本 + 路由。陷阱：只看平均延迟不看 P99；客户端瓶颈（单连接、TLS 握手）误判为服务瓶颈。

## Q12. "packing" 与"多轮对话"形式的区别；如何提升多轮对话能力（虾皮 Q3/Q4）

**训练数据组织角度**（这是该题的出处语境）：

- **packing**：把多条短样本拼接成一条长序列（用 separator/位置重置分隔），为了**填满训练序列长度、提高 token 利用率**——样本间互相独立，attention mask 通常阻断跨样本注意力（或不管，让模型学会 separator）。解决的是"短样本多、padding 浪费"的效率问题。
- **多轮对话形式**：一条样本内含多轮 user/assistant 交替，**轮次间有真实上下文依赖**；训练时只在 assistant token 上算 loss（user 部分不学），推理时天然对应 chat 模板与多轮 KV prefix 复用。

区别三连：**样本关系**（独立 vs 依赖）、**loss mask**（全学/分隔即可 vs 只学 assistant）、**推理形态**（与 KV prefix cache 无关 vs 多轮命中 prefix cache）。SFT 两者可组合（多轮对话打包填充长度）。

**提升多轮对话能力**：① 数据上用真实多轮分布（含追问、指代、省略），覆盖工具调用/澄清等行为，而非单轮指令的堆叠；② 训练上对长多轮做 loss mask 与轮次采样（防过拟合最后一轮）；③ 推理/系统上开 prefix caching（历史轮 KV 复用，降低多轮 TTFT）、上下文管理（超长时摘要压缩）、RAG 注入会话相关记忆；④ 评测上用多轮 benchmark（MT-Bench、MultiTurnArena）+ 人工/LLM-as-judge。

## Q13. DeepSeek R1 采用什么注意力优化方案？（联想 Q1）

## Q15. LLM 在 NPU 上推理的瓶颈；prefill/decode 的 Matmul 策略；分块数据缓存连续性；昇腾对 Transformer 的适配（荣耀二面 Q1-Q4）

**Q1 NPU 推理瓶颈**：与 GPU 同构但更尖锐——① **访存带宽**（decode 读权重+KV，HBM 带宽是硬上限，NPU 带宽通常低于同级 GPU）；② **算子库成熟度**（新结构/变长 shape 的 kernel 覆盖慢，fallback 到 CPU 或低效实现）；③ **动态 shape**（NPU 编译器对静态 shape 优化激进，变长 batching 代价高）；④ 多卡互联（NPU 间 all-rede 带宽/拓扑）；⑤ 大 batch 下的调度与 DDR 内存驻留。答题先说"decode memory bound / prefill compute bound 的分阶段结论"，再列 NPU 特有的工具链/动态 shape 问题。

**Q2 Prefill vs Decode 的 Matmul 优化**：

- Prefill：大 M 的 GEMM，compute bound——优化=选好 tile（Cube 分块乘满矩阵单元）、双缓冲流水、权重全程驻留；对 attention 用 FlashAttention 分块（SRAM 内算 score×V）；TP 切分 M/N 维都行。
- Decode：GEMV/瘦 GEMM，memory bound——优化=**权重读一次算多路**：① 加大 batch（continuous batching 把 M 攒大，GEMV→GEMM）；② weight-only 量化（W4/W8）直接减读取字节；③ 向量宽度拉满（128b 向量 load）、L0B/L1 权重复用、多 batch 权重 broadcast；④ kernel 融合（LN+_add+matmul）减少激活读写；⑤ CUDA Graph/整网静态化消除 launch。

**Q3 分块计算中数据在缓存的连续性**：① 访问模式与存储布局同构——分块（tiling）后每块的元素在 DRAM/缓存里连续（NHWC/分块内存布局、pack 后的权重）；② tile 尺寸对齐缓存行与 bank（对齐 32B/128B，避免跨行）；③ 复用距离控制在容量内——选 tile 使 A 块驻留 SRAM/L1 期间完成对所有用到它的输出块的计算（经典 GEMM 循环顺序：外层遍历 K 块）；④ 预取（双缓冲）把下一块的搬运与当前块计算重叠；⑤ 避免伪共享/跨 SM 边界切分。

**Q4 昇腾对 Transformer 的适配性**：达芬奇架构的 Cube 单元（矩阵乘）+ Vector 单元（激活/LN/Softmax）+ AI Core 阵列与 Transformer 的"大 GEMM + 轻量逐元素"负载匹配度高；CANN 图编译（算子融合、整图下沉）+ MindIE 推理引擎针对 decode 做了 KV 管理/batching；短板在长尾算子（自定义激活、动态 shape、投机采样类新结构）与生态（需要专门移植与调优），开发成本高于 CUDA 生态。定性结论：**结构匹配、生态追赶**。

## Q16. 推理优化的整体认识；端侧大模型部署的挑战与方案（海康-一面 Q4、海康 Q4、智源一 Q2）

**端侧挑战**：算力/内存/功耗预算小（无独立显存，走 CPU/NPU/DSP）、内存带宽窄、异构算力（大核+小核+NPU）、动态输入（语音/相机多模态）、无批量（batch=1 GEMV 更依赖带宽）、系统抖动（温控降频）、OTA 更新。**主流方案**：量化（W4A16/W8A8，NNIE/NPU 支持 INT8）、算子融合与图优化（ncnn/MNN/TNN/Executorch/MLC-LLM）、KV Cache 放内存分级、小模型（1-3B）+ 云端协同、投机采样端侧化、按硬件 tile 的手工 kernel（NEON/MNN 关键算子）。可结合 ncnn/RK3588 实操见 [102 T5 系统与部署](./102-t5-系统与部署.md)。

## Q17. 静态图与动态图；动态 shape 怎么处理（智源二 Q5、海康 Q5"模型导出时如何处理动态维度"）

- **静态图**（TF1/ MindSpore 图模式 / ONNX）：先建计算图再执行，编译期完成 shape 推导与全局优化（融合、内存规划、算子排布），性能好、可整体下沉硬件；代价是灵活性差，控制流要 low-level API 表达。
- **动态图**（PyTorch 默认 eager）：逐算子即时执行，随时打印/条件分支/任意 Python 逻辑，易调试；代价是每步调度开销大、无法跨算子优化。
- **动态 shape 三板斧**：① **padding/bucketing**——把变长归一到几个档位（8/16/32 档），每档编译一份 kernel/CUDA Graph，batch 维尤其常用；② **符号 shape 编译**——Torch.compile/TVM/MindSpore 用动态轴（`torch.SymInt`）把维度当符号变量，kernel 生成参数化 tile；执行时按真实 shape 实例化或选择已编译版本；③ **分段处理**——变长部分（prefill/attention）走动态路径，定长部分（decode/FFN）静态化；推理引擎还用 paged KV 把"变长 KV"变成"定长块查表"，把动态性隔离在 block table 层。

- **模型导出（ONNX/TRT）时的动态维度**：`torch.onnx.export(..., dynamic_axes={"input": {0: "batch", 1: "seq"}})` 把 batch/序列维声明为动态轴；TensorRT 解析 ONNX 后建 **optimization profile**（每个动态维给 min/opt/max 三档），builder 按区间生成 kernel（多 profile = 多份特化，启动时间换运行灵活性）；导出前处理控制流（trace 拍平、if/loop 转 ONNX op）、固定能固定的维度（导出后精度/性能都更优）；验证用不同 shape 推理对拍。经验：动态维越多编译越慢、性能越接近"取最大档"，**只保留必须动态的 1-2 维**（batch 与 seq），其余固化。

## Q18. 推理框架中计算图、运行图、内存管理的职责；如何设计推理框架整体架构（智源二 Q6）

- **计算图（构图/ IR）**：模型 → 中间表示。职责：算子节点与张量依赖、shape/dtype 推导、常量折叠与图优化（融合、剪枝、布局变换、量化 rewrite）。对应 PyTorch 的 FX/inductor IR、TensorRT 的 network definition。
- **运行图（执行计划）**：优化后的图 + 执行策略。职责：调度顺序（拓扑/并行流）、算子到后端（CUDA/FFT/NPU）的派发、kernel 选择、多流依赖、CUDA Graph 捕获；迭代间可复用。
- **内存管理**：职责：权重/KV/激活/工作区的生命周期规划——静态内存规划（按拓扑序算各张量 lifetime，重叠复用arena）、KV 分页/池化、prefix 共享、CPU-GPU 分层；目标是最小峰值显存与零拷贝。

**设计一个推理框架**（答题骨架）：

```
输入层    tokenizer/多模态 processor → 请求队列
    ↓
前端      模型加载（safetensors）→ 计算图构建 → 图优化（融合/量化/布局）→ 编译期内存规划
    ↓
调度器    continuous batching / chunked prefill / 抢占 / prefix cache /（可选 PD 分离）
    ↓
执行器    运行图派发 kernel、多 stream、CUDA Graph、异步输出
    ↓
后端算子  自研 kernel + vendor 库（cuBLAS/FA）+ fallback；量化 kernel 路由
    ↕
内存      KV paged 池 / 权重常驻 / 激活 arena / offload
    ↓
服务层    OpenAI API / 流式 / 结构化输出 / metrics
```

关键设计决策：变长输入在哪里吸收（bucket/分段）、KV 的物理布局、CPU 与 GPU 的重叠（异步调度）、量化与 kernel 的解耦接口。

## Q19. 常见图优化技术；计算图的构建方式（智源二 Q7、传音 Q13）

**图优化**（推理引擎 compiler pass）：① 常量折叠/死代码消除；② **算子融合**（LN+x、GEMM+bias+激活、softmax 融合，见 [03](./03-gemm与算子优化.md)）；③ 布局变换（NCHW→NHWC、矩阵乘转置消除）；④ 代数简化（$x×1$、$x+0$、concat 拆分传播）；⑤ 量化 rewrite（浮点算子→量化算子+Q/DQ 插入）；⑥ 内存规划优化（lifetime 重叠、in-place）；⑦ 子图替换（图匹配到手工融合库，如 cuDNN/TensorRT plugin）；⑧ 降维/广播简化、公共子表达式消除（CSE）。

**计算图构建方式**：① **追踪式（trace）**——跑一遍样例记录算子（torch.jit.trace/TornadoFX 风格），快但捕获不到数据依赖控制流；② **源码解析（AST）**——分析 Python/torch.fx symbolic_trace，保留控制流；③ **编译器 IR 前端**——TVM Relay/MLIR 从 ONNX/TF 等交换格式读入；④ **命令式构图**——TensorRT parser / explicit API 逐层 add（部署侧最常见）；⑤ **导出交换格式**——训练框架→ONNX/prototxt→目标引擎 parse。构建要点：shape 推导、控制流表达（loop/if 子图）、动态轴标注。

## Q20. Continuous Batching 工作机制（小厂实2 Q9）

见 [05 推理引擎与优化](./05-推理引擎与优化.md) Q2：调度粒度=**每次前向迭代**（Orca 提出 iteration-level scheduling），完成的请求立即出队、等待中的请求即时补位，配合 slot mapping 映射逻辑位置到 paged KV 物理块——相对 static batching 吞提 2-4×。结合本篇 Q1 的 vLLM scheduler 流程作答即可。

## Q21. FasterTransformer 核心特性；常见推理/训练框架对比与选型（南湖 Q8/Q9、传音 Q12）

**FasterTransformer（NVIDIA，已演进为 TensorRT-LLM 前身）**：① 纯 C++/CUDA 的 Transformer 解码器库——每层 GEMM 走 cuBLAS，attention 用自研 Open-Source FasterTransformer(Masked Multi-Head) kernel（flash 思想的分块软最大）；② ** fused kernel 族**：LayerNorm/bert embeeding/decoding（top-k sampling 融合）等；③ 支持 INT8/FP8（Hopper）量化推理；④ MPI 多卡 TP+PP；⑤ 半静态 batching（一次请求组内复用上下文，非 iteration 级）——这是它与 vLLM 世代的最大代差；⑥ C++ API/TF 集成。考点：FT 是"高性能算子库+简单运行时"，**没有 continuous batching/paged KV**，生产 LLM 服务现在选 TensorRT-LLM/vLLM/SGLang。

**框架选型**（按场景）：

| 场景 | 推荐 | 理由 |
|---|---|---|
| 通用 LLM 服务（吞吐） | vLLM | 生态最全、量化后端多、PD 分离 |
| Agent/结构化/多分支 | SGLang | RadixAttention、overlap scheduler、FSM |
| 极致 NVIDIA 性能/生产固化 | TensorRT-LLM | 编译期优化+In-flight batching+FP8 |
| 端侧/移动 | llama.cpp / MLC-LLM / MNN / ncnn | 量化+NEON/DSP、无服务器依赖 |
| 训练 | Megatron-LM/deepseed（大模型）、TorchTitan | TP/PP/ZeRO 成熟 |
| 华为 | MindIE/CANN | 昇腾适配 |

对比维度口诀：吞吐/时延、量化与 kernel 支持、调度能力（batching/prefix）、硬件覆盖、易用性与生态、license。

   答题技巧：说"我会按 attention/kernels/调度/量化四条线各举一例"，展现体系感。

## Q23. H 系列 GPU 与 L 系列 GPU 的架构差异（飞星 Q4）

| | H 系列（H100/H800/H20，Hopper） | L 系列（L40/L40S/L20，Ada） |
|---|---|---|
| 定位 | 数据中心训练+推理旗舰 | 推理/图形卡（单卡性价比） |
| 芯片/互联 | SXM5、**NVLink 900GB/s**、可多卡 MIG | PCIe 4.0/5.0，无 NVLink |
| 显存 | HBM2e/HBM3 80GB，**3.35TB/s**（H20: 96G/4.0TB/s） | GDDR6 48GB，~864GB/s |
| FP8 | **有**（Transformer Engine 自动混合 + FP8 Tensor Core 2×FP16） | L40S **有 FP8 Tensor Core**（Ada，733T）但无 Transformer Engine、无自动混合；L40 无 FP8 |
| 精度 | FP16 989T / FP8 1979T（稀疏 2×） | FP16 362T（L40S） |
| 特性 | TMA（async bulk copy）、线程块簇、warp specialization | 第八代 NVENC/NVDEC、图形光追 |
| 跑 LLM | 大 batch/长序列/多卡扩展 | 中小 batch、单卡部署，受限于带宽 |

记忆抓手：H=带宽（HBM+NVLink）+FP8 TE；L=GDDR 显存大但带宽低、无 NVLink——**decode 场景 H 系列优势按带宽比例放大**。H20 是特例：算力阉割、带宽保留（4TB/s），推理（decode bound）反而还行。

## Q24. 昇腾 CANN 与 MindIE 的核心组件（Teleai Q8）

- **CANN（Compute Architecture for Neural Networks）**：昇腾计算栈——上层 **PyTorch Adapter（torch_npu）**/TF 适配器（训练框架无缝切）；**ACL（Ascend Computing Language）** runtime API（设备/流/内存管理）；**GE（Graph Engine）** 图编译执行；**HCCL** 集合通信库（对标 NCCL）；**算子库 Ascend C / TBE（TIK）** 开发自定义算子；编译器（把计算图编译到 DaVinci Core 的 Cube/Vector 指令）；工具链（msame、profiler）。
- **MindIE（MindSpore Inference Engine）**：昇腾推理服务套件——**MindIE-LLM**（LLM 推理加速：continuous batching、PD 分离、投机采样、量化 W8A8/W4A16、长上下文优化）；**MindIE-Service**（开放 API 服务，OpenAI 兼容、HTTP/HTTPS、多模型调度）；MindIE-Edge（端侧）；对标 vLLM/TensorRT-LLM 在昇腾上的角色，底层调 CANN 算子。
  答题框架：**CANN=编译+算子+运行时（对标 CUDA+cuDNN+NCCL），MindIE=引擎+服务（对标 vLLM+Triton Inference Server）**。

## Q25. 设计一个分布式推理框架（小厂一 Q1）

系统设计题，按"需求 → 架构分层 → 关键模块 → 难点"作答：

**需求假设**：多副本高并发 LLM 服务、长/短请求混合、SLO 分级、弹性扩缩容。

```
        客户端 → LB/网关（认证/限流/路由）
                    ↓
        全局调度层（cluster manager）
        · 请求路由: prefix 感知(哈希公共前缀→同副本)、SLO 分级、负载感知
        · 模型/副本管理: K8s Operator 扩缩容、灰度升级
                    ↓
        推理实例（可多机）
        · 引擎: continuous batching + chunked prefill + 抢占(本篇 Q1/Q2)
        · KV 管理: paged 池 + prefix cache; 大模型 TP/PP/EP(DeepSeek 类)
        · 可选 PD 分离: prefill 组与 decode 组 + KV 传输层(RDMA)
        · 量化: W8A8/FP8 kernel 路由
                    ↓
        共享存储层: 模型权重仓库(预热/分层加载)、全局 KV cache(可选)
```

**关键模块**：① 请求路由（prefix 哈希提高 KV 命中、一致性哈希减迁移）；② 实例内调度器（见 Q1）；③ KV 生命周期（本篇 Q2 抢占 + prefix LRU）；④ 传输层（TP 用 NCCL，PD 分离用 RDMA/NIXL，权重用对象存储+P2P 分发）；⑤ 可观测（TTFT/TPOT/GPU 水位/命中率 metrics + trace）。

**难点与权衡**：路由的缓存感知 vs 负载均衡冲突；PD 分离的 KV 传输成本 vs 干扰收益；抢占 vs 尾延迟；多租户配额与公平；权重热更新。加分点：结合 Mooncake/Disaggregated serving 谈以 KV 为中心的架构趋势。
