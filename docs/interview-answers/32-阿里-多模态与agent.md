## Q1. 【重点】描述 Qwen-VL 的完整训练流程（一2 Q1）

组件三件套：**视觉编码器 ViT（OpenCLIP ViT-bigG 初始化）+ 连接器（Qwen-VL 一代是 cross-attention Resampler，Qwen2-VL 起改为 MLP）+ LLM（Qwen 底座）**。一代三阶段：

1. **阶段 1（对齐预训练）**：冻结 LLM，只训 ViT 与连接器；数据是大规模弱标注图文对（约 5B token，含网络爬取 caption、OCR、图文交错文档）；目标 = 让视觉特征学会"说 LLM 听得懂的语言"，图像被压成固定 256 个 visual token（Resampler 的 query 数固定）；
2. **阶段 2（多任务多模态预训练）**：全参数训练，输入分辨率提升（448 起步）；数据换成高质量多任务混合——VQA、doc-VQA/OCR、grounding（bbox 输出格式 `<box>(x,y)(x,y)</box>`）、caption、纯文本（防遗忘）；这一步建立定位、读文档、图表理解能力；
3. **阶段 3（指令微调 SFT）**：冻结 ViT，指令对话数据（多模态对话、图文创作、定位指令）对齐到对话格式，混纯文本指令数据。

**Qwen2-VL 关键升级**（面试常追问）：① **Native Dynamic Resolution**——不再 resize 到固定尺寸，任意分辨率图片按 2×2 patch 直接切（NaViT 思路），序列长度随图片面积变化，训练用 packing；② 连接器简化为 **MLP**（pixel-unshuffle 把每 2×2 patch 缩成 1 token，视觉 token 数 ÷4）；③ **M-RoPE 多模态旋转位置编码**（见 Q4）；④ 视频帧与图像统一处理。三阶段流程结构不变（对齐 → 多模态预训练 → SFT），数据规模与分辨率课程加大。

## Q2. 多模态大模型中，将视觉特征传递给 LLM 有哪些常见方法？（一2 Q2）

| 方法 | 代表 | 机制 | 优缺点 |
|---|---|---|---|
| Cross-attention 注入 | Flamingo | 新增 gated cross-attn 层，visual token 作 K/V，LLM 各层可插 | 不占 LLM 序列长度；但改 LLM 结构、工程复杂 |
| Q-Former / Resampler | BLIP-2、Qwen-VL | 可学习 query 从 ViT 特征里"抽取"固定数量 token | 压缩比高（任意图→256/32 token）；有信息瓶颈、需专门预训练连接器 |
| **MLP / Linear projector** | LLaVA、Qwen2-VL、InternVL | ViT patch 特征过 1-2 层 MLP 直接进 LLM 词表 | 结构最简单、信息保留最全（一代 LLaVA 仅 2 层 MLP 就 SOTA）；视觉 token 多、计算贵，常配 pixel-shuffle/token merging 压缩 |
| Patch 直接 embedding | Fuyu | 无独立 ViT，图像块线性投影进 decoder | 最简洁；缺乏可复用的视觉预训练 |
| 前缀软提示 | Prompt tuning 系 | 可学习 prefix 向量 | 参数省；表达弱，已少用 |

演进趋势：**"强 ViT（CLIP/SigLIP 初始化）+ 简单 MLP + 大规模联合训练"** 胜出——复杂连接器（Q-Former）的压缩收益被"压 token 数（2×2 合并/高分辨率原切）+ 更长上下文 LLM"取代。回答时点出 trade-off 三要素：**视觉 token 数（LLM 计算量）、信息保留度、训练稳定性**。

## Q3. ViT 通常采用什么方式进行预训练？（一2 Q3）

- **有监督分类**：原始 ViT 论文用 JFT-300M 大规模标签预训练（迁移超 ImageNet-1k 训练）——标签贵、语义有限；
- **对比学习（图文对齐）**：CLIP/SigLIP——图像 encoder 与文本 encoder 在成对数据上对齐，得到**语义强、开放词表**的表征，是多模态 LLM 视觉塔的主流初始化（Qwen-VL 系、LLaVA 均用）；
- **掩码图像建模（MIM，自监督）**：MAE（75% mask + 轻 decoder 重建像素，表征适合下游微调）、BEiT（mask + 离散 visual token）；DINO/DINOv2 自蒸馏——特征质量高，适合检测/分割与 zero-shot 检索；
- **多模态 LLM 场景的实践**：CLIP/SigLIP 初始化 → 对齐阶段与 LLM 联合微调（通常解冻 ViT 全参或后段 block），高分辨率能力靠 native resolution 继续训。
- 结构要点（追问常带）：patch 16×16 线性投影、[CLS]/global pooling、可学习 1D position embedding（后续插值到更大分辨率）、ViT 没有归纳偏置 → 比 CNN 更吃数据量。

## Q4. 针对不同尺寸的图片或视频输入，位置编码应如何设计？（一2 Q4）

问题本质：序列长度可变 + 位置需可外推。

1. **固定网格插值**：训练 224/448 网格，推理更大分辨率时把 1D position embedding 双三次插值（ViT 原生做法）——分辨率跳变大时性能掉；
2. **2D 分解**：位置编码分解为（行, 列）两组 1D 编码相加/拼接，天然支持任意宽高比；
3. **Native 分辨率 + packing（NaViT/Qwen2-VL）**：每张图按自身宽高切 patch，序列长度=patch 数，训练时序列 packing 混排——位置编码必须支持变长 → 用 **RoPE 系**做相对位置；
4. **M-RoPE（Qwen2-VL）**：把每个 token 的位置分解为 **(t, h, w) 时间-高-宽三分量**各自旋转；文本 token 三分量取相同值（退化为普通 RoPE），视觉 token 按真实时空坐标展开，视频的时间维单独编码——统一了文本/图像/视频的位置空间且支持任意分辨率与帧数；
5. **视频额外问题**：帧间时间位置（帧序号 or 时间戳编码）、变长视频的帧采样策略（均匀/关键帧/事件切片），长视频用分层（段内空间+段间时间）编码；
6. **外推兜底**：NTK-aware/YaRN 缩放（与纯文本长上下文同套技术，见 [31](./31-阿里-训练与算法.md) Q4）。

## Q5. 多模态 RAG 的基本思路与实现方案（一2 Q6）

与文本 RAG 同骨架，差异在"证据是多模态的、检索是跨模态的"：

1. **入库（离线）**：文档/PDF 解析（版面分析、图表转图像+caption、表格结构化）→ 切块（语义块 + 图文对保留）→ 多模态 embedding（CLIP 系图文统一空间，或文本模型 + 图像描述文本双索引）→ 向量库 + 原始资产存储（对象存储）+ 元数据（来源/页码/时间）；
2. **检索（在线）**：query（文本或图像）→ 跨模态召回（文搜图/图搜图/文搜文混合）→ 混合排序（向量 + BM25，RRF 融合）→ **多模态 reranker**（cross-encoder）；
3. **生成**：把命中的图像（或其多模态特征）与文本块一起送 MLLM，要求引用证据生成；图像证据直接走视觉通道（Qwen-VL 类模型），长文档走"页图 + 文本"双通道；
4. **工程要点**：图表类问题必须保图像证据（表格 OCR 有损）、多路索引一致性、评测用"证据命中率 + 端到端答案正确率"双指标。
文本 RAG 检索模块的完整方案见 Q6。

## Q6. RAG 系统中检索模块的实现方案有哪些？（一1 Q4）

- **稠密检索**：bi-encoder（双塔）编码 query/文档 → ANN 索引（**HNSW** 图索引低延迟、**IVF-PQ** 量化省内存，Milvus/Faiss/pgvector 选型按规模）；
- **稀疏检索**：BM25/倒排——关键词精确匹配强（型号、专有名词），与稠密互补；
- **混合检索**：多路召回 + **RRF 或加权融合**重排——生产默认；
- **重排**：cross-encoder 对 top-50 精排（精度↑延迟↑），或 LLM listwise rerank；
- **查询理解**：改写/扩展（HyDE 生成假设文档再检索、multi-query）、意图路由（FAQ/结构化/语义）、对话历史压缩成独立 query；
- **结构化过滤**：元数据（时间/权限/类目）在向量检索前置过滤；表格/SQL 类走 text2SQL 路线而非向量；
- **工程**：增量索引、embedding 版本管理、缓存（query→结果 LRU）、评测（recall@k / nDCG + 端到端答案质量）。

## Q7. 【重点】阐述你设计的 Agent 系统的整体架构；各 Agent 分别负责什么、输入输出是什么？（一1 Q6、淘1 Q6）

按分层模板答（结合自己项目替换内容）：

```
┌─ 交互层：MCP / CLI / HTTP / IM 卡片
├─ 编排层：Supervisor(Router/Planner) → Executor(s) → Verifier，循环直到 Done
├─ 能力层：规划(任务分解 DAG) · 记忆(短期上下文+长期库) · 工具(检索/代码/文件)
│          · 反思(失败归因与重规划)
└─ 模型层：LLM(多尺寸分级：规划用强模型、执行用小模型) + 多模态感知
```

- **Planner/Supervisor**：输入=用户目标+当前状态摘要；输出=任务 DAG（或下一步指令 + 接受标准）；负责分解、派发、终止判定；
- **Executor**：输入=单任务指令+相关上下文（检索注入）；输出=结构化结果（diff/报告/数据）+ 工具调用轨迹；执行检索、写代码、跑命令；
- **Verifier/Critic**：输入=任务结果+接受标准；输出=通过/失败+归因（哪一步错、补什么上下文）；驱动重试与升级；
- **Memory**：输入=会话与轨迹；输出=被检索的上下文片段（见 Q9）；
- 关键设计决策（面试下钻点）：单 Agent 循环 vs 多 Agent 的取舍（上下文隔离、成本、错误传播）、模型分级路由、工具描述即接口（schema 清晰度直接决定调用成功率）、失败兜底（预算上限、死循环检测、人工升级）。

## Q8. Workflow、Agent、Skill 三者的区别与定位（淘1 Q2）

- **Workflow（工作流）**：**预定义控制流**——DAG/状态机写死步骤，LLM 只是某些节点里的函数（分类/抽取/生成）。确定性高、可控可审计、成本低；改流程要改代码。适合稳定业务管线（审核、ETL、报告生成）；
- **Agent**：**LLM 在循环里自主决策**——感知（上下文）→ 规划（选下一个工具）→ 行动 → 观察，循环直至目标达成。灵活处理开放任务，但不确定性、成本、时延都高。适合需求无法穷举的探索型任务（编码、研究、排障）；
- **Skill（技能）**：**封装好的可复用能力单元**——把某类任务的 prompt 模板、工具集、参考流程、脚本资源打包成"说明书"，按需加载（如 Claude Code 的 SKILL.md + scripts：模型先读简介，判断相关才展开全文——渐进披露省 context）。定位是给 Agent/Workflow 共享调用的"插件"。
- **一句话定位**：Workflow 是**骨架**（谁先谁后写死），Agent 是**大脑**（每步怎么走现场决定），Skill 是**肌肉**（标准化动作）。选型：能写死就 Workflow，把 Agent 嵌在必须判断的节点；常用能力沉淀为 Skill 供两者复用——三者不是互斥而是组合。

## Q9. 【重点】Agent 的记忆模块如何设计？常见的记忆管理策略？上下文记忆策略如何设计与实现？（淘1 Q1、实2 Q2）

**分层设计**（借鉴认知科学的经典三分）：

1. **工作记忆（短期）**：当前上下文窗口内的消息轨迹；策略：滑窗裁剪 + **滚动摘要压缩**（旧对话压成 summary 释放预算）、关键事实单独抽取（"用户约束"列表置顶）；
2. **情景记忆（episodic）**：过往任务轨迹与结论 → 向量库存（embedding=任务描述+结果摘要），新任务先检索相似历史（少踩重复坑）；带时间戳与衰减；
3. **语义记忆（知识）**：领域文档/规则 → RAG 知识库；**程序记忆**：沉淀的 Skill/SOP（见 Q8）；
4. **外部状态记忆**：文件系统即记忆（Claude Code 的 CLAUDE.md 项目约定、TODO 文件、checkpoint 目录）——跨会话持久、可审计、天然可 diff。

**管理策略**：写入（任务结束提炼要点/重要性打分过滤）、检索（相似度 + 时间衰减 + 使用频率加权，Generative Agents 的 recency-importance-relevance 三因子是标准答案）、更新（追加 vs 覆盖：事实变化用 update，经验用 append）、淘汰（容量上限 LRU）、隔离（多用户/多项目的记忆命名空间）。
**上下文记忆策略**（多轮对话落地）：token 预算分配（system/记忆/历史/当前任务的配比）、prefix KV cache 复用（稳定前缀的显存/时延优化，对应 [30](./30-阿里-推理与量化.md) Q6）、长会话定期 summarize-and-carry。

## Q10. Agent 的对话记录采用什么方式保存？使用怎样的数据结构？（控实 Q3）

分三层答：

- **内存态（会话中）**：消息数组 `[{role, content, tool_calls, tool_results}]`（OpenAI 消息格式是事实标准）——本质是**append-only 链表/双端队列**（尾部追加、头部裁剪）；多分支探索（一棵回溯树：每个节点存父指针，支持"回到某步重来"）；
- **持久化**：**JSONL append-only 日志**（每行一条消息，天然审计友好、可重放重建状态——Claude Code 的 session 文件就是这个思路）；元数据入库（SQLite/Postgres：sessions/messages 两表，索引 user_id/时间），大附件走对象存储引用；回放=重放 JSONL；
- **检索层**：历史会话向量化入向量库（跨会话记忆，见 Q9）；**前缀树/倒排索引**做关键词级检索。
追问点：为什么 append-only 而非覆盖（可审计、崩溃恢复、A/B 重放）；KV cache 增量会话与服务端状态（prefix 复用）；数据合规（PII 脱敏、保留期限）。

## Q11. Skills 读取超长 SOP 的场景，有哪些优化技巧？（实2 Q3）

- **结构化改造**：把 SOP 从"长文档"改成**任务粒度的 checklist/YAML/流程图（Mermaid）**——标题编号可寻址，Agent 按步骤号取段落而非全文进 context（**渐进披露**，同 Claude Code 的 Skill 加载机制）；
- **步骤级 RAG**：SOP 分块 embedding，执行到哪步检索哪步（query=当前任务+上一步结果）；
- **分层摘要**：先给目录树（一级摘要），Agent 判断需要哪章再展开细节——token 从 O(全文) 降到 O(路径)；
- **子 Agent 分治**：map-reduce——子 Agent 逐段提取与当前任务相关的结论，主 Agent 只收摘要；
- **状态外置**：把"执行到第几步/已完成项"写成显式状态文件（TODO/状态机），重启可续跑，避免靠上下文记忆流程位置；
- **执行校验**：每步后用断言（输出 schema/单元检查）验证是否符合 SOP，错误早停。

## Q12. 编写 Prompt 需要考虑哪些关键因素？如何评估 Prompt 质量？（淘1 Q3）

**编写要素**：

1. **任务与角色定义**：身份、目标、边界（做什么/不做什么）；2. **上下文充分性**：few-shot 示例、领域约束、参考材料注入方式；3. **输出规范**：格式 schema（JSON/Markdown）、字段枚举、长度约束——可机器校验的输出是工程化前提；4. **推理策略**：CoT / ReAct / plan-then-execute 的显式引导；5. **变量化模板**：固定部分与变量部分分离，便于版本管理与回归；6. **安全**：注入防御（不可信内容隔离包裹）、拒答策略、敏感信息红线；7. **成本与延迟**：token 预算、模型分级（简单任务小模型）。

**评估方法**：① 建 **eval 集**（输入 × 期望输出/rubric，覆盖正常+边界+对抗）；② 自动评分：规则断言（schema 校验/单测/精确匹配）+ **LLM-as-judge**（rubric 打分，与人工抽检对齐一致性）+ 偏好对比（A/B side-by-side）；③ 指标：通过率、格式合规率、成本/次、P95 延迟；④ 流程：prompt as code（版本库+变更评审+回归测试），上线后灰度与采纳率监控。

## Q13. 开发一个 MCP 后，如何评测其实际效果？后续如何迭代优化？（控实 Q1）

**评测维度**：

1. **功能正确性**：工具调用参数 schema 合规率、任务完成率（端到端场景集：典型/边界/错误注入）；
2. **效率**：完成任务的平均调用次数、token 成本、时延（工具描述太烂会导致反复试错）；
3. **健壮性**：非法参数/超时/依赖服务故障时的恢复（错误信息是否可被 LLM 理解并自纠）；4. **安全**：越权操作、注入（工具返回内容里藏指令）、资源滥用；5. **兼容性**：不同客户端/host 的行为一致性。

**方法**：固定场景评测集跑批（LLM-as-user 模拟多轮交互）+ 真实使用 trace 回放 + 与"无该 MCP 基线"对照（增益归因）。
**迭代闭环**：失败 case 聚类 → 大多数问题出在**工具描述与 schema 质量**（参数说明不清、缺枚举/默认值）→ 改错误消息（把失败原因写成 LLM 能读懂的自然语言）→ 工具拆分/合并（职责单一、参数≤7 个经验阈值）→ 大结果集分页/缓存 → 重跑评测集回归。上线后监控调用分布与错误率作为下一轮输入。

## Q14. Agent 系统如何实现链路追踪与可观测性？（控实 Q2）

- **Trace 模型**：一次任务 = 一个 trace；**span 树**上每节点 = 一次 LLM 调用 / 工具调用 / 检索 / 子 Agent——对齐 OpenTelemetry 的 GenAI 语义约定（span 记录 prompt、completion、model、token 数、成本、时延、错误）；
- **采集**：框架钩子（LangSmith / Langfuse / Arize Phoenix / OpenInference），自研则在 agent loop 的统一出口埋点；trace_id 贯穿全部 span 并透传到业务日志；
- **指标层**：每步成功率/重试率/工具错误率、**循环与卡死检测**（同类工具调用连续 N 次）、成本与 P50/P95 时延按阶段分解、任务级成功率与人工接管率；
- **回放与调试**：完整记录输入输出（含采样参数）支持确定性回放；span 级 diff 对比 prompt 版本；用户反馈（点赞/点踩）挂到 trace 上回流；
- **告警**：成本/任务突变、错误率阈值、长尾卡死。

## Q15. 目前主流的 Agent 开发框架有哪些？各自特点？（控实 Q4）

- **LangChain / LangGraph**：生态最大；LangGraph 把 Agent 建模为**图状态机**（节点/边/状态），原生支持循环、分支、checkpoint 与 human-in-the-loop——生产可控性的代表；
- **OpenAI Agents SDK**（Swarm 后继）：极简 handoff 模型（Agent 间转移控制权）+ 内置 tracing，轻；
- **Claude Agent SDK / Claude Code**：工程化标杆——agent loop + 工具（文件/bash/检索）+ **Skills 渐进披露 + MCP 工具生态 + hooks**；"少框架、强循环 + 强护栏"路线的代表；
- **AutoGen / AG2（微软）**：多 Agent 对话协作（group chat、code interpreter 沙箱）；
- **CrewAI**：角色化"团队"编排（Captain/Crew），上手快；
- **国内**：**Qwen-Agent**（通义系，原生工具调用/代码执行/长文档，与 Qwen 模型协同——阿里面试提到加分）、ModelScope-Agent。
- 观点题答法：核心 agent loop 本身 ~百行代码（`while: LLM→tool→observe`），框架的价值在**状态管理、可观测、评测、生态（MCP）**；重量级抽象有"抽象税"，生产常选轻内核 + 自建可观测。

## Q16. 【重点】利用 Agent 自动生成 CUDA kernel 的实践与实现方案（阿1 Q2）

工程框架（与 [03 GEMM 与算子优化](./03-gemm与算子优化.md) Q12 同题，这里给 Claude Code 式工程化细节）：

1. **Spec 驱动**：不直接说"写个 kernel"，先让 Agent 生成/对齐 **spec 文件**——算子语义（公式）、输入输出 shape/dtype 清单（含边界 shape）、数值容差（rtol/atol 分级）、性能基线（对齐目标：naive 版实测数字）；
2. **候选生成**：**Triton 优先**（编译快、autotune 扫 tile，Agent 迭代周期秒级）、CUDA 兜底（热点极限场景）；few-shot 提供本仓库已有 kernel 风格模板（Agent 先 grep 参考实现再写）；
3. **验证闭环（护栏）**：编译 → **与 PyTorch 参考对拍**（随机 + 边界 shape + 容差断言）→ `compute-sanitizer` 查越界/竞态 → 超时预算防死循环；正确才进入性能阶段；
4. **性能闭环**：autotune / 手工枚举 tile 配置 → ncu 提取 SOL/带宽 → **把 profile 文本喂回 Agent** 迭代（"memory bound，L1 命中率低 → 建议 smem staging"这类可执行反馈最有效）；
5. **Claude Code 类实践**：CLAUDE.md 写死工程约定（目录/命名/验证命令）、hooks 在每次编辑后自动跑对拍测试（红灯即自动修复循环）、PR 由另一个 critic prompt 审查（性能回归与边界 case）；
6. **度量与结论**：通过率@k（k 个候选至少一个正确）、性能达基线比例、人类修改 diff 率；经验结论——elementwise/reduction/常规融合类 Agent 已可靠超越新手，FA 级复杂融合仍需人类模板与领域知识，"生成-验证-反馈"闭环质量决定上限。

## Q17. 【重点】如何看待用 AI Agent 辅助代码编写、Review 与工程梳理？（云二1 Q8）

按三个场景给实践 + 边界：

- **编写**：最大收益在"有明确验收标准的机械性工作"——TDD 循环（先让 Agent 写测试再写实现）、样板代码、跨文件批量重构（API 迁移）、大仓库导航（Agent 用 grep/glob 先读上下文，比人快）；关键是**小步提交 + 每步可运行**，人审 diff 而非审思路；
- **Review**：规则工具（lint/类型/静态分析）+ LLM 语义审分层——LLM 擅长抓逻辑错误、边界遗漏、并发问题、安全隐患；要控制误报（输出按 P0-P3 分级、可配置忽略），并把 review 意见做成可点击注释；
- **工程梳理**：文档生成（README/ADR 从代码反推）、死代码与依赖梳理、迁移方案（先让 Agent 出计划再执行）、onboarding 问答（对代码库的 RAG）；
- **治理与风险**：幻觉 API（必须编译/测试兜底）、仓库内容注入攻击（不可信文件内容要隔离）、许可证/安全（生成代码的来源合规）、责任边界（AI 辅助 ≠ 免审，关键路径人类拍板）；
- **观点结论**：Agent 把工程师从"写"搬到"定义问题与验收"——工程价值 = spec 质量 × 验证闭环强度；这在 CUDA kernel、迁移、测试补全等"验证容易、劳神"的任务上收益最大（与 Q16 呼应）。

## Q18. 基于现有大模型，如何结合 Agent 方法训练一个金融领域代码 Coder 模型？（云二 Q7、云二2 Q6 开放题）

六段式方案（训练与 Agent 双线交织）：

1. **数据**：金融代码语料清洗（合规/风控/量化/报表/SQL；许可证与敏感信息过滤）；用大模型**蒸馏指令数据**（金融场景函数生成、bug 修复、代码解释），可验证的（有单测/可执行）优先；
2. **环境**：构建**沙箱执行环境**——金融库环境（pandas/量化框架/SQL 模拟器）+ 工具（行情/数据库 mock API）+ 安全隔离（无外网、资源限额）；环境是可验证 reward 的前提；
3. **SFT**：base → 领域续训（金融语料）→ 指令 SFT（蒸馏数据 + **agent 轨迹数据**：大模型在沙箱里跑通的工具调用序列，含失败-重试样本）；
4. **RLVR + GRPO**：可验证奖励 = 编译通过 + **单测通过率** + 静态检查 - 安全违规惩罚；GRPO 组内对比训练（同任务多候选，通过/失败天然分组，见 [31](./31-阿里-训练与算法.md) Q17）；过程奖励（工具调用合理性）可叠加；
5. **Agent 化部署**：模型 + 工具（代码执行、检索合规文档、SQL 执行）+ 规划循环；**self-improvement**：上线 trace 中成功的轨迹回流训练数据；
6. **评测与合规**：自建金融代码 benchmark（合规校验/SQL 正确性/回测脚本）、人审看板；输出合规过滤（投资建议免责/敏感数据）、审计日志。

## Q19. Vibe Coding 实操：现场根据给定问题编码实现（淘1 Q7 实践题）

考察"与 AI 结对把活干成"的纪律，实操要点：

1. **先把验收标准写下来**：让 Agent 先生成测试/对拍用例，人确认后进入实现（tests-first，防"看起来对"）；
2. **最小闭环 → 增强**：先跑通最简单实现（哪怕朴素算法），再让 Agent 逐步优化/重构，每步保持全绿可运行；
3. **给足上下文**：相关文件、约束（依赖版本、性能要求）显式给出；仓库级约定写进 CLAUDE.md 类配置；
4. **报错直接回贴**：编译/测试错误原文喂回，让 Agent 自修（比人肉翻译错误快）；
5. **终审 diff**：交付前通读变更、跑全量验证、删除 Agent 留下的死代码/调试语句。
现场表达：边做边说"我在定义验收标准/我在验证这步"——评分点是流程纪律而非打字速度。
