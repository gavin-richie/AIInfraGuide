## 一、商汤（GEMM 优化项目深挖 + 低比特）

### Q1. 详细描述 GEMM 优化的实现过程（商 1）

分层答（"由粗到细的优化思路"详见 [03](./03-gemm与算子优化.md) Q3）：

1. **naive 基线**：每线程算一个 C 元素，循环 K——每读 2 个数算 2 次乘加，访存计算比 1:1，带宽立刻打满，利用率 <10%；
2. **smem tiling**：CTA 级切 (BM,BN) tile，A/B 块先协同搬进共享内存再计算——全局访存降为 1/(BM·BN)^½ 量级，每次装载被 tile 内复用 BM 或 BN 次；
3. **寄存器 tiling**：每线程算 tile 内 8×8 个 C 元素（Q2），数据从 smem 进寄存器后连续做 64 次 FMA；
4. **向量化访存**：全局↔smem 用 128bit（`float4`/8×fp16）访问；smem 访问避免 bank conflict（padding/swizzle）；
5. **双缓冲/多级流水**：`stages` 级 smem 缓冲，装载与计算重叠，隐藏 global 延迟（Ampere cp.async、Hopper TMA）；
6. **展开 + 计算访存配平**：`#pragma unroll` 展开 k 循环（Q5），保证 ILP；
7. **Tensor Core**（Q10）：fp16 用 HMMA/`mma.sync`，进一步把每线程 8×8 的 FFMA 替换为 warp 级矩阵片 fragment。

仓库实测参考：`solutions/cuda/src/gemm.cu` 的 naive → smem tiling 在 RTX 3090 上 1024³ FP32 从 ~个位数利用率提到 2804 GFLOPS（见 [solutions/README.md](../../solutions/README.md)）。

### Q2. 单个线程计算 C 矩阵 8×8 个元素的原因（商 2）

一笔指令账（推演代码 `gemm_tile.py::tile_resource_report`，128×128 tile / 256 线程）：

- 每线程累加器 = BM·BN/threads = 128·128/256 = **64 个 fp32 寄存器**，排成 **8×8**；
- 每个 k 步：线程需要 A 的 8 个 + B 的 8 个值（双缓冲下 LDS.128 各 2 次，共 **4 次 LDS.128**），然后做 **64 次 FMA**——计算:访存指令比 **16:1**；
- 若只算 2×2（4 累加器）：同样 2 次 LDS 只换 4 FMA，比例 2:1，smem 带宽先爆；若算 16×16（256 累加器）：寄存器直接超 255 上限（Q3）。
- 8×8 是 Ampere 上 256 线程配 128×128 tile 时的**平衡点**：64 个累加器 + 片段/寻址约 144 个寄存器（预算值），既不 spill 又留出 occupancy 空间。

```bash
from pprint import pprint
pprint(tile_resource_report(GemmTileConfig(BM=128, BN=128, BK=64, threads=256)))"
# accum_layout '8x8' / fma_per_thread_per_k 64 / lds128 4 / instr_ratio 16.0 / spill_risk False
```

### Q3. 寄存器是否会发生溢出，如何应对（商 3）

**会**。每线程寄存器上限 255（占用表按 8 的粒度分配），超出部分编译器 spill 到 **local memory**（物理上就是 global memory，走 L1/L2，带宽差一个量级、且不享受寄存器的零延迟），典型症状是 SASS 里出现大量 `LDL/STL`、性能断崖式下降。

预算公式（`gemm_tile.py` 实现的就是它）：

```
est_regs ≈ 累加器(BM·BN/threads) + A/B 片段双缓冲(2·(r+c)) + 寻址(~16) + 杂项(~32)
```

- 128×128/256t：64+32+16+32 ≈ **144**，安全；
- 256×256/256t：累加器独占 256 → **必然 spill**（`tile_resource_report(...)['spill_risk'] == True`）。

**应对**：① tile 变大前先算这笔账（用本模块）；② `__launch_bounds__(256, 2)` 或 `-maxrregcount` 给编译器硬约束（代价是超限部分强制 spill，需权衡）；③ 改用 Tensor Core——累加器变成 fragment 由硬件管理，fp16 同样 tile 寄存器压力减半；④ 减小 BM/BN 或增加线程数（128×128/512t → 每线程 4×4，代价是指令比下降）；⑤ 验证手段：`nvcc --ptxas-options=-v` 看实际 `Used N registers, M bytes spill stores`，Nsight Compute 的 Source 页看 LDL/STL 热点。

### Q4. 单个 tile 内执行了多少次计算（商 6）

三层口径（以 128×128×64 一步为例）：

- **tile 一个 k 步**：CTA 完成 BM·BN·BK = 128·128·64 = **1,048,576 次 MAC**（`macs_per_tile_kstep`）；
- **每线程每 k 步**：8×8 = **64 次 FMA**（Q2）；
- **整个 K 循环**：tile 总 MAC = BM·BN·K；一个 CTA 负责的 tile 数 = (M/BM)·(N/BN)，乘起来就是全局 2·M·N·K FLOPs 的 MAC 一半。

### Q5. `#pragma unroll` 的作用与使用场景（商 5）

**作用**：编译期展开循环体，消除循环控制开销（比较/跳转/地址递增），并把多次迭代的 load 提前发射、FMA 相互错开依赖链，提高 ILP；展开后常数下标还让编译器敢做寄存器分配与向量化（LDS.128/LDG.128）。

**场景与代价**：k 步数为编译期常量（`BK` 是模板参数）且循环体小（我们的 64 FMA/步）时收益最大；无条件展开大循环会导致指令缓存压力与寄存器需求暴涨（可能诱发 spill）——所以 GEMM 里通常 `#pragma unroll` 展开**内层 k 的 8/16 步**，外层保留。CUDA 隐式会展开小循环，显式标注是给编译器确定信号。

### Q6. 与 cuTLASS/CUTLASS 相比，自实现版本的性能对比（商 7）

诚实口径：自实现一般到 **CUTLASS 的 60%-85%** 就很好了。CUTLASS 多出来的部分：① 参数空间全搜索过的 tile/Stage/rasterization 组合；② swizzle 消 bank conflict 的成熟模式（我们只 padding）；③ Hopper 上 warp specialization + TMA 的完整流水线；④ epilogue 融合（bias/activation/残差）针对各形状调优。自实现的价值在**可控**：形状特化（如 ldm+k 小形状）、与上下文 kernel 融合、去掉泛型抽象的 launch 开销。答的时候给出"实测差多少 + 差在哪一层 + 什么场景反超"比笼统说"差不多"加分。

### Q7. Tensor Core 的工作原理与使用方式（商 10）

**原理**：一个 warp 级 MMA 指令完成矩阵乘加，如 `mma.sync.aligned.m16n8k16.f16.f16.f32.f32`——16×8×16 的 D=A·B+C，A/B 按 fragment（每线程持特定行列的寄存器片，`ldmatrix` 协同装载）分布在整个 warp 的寄存器里，硬件内部用高精度累加（fp16 输入 fp32 累加），一条指令顶 64 条 FFMA。INT8 的 IMMA（m16n8k32.s8）计算密度再翻倍（Q8）。Volta 起每代翻 HMMA 吞吐（Ampere 156/312 TFLOPS fp16/bf16 → Hopper 用 WGMMA 异步搬出寄存器）。

**使用方式**：① PTX 内联 `mma.sync` + `ldmatrix`（面试手写层面）；② `wmma` API（`nvcuda::wmma::fragment/mma_sync`，可读性好）；③ 库/CUTLASS `CuTe`（[03](./03-gemm与算子优化.md) Q5）；④ PyTorch 侧就是 `torch.matmul` 走 cuBLAS。要点：fragment 的寄存器布局是固定的（A 行主/B 列主），装载用 `ldmatrix.x4` 一条指令喂 16×16 片，避免手动 gather。

### Q8. 低比特位 GEMM 的开发经验（商 11）

按 W8A8 / W4A16 两路线答（公式详见 [06 量化](./06-量化.md) Q1/Q2）：

- **W8A8**：权重 per-channel INT8 + 激活 per-tensor/per-token INT8，INT8 IMMA（m16n8k32）+ INT32 累加，epilogue 乘 `s_a·s_w[c]` 反量化。算力密度是 FP16 HMMA 的 2×，prefill/大 batch 计算瓶颈场景收益大。难点：激活离群值 → SmoothQuant 把难度从激活迁到权重（[06](./06-量化.md) Q3）；
- **W4A16（weight-only）**：只压权重，kernel 内反量化成 fp16 再 HMMA（Marlin：寄存器分块解包+一次解 8 列，详见 [06](./06-量化.md) Q2）。decode memory bound 场景权重读取量减 3/4，提速接近 4×；GPTQ/AWQ 负责"压得准"（Hessian 逐列补偿 / 等效缩放迁移）；
- **误差直觉**（`quantized_gemm.py` 实测，K=4096 高斯随机权重）：W8A8 点积相对误差 ≈ **1.4%**（每操作数 ~0.9% 的量化噪声按 √2 合成，与理论一致）；W4A16 g128 ≈ **12%**——随机权重对 INT4 是最坏情况，真实 LLM 权重有通道结构、经 AWQ/GPTQ 处理后任务损失远小于这个数字。

### Q9. 是否做过卷积算子优化（商 8）

思路库（详见 [03](./03-gemm与算子优化.md) Q13/Q14 的 conv+BN 融合与推理框架卷积实现）：① **im2col + GEMM**——通用、吃满 GEMM 生态，代价是显存膨胀与拷贝；② **implicit GEMM**（cuDNN/CUTLASS 路线）——不物化 im2col，索引计算内置在装载里，GEMM 主循环不变；③ **Winograd**——F(2×2,3×3) 理论乘法 2.25×↓，只适用小核、数值精度敏感（fp16 慎用）；④ **FFT**——大核/大图；⑤ **NCHW→NHWC + channels last**——向量化与 Tensor Core 要求；⑥ DWConv 走专用 kernel（每通道独立，瓶颈在 smem 复用）。回答时给出"选型取决于 shape/精度要求"的框架即可。

### Q10. 是否了解 PPL（商 9）

商汤自研的高性能计算库（PPL = Paraverse Performance Library 系，开源有 PPLNN 推理引擎与 `ppl.kernel` 系 CUDA 算子库），定位类似 TensorRT/cuDNN 的自研替代：覆盖 Conv/MatMul/Reduce 等算子的 hand-tuned CUDA kernel、INT8 量化推理、图优化与多后端（CUDA/x86/RISCV）。回答策略：不知道就直说，但对标答"自研算子库通常解决的是：官方库覆盖不到的自有算子/形状、极致 batch=1 场景、跨硬件移植"，展示理解而非背名词。

## 二、旷视科技（vLLM / CUDA 算子 / LLaMA 部署）

### Q11. vLLM 推理框架的核心机制与特点（旷实 1）

与 [05 推理引擎与优化](./05-推理引擎与优化.md) Q2/Q3 同族，一句话版：**Continuous Batching**（iteration 级调度，请求随完随走）+ **PagedAttention**（KV 分页、显存利用率 >90%，[04](./04-attention与kvcache.md) Q6）+ **Prefix Caching**（系统提示前缀 KV 块复用）+ **Chunked Prefill**（长 prompt 切块混排，平抑 TTFT）+ kernel 层（FA/量化/CUDA Graph）+ 生态（TP/PP、投机解码、PD 分离）。特点：吞吐导向、OpenAI 兼容 API、量化后端（GPTQ/AWQ/FP8）开箱即用。

### Q12. CUDA 算子优化的具体实践与手段（旷实 2-4）

方法论 = 先定位后动手（工具见 [03](./03-gemm与算子优化.md) Q4：Nsight Compute/Systems、nsys timeline）：

1. **合并访存**：coalesced 128bit 访问、避免跨 cacheline（warp 内连续线程访问连续地址）；
2. **共享内存**：数据复用（GEMM/卷积 tile）、`+padding` 或 swizzle 消 bank conflict（转置 kernel 实测 [02](./02-cuda-编程题.md)）；
3. **减少冗余访存/计算**：寄存器缓存、公共子表达式外提、Welford 单遍统计；
4. **原子操作治理**：smem 私有化 + 树形归约（直方图 19.9× 实测）、warp shuffle 硬件归约；
5. **occupancy 与 ILP 配平**：每线程多元素提高计算访存比（本篇 Q2）、unroll、分支消除；
6. **launch/传输开销**：kernel 融合、CUDA Graph、多流重叠 H2D 与计算、cp.async/TMA 双缓冲；
7. **数值与精度**：fp16/bf16/tf32 Tensor Core、量化。

答题模板：背景（谁调用、shape、SLO）→ profile 结论（SOL 差距、瓶颈在带宽/延迟/占用）→ 手段（上面挑 2-3 个实测有效的）→ 结果（加速比 + 为什么有效）。仓库素材：`solutions/cuda/` 的 14 类 kernel + `--bench` 实测数据。

### Q13. LLaMA 的 .bin 文件做了哪些预处理？是否拆分多个文件？（旷校 1/2）

以 llama.cpp/早期部署为背景：

- **格式**：原始 `pytorch_model.bin` 是 pickle 的 state_dict（乱序、fp32、含优化器无关的命名前缀）——部署前先做**离线转换**：抽权重 → 转 fp16/bf16 → 按 `tensor->layer->name` 重排为**逐层顺序存储**（推理流式 mmap 加载的关键）→ 写自定义魔数+shape 头。更现代的做法是 **safetensors**（零拷贝 mmap、无 pickle 安全风险）；
- **是否拆分**：通常**按层/按大小拆多个 shard**（如每片 ≤2GB 或每层一文件）：好处是① mmap 时按需加载不一次吃满内存；② 多线程/多机并行加载（PD 分离场景 KV 恢复也走同样的分片思路）；③ 单文件损坏影响面小。指标就是**加载吞吐**：单文件串行 fp32→GPU 是最差情况。

### Q14. 所有层如何初始化？CPU→GPU 如何拷贝？forward 流程？（旷校 3/4/5）

- **层初始化**：两种模式——**eager**（构造时按 config 完整建层并填充权重）与 **lazy/meta**（先在 meta device 上建结构不占显存，加载到哪层再物化哪层；vLLM 更进一步按 tp rank 只建本卡分片）。要点：权重加载路径 `np/mmap → torch tensor(share memory) → cuda tensor`，避免走 `torch.load` 的整包反序列化；
- **CPU→GPU 拷贝**：`cudaMemcpy`（同步）/ `cudaMemcpyAsync + cudaStreamSynchronize`（异步）；**必须用页锁定（pinned）内存**做源（见阶跃 Q22）： pageable 内存驱动要先 staging 拷贝，带宽减半且异步失效；大模型加载用多线程分片 + 各自 `copy_` 到 GPU，小块多次搬运可被驱动流水化；
- **forward 流程**（decode 一步）：`token ids → embedding（按 tp 切）→ 逐层 [RMSNorm → QKV proj（GQA）→ RoPE → attention(读 KV cache，Paged) → O proj → 残差 → RMSNorm → gate/up proj → SiLU·gate → down proj → 残差] → 最终 norm → lm_head → 采样`；prefill 一次算整段并写 KV，之后 decode 逐 token。面试常追问 KV cache 显存公式（[04](./04-attention与kvcache.md) Q7）。

### Q15. 内存管理方案与显存池数据结构（旷校 7/8）

- **为什么要池**：训练/推理中张量频繁创建销毁，直接 malloc/free 走 CUDA 分配器有同步与碎片开销；自建池做**预分配 + 复用**；
- **显存池数据结构**：经典 **size-class free list**（ segregated free lists）——按块大小分桶（2^k 粒度），每桶一条空闲链表，分配 O(1) 取头、释放 O(1) 头插，合并靠伙伴系统（buddy）按位找相邻块；或 slab + bitmap；
- **推理特化**：vLLM 的 KV block allocator 本质是**固定大小块的空闲表 + 引用计数**（`block_table[req][逻辑块] = 物理块`，copy-on-write 支持共享前缀，详见 [04](./04-attention与kvcache.md) Q6）；PyTorch 的 caching allocator 则是按 stream 的 size-bin 缓存 + split/merge；
- **CPU 侧配对**：pinned memory 池（加载/换出 KV 用）、对象池化减少 GC。

## 三、智谱（量化粒度与校准）

### Q16. per-tensor / per-channel / per-group 三种量化粒度的区别，哪种最细？（智 1）

| 粒度 | scale 数量 | 典型场景 | 特点 |
|---|---|---|---|
| per-tensor | 1 | 激活（W8A8 的 act）、早期 INT8 | 开销最小，离群值伤害全局 |
| per-channel | 输出通道数 C | 权重标配（W8） | 每行独立 scale，权重分布差异被吸收 |
| **per-group** | C·K/g（沿输入维 K 每 g=128 元素一组） | **W4A16（GPTQ/AWQ）** | **最细**，精度最好；scale 存储与反量化乘法最多 |

结论：**per-group 最细**。实测（`compute_scale` + `fake_quant`，固定 seed）：同一权重 INT8 量化误差 per-tensor > per-channel > per-group 单调下降（`pytest tests/test_t2.py::TestGranularity -q`）。注意 group 是沿 **K 维（in_features）** 切分——比 per-channel（每行一个 scale）更细一层；粒度越细精度越好，但 scale 元数据与 kernel 反量化开销越大，W4 需要 group 就是因为 16 级太粗必须补粒度。

### Q17. minmax 校准与 percentile 校准的核心差异（智 2）

- **minmax**：阈值 = absmax，`scale = absmax/127`——一个离群点就把步长拉大，绝大多数正常值被压进少数格子（详见 [06](./06-量化.md) Q4）；
- **percentile**：阈值 = |x| 的 q 分位（q=99.9% 即忽略最极端 0.1%），`scale = quantile(|x|, 0.999)/127`——**牺牲离群点（clamp 到阈值）换全局更细的步长**；
- **本质差异一句话**：阈值取"绝对最大"还是"分布分位"；minmax 对离群值零容忍截断（保留全部动态范围），percentile 主动截断尾部。选择依据：下游对离群点是否敏感（LLM 激活离群是系统性的 → percentile/更聪明的方法，或干脆 per-channel 化）。

实测（1‰ 离群 ×100）：percentile 的 scale 比 minmax **小一个数量级**（`test_percentile_ignores_outliers`）。

### Q18. KL 散度校准与 MSE 校准的基本原理（智 3）

- **KL（entropy，TensorRT 经典）**：把 |x| 建 2048-bin 直方图，枚举截断阈值 T：参考分布 P = 阈值内直方图 + 尾部质量折叠进最后一格（模拟 clamp）；候选分布 Q = P 量化到 128 level 再摊回直方图；取使 **KL(P‖Q)** 最小的 T——信息论意义下"量化后分布最像原始分布"的截断点。截断太少步长太粗（Q 失真大）、截断太多折叠失配大，KL 自动取平衡；
- **MSE**：对候选阈值集合（如分位网格）直接计算 `fake_quant(x) − x` 的均方误差取 argmin——优化目标直接对齐重建误差，工程实现最简单，GPTQ 系的逐层搜索是它的加权版。

实测行为（`calibration_compare`，RTX 3090/CPU 一致）：均匀分布（无尾部）KL 选择**不截断**；正态分布温和截断（absmax 5.08 → 4.56，≈99.99% 分位）；含 1%×20 离群时 KL 截到 25.7、percentile(99.9) 截到 26.9，而 **MSE 反而选 100% 不截断**——平方误差会保护大幅值样本，这就是"目标函数决定截断行为"的活例子（面试讲出来是加分项）。

### Q19. 手写 minmax 校准和 percentile 校准（智 8，现场编程）

`calibration.py` 两函数即答案（面试 15 行版）：

```python
def minmax_scale(x, num_bits=8):        # 对称 int8
    return x.abs().amax() / (2 ** (num_bits - 1) - 1)

def percentile_scale(x, q=99.9, num_bits=8):
    threshold = torch.quantile(x.abs().flatten(), q / 100)
    return threshold / (2 ** (num_bits - 1) - 1)
```

### Q20. SmoothQuant 的量化粒度与工作原理，与 AWQ、GPTQ 对比（智 4）

[06 量化](./06-量化.md) Q3 已给全对比表，本篇补智谱追问的**粒度**细节：SmoothQuant 的迁移缩放 $s_X$ 是 **per-channel（通道级）** 的——对激活 X 的每个输入通道 j 取 $s_j = \max|X_j|^\alpha / \max|W_j|^{1-\alpha}$，等价变换 $Y=(X \diag(s)^{-1})(\diag(s)W)$ 把激活的通道级离群"搬"到权重上，之后**权重/激活都可安全 per-tensor INT8**（W8A8）。对比：**AWQ** 也是 per-channel 缩放（对权重显著通道 ×s、激活 ÷s，等价且不训不反传，缩放系数按网格搜索）；**GPTQ** 不缩放，逐列量化用 Hessian 信息把误差补偿到未量化列（per-group 存 scale）。流程上：SmoothQuant/AWQ 是"缩放→RTN 量化"，GPTQ 是"误差补偿式量化"。

### Q21. NV FP4 的量化原理、缩放因子维度、存储格式；FP8 vs FP4 场景（智 5/6）

[06 量化](./06-量化.md) Q5 已解 FP8/FP4 基础，本篇补 NV FP4（Blackwell）要点：

- **原理**：FP4 用 **E2M1**（2 指数位 1 尾数位，±{0,0.5,1,1.5,2,3,4,6} 共 16 值）——纯 4bit 动态范围只有 2^±2，必须配两级缩放：**block-wise 二级缩放**，每 **16 个连续元素**一组（沿存储的最后一个维度/innermost dim 计算），组内 E2M1 量化、组级 scale 是 **E4M3(FP8)**；
- **缩放因子维度**：`scale_factor` 沿 innermost 维（每 16 元素一个 FP8 scale，`tensor_core_scale` 与之配套做 tensor core 内的逐 block 反量化）；
- **存储格式**：权重 fp4 打包（2 元素/byte）+ 每 16 元素一个 FP8 scale（+可选 tensor-core 级二次幂对齐）；代表格式 nvfp4 = e4m3 scale × e2m1 data；
- **FP8 vs FP4 场景**：FP8（E4M3/E5M2）动态范围接近 fp16，训练/推理通吃，Hopper 起硬件支持，W8A8/A8 训练;NV FP4 只在 Blackwell tensor core 有 2× 于 FP8 的算力，适合**推理端 weight-only 或激活离群可控的大批量 GEMM**；精度敏感/离群严重用 FP8，极致带宽与算力密度（decode 大 batch、MoE 专家权重）试 FP4，两者经常组合（FP8 scale + FP4 data）。

### Q22. DMA 与 RDMA 的原理及区别（阶 1）

- **DMA**（Direct Memory Access）：**单机内**的搬运协处理器——CPU 只下发描述符（源/目的物理地址、长度），DMA 引擎自行在外设/内存间搬运，完成后中断通知；解放 CPU 且并行于计算。GPU 语境：SM 不直接读 PCIe/MMIO，拷贝由**拷贝引擎（CE）**执行，`cudaMemcpyAsync` 即下发 DMA；
- **RDMA**（Remote DMA）：**跨机**绕过对方内核协议栈的 DMA——网卡（RNIC）硬件直接读写远端**应用注册的内存区域**，数据路径不进远端 CPU/OS（零拷贝、内核旁路），延迟从 ~几十 μs 降到 ~1-3 μs，CPU 占用近零。动词三件套：注册 memory region（pin + 映射）→ post WR（SEND/RECV、WRITE/READ）→ 轮询 CQE 完成事件。 verbs/RoCE v2（以太网）/IB；NCCL 底层即用 RDMA（或 NVLink/SHARP）；
- **区别一句话**：DMA 是单机总线级搬运引擎；RDMA 是网络化的 DMA（把"远端一段内存"当"本地外设"直接读写），多出的三件事——网络传输、内存注册安全、完成队列语义。集合通信库（NCCL）在两者之上抽象统一接口。

### Q23. cudaMemcopy 时为什么需要 pin（锁定）内存？（阶 2）

**原因**：GPU DMA 引擎只能访问**物理地址连续且不会被动换页**的内存。普通 pageable 内存由 OS 可任意换出/迁移，驱动无法直接交给 DMA，只能先拷到驱动内部的 staging pinned buffer（多一次 CPU 拷贝 + 锁页开销）。pinned（页锁定）内存被 OS 承诺不换页，DMA 可以直取，因此：

- **带宽**：省掉 staging 中转，H2D/D2H 满 PCIe 带宽（约 12-25 GB/s，pageable 通常只有一半）；
- **异步性**：`cudaMemcpyAsync` 只有配 pinned 源/目的才真正与 kernel 计算重叠（pageable 版会退化成同步拷贝）；
- **代价**：pin 物理页不可换出（占用 ram、过度分配拖垮系统），所以要池化复用而非反复 `cudaMallocHost`；CPU 侧 `torch.tensor.pin_memory()` / DataLoader 的 `pin_memory=True` 即此意。

### Q24. 进程与线程的核心区别（阶 3）

- **资源单位 vs 调度单位**：进程是**资源分配**单位（独立虚拟地址空间、文件描述符表），线程是 **CPU 调度**单位（共享所属进程的地址空间/全局变量/堆，独有栈/寄存器/PC）；
- **切换成本**：进程切换换页表 + 刷 TLB（隔离带来高成本）；线程切换只换上下文（同地址空间）；
- **通信/同步**：进程间要 IPC（管道/共享内存/消息队列/socket，RDMA 也算一种）；线程间直接读写共享变量 + 锁/原子（[09 C++ 与系统基础](./09-cpp与系统基础.md) 的锁家族）；
- **故障域**：线程崩（段错误）整个进程陪葬；进程隔离好。GPU 语境延伸：单机多卡常用**一进程多线程**（NCCL 通信线程与计算线程）与**多进程一卡**（MPS/MIG）；多机训练 torchrun 起多进程（spawn），防 GIL/故障传播——面试结合分布式谈"为什么 DDP 是多进程"（隔离故障、绕开 GIL、与 NCCL 多进程通信器天然对齐）是加分项。
